関数従属性から見た
DocumentV1 の構造的整合性

DocumentV1 を「関数従属性（どの項目がどの項目を一意に決めるか）」の観点で読み直した記録。 同一のドメイン関係が複数のフィールドに分散し、読み取り側が推測で解決している箇所を特定し、 その機構と是正案を示す。カード本文・空間配置・見立て（claimType / holdState）は 対象外とする ── これらは正規化になじまない KJ法固有の表現であり、本分析の適用範囲ではない。

F-3 統合関係の4重表現（検証済み） F-4 解決経路の固定値（潜在欠陥） F-5 島所属の未強制

本書が正本（AGENTS.md §3）。データ構造の運用境界は data_model_operations_overview.html、 型定義は schemas.md、責務境界は architecture.html を正本とする。
本書は分析であり決定ではない。実装着手には ADR-0047 のゲート判定と issue 起票を要する。

01

分析の枠組みと適用範囲

関数従属性 x → y とは「x の値に対して y の値が一意に対応する」関係を指す。 本分析の主張は単純である ── 同一の関数従属性を複数箇所に保持すると、 それらを一致させる仕組みが存在しない限り、読み取り側は推測せざるを得なくなる。

DocumentV1 は単一JSONスナップショットであり、物理DBの外部キー制約を持たない （documents.payload_json は不透明なTEXT）。したがって整合性を保つ手段は 検証コード（validate_doc.ts）の不変条件だけである。 この前提は変えない ── ローカルファーストと単一ファイル可搬性はアーキテクチャ目標であり、 物理正規化はその目標と衝突する。

1.1 適用範囲の線引き

領域適用理由
統合関係、島所属、辺の端点、レビュー帰属、判断ログ、テナント/利用者対応適用するシステム内世界の確定事実。「統合されたか否か」は解釈ではなく事実であり、関数従属性が実在する
text / summaryText / critique適用しない内容は正規化の対象ではない。言葉を選び直すこと自体がKJ法の作業
x / y（空間配置）適用しないKJ法において配置は意味である。正規形の概念が適用できない
claimType / holdState / critiqueTags適用しない利用者の現在の見立て。可逆であり、確定を意図しない

この線引きから得られた対比軸 ──「確定事実」と「現在の見立て」── は、本分析の範囲を超えて SafeMode の redact 判定、export の既定ON/OFF、L0〜L3 の割当根拠にも適用余地がある。本書では指摘に留める。

02

F-3 統合関係が4フィールド・2実装に分散

検証済み

「N枚のカードを1枚へ統合した」というドメイン関係は一つである。しかし現行実装では、 2つの関数が、排他的なフィールド集合で、同じ関係を書いている。

書き込む対象 applyCanonicalization()
domain/canonical_ops.ts		 createRepresentativeMerge()
domain/representative_merge.ts
新カード（統合先）へsources: string[]repOf: string[]
元カード（統合元）へcanonicalId: stringmergedIntoCardId: string
島の更新元カードを残したまま統合先を追加rewire 指定時のみ元カードを除去して統合先を追加
readingOrder元カードを除去し統合先を挿入更新しない
edges更新しないrewire 指定時のみ端点を張り替え

結果として同一のドメイン事象が、2種類の構造的に異なる文書状態を生む。 どちらの経路を通ったかは、どのフィールドが埋まっているかからしか判別できない。

挙動差は保持すべき仕様である。 applyCanonicalization() が元カードを島に残すのは、 「代表カードと出典カードを両方たどれる」という kj-atlas 固有の設計 （isSourceCard()、出典カードの開示UI）に基づく。 したがって是正の方向は2つの挙動を1つに統合することではなく、 関係の重複だけを解消して挙動差を明示的な属性にすることである。

03

F-4 解決経路が固定値で返る

潜在（未露出）

resolveRepresentativeOriginTrace() は統合元IDを3経路から収集する ── repOf、mergedIntoCardId の逆引き走査、sources ── にもかかわらず、返り値の representativeResolvedBy を 経路によらず "repOf" に固定している。 

// domain/merge_traceability.ts

  if (representative?.repOf && representative.repOf.length > 0) { ... }      // 経路1
  for (const card of document.cards) {
    if (card.mergedIntoCardId === representativeCardId) { ... }               // 経路2
  }
  if (representative && sourceIds.size === 0 && Array.isArray(representative.sources)) { ... }  // 経路3

  return {
    representativeCardId,
    sourceCardIds,
    missingSourceCardIds,
    representativeResolvedBy: "repOf",   // ← 経路2・経路3で解決しても "repOf" と報告される
  };
呼び出し経路影響状態
resolveDecisionOriginTrace() 経由影響なし呼び出し側が実際の解決経路で上書きするため、正しい値が返る
App.tsx からの直接呼び出し誤った来歴を返す現時点では呼び出し側が sourceCardIds / missingSourceCardIds のみを使用し、representativeResolvedBy を参照していないため未露出。この値を使う変更が入った時点で顕在化する

単体テストは toEqual で固定値 "repOf" を期待しているため、この不整合を検出しない （merge_traceability.test.ts）。F-3 を是正すれば本項は構造的に消滅する。 是正しない場合は、返り値を実際の経路に合わせる単独修正が必要。

04

F-5 島所属の関数従属性が強制されていない

構造

App.tsx はカードから島を引くとき islands.find(i => i.cardIds.includes(cardId)) ── 最初に一致した島を採用 ── としている。これは cardId → islandId を関数（一意）とみなす実装である。 しかし Island.cardIds[] は逆方向の配列であり、 同一カードが複数の島に列挙されていても strict 検証は通過する。 関係が「島 → カード群」の形で保持されているため、「カード → 島」の一意性を表現できていない。

4.1 既存の一意制約は手書きで、対象が非対称

複合キー相当の一意制約は、既に一部の関係で手実装されている。ただし対象が揃っていない。

関係一意性の扱い実装箇所
evidenceLinksあり ── (fromCardId, toCardId, type) の重複を検出validate_doc.ts / validate.ts
shelfあり ── cardId の重複を検出validate_doc.ts
島所属 (islandId, cardId)なし ── 島をまたぐ重複を検出しない—
統合関係 (統合先, 統合元)なし ── 4フィールド間の一致も検証しない—

一意制約が必要であること自体は既に認識され実装されている。欠けているのはどの関係に必要かを 体系的に判定する手順であり、個別の実装力ではない。

05

F-6 イベントログが状態から導出されている

構造

kj-atlas には統合判断のイベント記録が既に存在する ── DocumentV1.mergeSuggestionDecisions[] と物理テーブル merge_decision_logs。 ところが domain/merge_decision_audit.ts は、監査イベントを作るために resolveDecisionOriginTrace() を呼び、カード側に散らばった状態から 来歴を再構成している。依存が逆転している。

なお「追記のみ」を全モデルへ広げる主張ではない。不変であるべきは 確定した事象（統合判断、レビュー帰属、RoundSnapshotV1）であり、 作業中の DocumentV1 は可変のままでよい。現行の DocumentV1（可変）と RoundSnapshotV1（不変）の分離はこの区別と整合している。

06

F-7 機能単位の追加が構造を発散させている

構造

DocumentV1 は21フィールドを持ち、うち12が optional である。 optional フィールドの多くは、機能issueが1件ずつ追加した経緯を持つ （shelf ← DOMAIN-EXPR-02、contradictionSignalDecisions ← DOMAIN-EXPR-04、 ka ← DOMAIN-KA-01、meta ← DOMAIN-TRACE-01、 representativeCue ← DOMAIN-VISUAL-CUE-01）。

これは設計の失敗ではなく、採用している手順の必然的な帰結である。 機能から出発すると、その機能が必要とする最小のフィールドが追加される。 関係から出発した場合と違い、既存の関係と統合されるかどうかは検討の対象にならない。 F-3 はまさにこの形で生じた ── 2つの機能issueが、同じ関係を、互いを知らずに実装した。

ADR-0058（単一 DocumentV1・追加のみ）は version 分裂という別の失敗を正しく防いでいる。 ただし「追加のみ」は構造の縮約経路を持たないため、 関係の重複を検出する手順を伴わない限り、発散は単調に進む。 本書が提案するのは ADR-0058 の撤回ではなく、その手前に 「新しい optional を足す前に、既存の関係と重複しないかを確認する」 という一段を挟むことである。

07

是正案

物理DBの正規化は行わない。ローカルファーストと単一JSON可搬性を壊すため、 適用範囲を「文書内の論理不変条件」に限定する。

段内容対応する所見破壊的変更
R1 resolveRepresentativeOriginTrace() の返り値を実際の解決経路に合わせる F-4 のみ なし。単独で実施可能。スキーマ不変
R2 関数従属性の不変条件を validate_doc.ts へ追加 ── 島所属 (islandId, cardId) の島をまたぐ重複、 統合関係4フィールドの相互一致 F-5、F-3の検出 なし（検証強化のみ）。ただし既存文書が新規則で不合格になり得るため、 warn 段階を先行させる判断が要る
R3 統合イベントを DocumentV1 内の正本として定義し、 カード側4フィールドを導出値へ格下げ。統合方式 （canonicalization / representative）と 島・辺の張り替え有無をイベント属性として明示 F-3、F-4、F-6 あり（追加は非破壊、格下げは破壊的）。 ADR-0058 の範囲内で「追加＋導出」に留めるか、version gate を要するかの判断が必要
R4 TS↔Python の契約ドリフト検出テストを追加（F-1 の再発防止）。 7表現のうち導出可能なものを機械生成へ移す F-1（既報）、F-7 なし。テスト追加
R5 設計手順として「新しい optional を追加する前に、表現しようとしている関係が 既存の関係と重複しないかを確認する」を AGENTS.md へ追記 F-7 なし。手順の追記

R1・R4・R5 は独立に実施できる。R2 は R3 の前提となり、R3 は最も大きい。 R3 を選ばない場合でも R1・R2 は F-4・F-5 を解消する。

8.1 本分析が到達していない範囲

  • 既存データへの影響を測っていない。 F-3 の不整合が実際の保存済み文書に どれだけ存在するかは未調査。R2 の warn 段階で計測してから R3 の要否を判断すべきである。
  • 辺の端点（fromKind/toKind が optional）は分析したが本書に含めていない。 端点種別が省略可能なため同一IDが文脈で別実体に解決され得るが、 現行の運用規模で問題が顕在化した証跡を確認できなかった。ADR-0047 R-1 の基準を満たさないため保留。
  • summaryText と summaryHistory[] の導出関係も同型の課題だが、 F-3 と違い読み取り時の推測を発生させていないため、優先度を下げた。
  • 本書は分析であり決定ではない。 R1〜R5 の実施には ADR-0047 のゲート判定と issue 起票を要する。

8.2 参照した外部知見

関数従属性・定義域制約・複合キーの観点、および「追記のみの記録を正本とし可変な集計を導出する」構成は、 渡辺幸三による業務システム設計の一連の論考（ブログ「設計者の発言」、 情報システム学会メールマガジン 2022.10.28 No.17-07「『データ・ファースト』な設計スタイルを身につけよう」、 三要素分析法）を参照した。

ただし当該体系は業務システムの物理DB設計を前提とする。 kj-atlas はローカルファーストの単一JSON永続化を目標に持つため、 物理正規化・複合主キーの主張はそのまま適用せず、 論理不変条件の設計としてのみ採用した（§07 冒頭）。 またカード本文・空間配置・見立てへは適用しない（§1.1）。
