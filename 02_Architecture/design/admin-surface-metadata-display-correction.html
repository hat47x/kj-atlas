管理面データ境界の実務補正

区分: 設計判断 / 更新: 2026-08-08
対象: master-data-settings-ui-ux-concept.md §3.3 管理面の本文非表示原則の補正
起票理由: 原理が強固すぎて運用者の識別能力を奪い、実務に支障があるため

補正の本質: 「本文非表示」原則は正しいが、「本文」の定義が広すぎた。 管理面で docIdのみ を表示する運用は、文書数が増えた時点で破綻する。 識別メタデータ（タイトル）は「本文」ではなく「索引情報」であり、管理面での表示は安全上の損失より識別上の利益が大きい。

1. 現行制約の診断

以下の3箇条が、実務上の識別能力を奪っている。

#現行規定出典実務上の支障
P1 「文書を参照する必要がある行ではdocIdだけを使い、タイトルへ解決しない」 master-data-settings §3.3 L121 管理者が50文書のアクセス設定をする時、doc-7f2a のようなopaque IDだけでは識別不能。運用ミス（誤った文書の公開範囲変更）を誘発する
P2 「一覧／検索対象はdocId、visibility、binding状態、policy version、updatedAtだけとする。文書タイトル、本文、カード、review状態、件数集計は取得も表示もしない」 master-data-settings §3.3 L134 Tenant Adminが文書アクセス設定を行う際、対象文書の誤認リスクが高い。特に類似内容の文書が複数ある場合、docIdのみでは区別不能
P3 「一覧の表示候補はregistrationId、表示名、docId、状態、作成日時、作成主体の固定メタデータ。文書タイトルと本文は表示しない」 master-data-settings §3.3 L144 エージェント登録時に、どの文書に対してtokenを発行するのかをdocIdのみで判断させるのは危険。誤った文書へのtoken発行は安全境界の侵害に直結する

2. 補正: 「本文」の定義を分解する

現行の「本文非表示」原則は、以下の2つを区別せずに禁止していた。

🟢 管理面で表示してよい情報 — 識別メタデータ
  • タイトル — 文書の識別子。利用者が文書に与えた名前。CardやNarrativeと異なり、それ自体が知的成果物の本体ではない
  • docId — システム内部の識別子
  • updatedAt — 最終更新日時（識別の補助）

これらは「索引情報」であり、Workspaceの文書一覧でも既に表示されている。 管理面でこれらを表示しても、文書の知的成果物（カード・島・関係・ナラティブ）は一切露出しない。

🔴 管理面で表示してはならない情報 — 知的成果物本体
  • カード本文 (Card.body, Card.ka.*)
  • 島の構造・形状 (Island.shape, Island.geometry)
  • 関係線 (Edge)
  • ナラティブ (Narrative)
  • レビュー状態 (ReviewAttribution)
  • 保留・違和感の内容 (Card.holdState詳細, CritiqueInput)
  • 証跡リンク (EvidenceLink)
  • 件数集計（カード数・島数・未レビュー件数等。統計であっても本文の特徴を漏らす）

これらは「本文」であり、管理面の目的（アクセス制御・外部接続管理）に必要ない。 むしろ、管理権限と本文閲覧権限の分離（職務分離）を破壊する。

3. 条文補正

3.1 文書アクセス設定面（§3.3 第2項）

現行 「一覧／検索対象はdocId、visibility、binding状態、policy version、updatedAtだけとする。文書タイトル、本文、カード、review状態、件数集計は取得も表示もしない。」

補正 「一覧／検索対象はタイトル、docId、visibility、binding状態、policy version、updatedAtとする。本文（カード・島・関係・ナラティブ・レビュー状態・証跡リンク）、件数集計は取得も表示もしない。タイトルは識別メタデータであり、本文には該当しない。」

3.2 エージェント登録面（§3.3 第3項）

現行 「一覧の表示候補はregistrationId、表示名、docId、状態、作成日時、作成主体の固定メタデータ。文書タイトルと本文は表示しない。」

補正 「一覧の表示候補はregistrationId、表示名、対象文書タイトル、docId、状態、作成日時、作成主体の固定メタデータ。本文（カード・島・関係・ナラティブ・レビュー状態）は表示しない。文書タイトルは対象文書の誤認防止のために表示する。」

3.3 Adminヘッダー境界説明（§3.3 導入部）

現行 「Adminヘッダーには、通常Workspaceと混同しない名称と『この画面は文書本文を表示しません』という境界説明を置く。文書を参照する必要がある行ではdocIdだけを使い、タイトルへ解決しない。」

補正 「Adminヘッダーには、通常Workspaceと混同しない名称と『この画面は文書本文（カード・島・ナラティブ）を表示しません』という境界説明を置く。文書を参照する必要がある行では、識別メタデータとしてタイトルとdocIdを併記する。タイトルを介した横断本文検索・プレビューは行わない。」

4. 新規要求: 文書タイトル生成（AI提案）

要求: 文書の内容から人間向けのタイトルを生成する仕組みが必要である。 現行は新規作成時に利用者が手動でタイトルを入力する以外に手段がなく、 内容を反映したタイトルが付与されない文書が蓄積しやすい。

4.1 設計判断

タイトル生成は、既存のAI提案パターン（proposal-only）に完全に収まるため、新たな原理的問題を生まない。

観点判断
業務設計利用者が文書の内容を表現するタイトルを効率的に付与できる。新規作成直後・編集中・共有前の各タイミングでタイトル提案を受けられる
データ設計タイトルはDocumentV1.title（L1 Supported）の一部。AI提案は派生データ（L3）であり、人間がAdoptした結果のみが文書本体に残る。変更なし
機能設計既存のSuggestionPanelパターンを流用。提案種別「title」を追加。1件ずつの明示Adopt/Reject。一括適用なし。SafeMode ON時はカード本文をAIへ送信しない（タイトル提案に必要な範囲だけをcontextとして投影）
反スコアリング複数候補を提示するが、順位付け・スコア・「最適」表示は行わない。候補は並列に提示し、利用者が選ぶ
複雑性予算既存SuggestionPanelへの提案種別追加（置換ではなく包含）。新規画面は作らない

4.3 制約

  • AI提案はproposal-only。人間が明示的にAdoptするまでタイトルは変更されない
  • 複数候補を並列提示し、順位・スコア・「最適」表示は行わない
  • SafeMode ON時は未レビュー本文をAIへ送信しない。provider=none時は機能自体を無効化（provider無効状態を劣化フォールバックとして扱わない）
  • タイトル提案の採用はMergeDecisionLogへ記録しない（タイトルは文書構造の一部であり、カードや島のようなmerge判断対象ではない）
  • タイトル変更は通常の文書保存競合処理（PUT /docs/{doc_id}のversion check）に載せる

5. 理念との衝突評価

今回の補正は、以下の核（ui_design_handoff.md の「侵してはならない核」）と衝突しない。

核衝突評価
コア価値は「少ない操作で曖昧さを保持できること」✅ 衝突なし。管理面のタイトル表示は識別のための最小情報追加であり、操作の複雑化ではない
保留は意味を確定しない健全な状態✅ 衝突なし。管理面は保留状態を扱わない
キャンバスを主、AIとの対話を従とする✅ 衝突なし。タイトル提案はAI提案パターンに完全準拠
単一正解、ランキング、採点で結論を誘導しない✅ 衝突なし。タイトル候補は並列提示
SafeModeは既定ON、共有前確認を必須✅ 衝突なし。タイトル提案はSafeModeを尊重
管理面の本文非表示⚠️ 補正あり。ただし「本文」の定義を「知的成果物本体」に限定する実務的補正であり、原則の否定ではない

理念との衝突が大きい項目はない。補正は「本文非表示」原則の定義の精緻化であり、原則そのものの放棄ではない。
