座標は誰のものか
── 人間とAIの表現非対称性とキャンバス階層の投影設計

KJ法キャンバスにおいて、座標が意味を持つのは人間側であり、生成AIにとって意味を持つのはカード・島のあいだの論理的関係である。 この非対称性を、キャンバスの階層構造の設計へどう反映するかを検討する。 結論から述べると、必要な論理投影はすでに3つ実装されており、AI入力経路だけがそれらを迂回している。

AIへ渡る関係情報: 実質ゼロ（実測） 座標非依存の論理投影: 既に3実装

本書は AGENTS.md §3 の文書形式方針（02_Architecture/ 直下・HTML + Mermaid 単独）に従う分析文書である。 責務境界は architecture.html、 データ構造の運用境界は data_model_operations_overview.html を正本とし、本書はそれらを置き換えない。
本書は分析と設計提案であり、決定ではない。§07 の候補は ADR-0047 のゲート判定と issue 起票を経て着手する。 実測 はコード実読・実行で確認した事実、提案 は本書の設計提案である。

01

問い ── 座標は「まだ言語化されていない意味」である

KJ法において、カードを動かす行為は結果の記録ではなく思考そのものである。 「この2枚は近い気がする」という感覚は、まだ言葉になっていない。近づけて置くことで、その感覚が保持され、後から検討できる。 座標は、言語化される前の意味を仮置きする媒体として機能している。

ここから、AIへ座標を渡すことの問題が導かれる。座標を渡して「この配置から意味を読み取れ」と求めることは、 人間がまだ決めていないことをAIに推測させることに等しい。これは本プロジェクトの明文の要求と衝突する。

AIは内容を採点せず、出典や文脈を推測せず、利用者の確認前に本文や状態を変更しません。
── 00_Prompt/domain.md:88

逆に、人間が言語化を完了した層── 島に囲んだ、表札を立てた、関係線を引いた、主張種別を付けた ── は、推測ではなく人間が確定させた事実である。AIが扱ってよいのはこちらであり、また扱うべきなのもこちらである。

02

KJ法自身が持つ「昇格の梯子」

重要なのは、この「空間 → 論理」の変換が本プロジェクト固有の設計判断ではなく、 KJ法という方法そのものの手順だという点である。KJ法の各工程は、暗黙の空間的意味を明示的な論理構造へ昇格させる段として並んでいる。

設計上の含意はこうである。AIとの協働境界は、この梯子のどこかに引くのではなく、梯子の左端と右側のあいだに引く。 人間は梯子を登る主体であり、AIは登り終えた段の上でだけ働く。

どのプロンプトも edges を渡していない。 ADR-0048 D3 で固定したKJ法の関係語彙（related / negate（対立）/ causal / mutual / equivalence）は、 AIに一度も届いていない。evidenceLinks、relationSummaries、claimType、 島階層（parentIslandId）、表札（placardCardId）も同様である。

つまり現状は「AIが座標を受け取ってしまっている」という問題ですらない。座標が渡るのは suggest-layout 1件だけで、 これは出力が座標である以上むしろ妥当である（§05.3 の例外）。実際の問題は逆方向にある ── AIは論理構造をほとんど何も受け取っておらず、キャンバスを「文字列の袋」として扱っている。

3.1 具体的に何が起きているか

エンドポイント受け取っていない構造と、その帰結
POST /ai/detect-contradiction 矛盾を扱うAPIが、人間が既に記録した矛盾を見ていない。 2枚のカードの text だけを受け取る（routes/ai.py:746-752）。EvidenceLink.type = "contradicts" も contradictionState（unconfirmed/confirmed/held/resolved）も渡らないため、人間が「確認済み」「保留」と判断済みの矛盾を再提示しうる。
POST /ai/suggest-card-groups グルーピング提案が、既存のグルーピングを知らない。 id と text の平坦なリストのみ（routes/ai.py:725-731）。既存の島、島の階層、カード間の関係、holdState（保留中）を見ずに提案するため、人間が既に下した判断と衝突する候補を出しうる。
POST /ai/generate-narrative readingOrder は渡るが edges は渡らない。叙述の骨格である因果（causal）・対立（negate）が使えず、順序だけから文章を組むことになる。

本件で最も重要な発見は、座標非依存の論理投影が既に3つ実装されており、AI入力経路だけがそのすべてを迂回していることである。 新しい層を発明する必要はない。

05

設計原則の提案

提案

5.1 三層への整理

DocumentV1 のフィールドを、誰にとって一次情報かで3層に分類する。 物理的な分割ではない ── 単一JSON可搬性（architecture.html）は維持し、投影の規則として整理する。

層フィールド一次情報の所有者AIへの扱い
空間層 x, y, transform, geometry, shape, collapsed 人間 渡さない。ただし構造的事実へ変換したものは渡してよい（5.2）
論理層 cardIds, parentIslandId, placardCardId, edges, evidenceLinks, claimType, readingOrder, relationSummaries 人間が確定させた共有事実 渡す。現在ほぼ渡っていない部分（§03）
状態層 textReviewed, reviewState, holdState, critique, critiqueTags 人間の現在の見立て 選択的に渡す。「保留中」「違和感あり」は AI が尊重すべき境界（CVI-7）。ただしAIが解消・正当化してはならない

5.2 「未言語化の近接」の扱い ── 座標を渡さずに事実だけ渡す

空間層を一律に遮断すると、ひとつ失うものがある。「空間的にまとまっているが、まだ島になっていないカード群」という状態は、 KJ法の梯子（§02）の途中にいることを示す有意味な情報である。

ここは区別できる。「近接している」という観測を渡すことと、「近接が何を意味するか」を推測させることは別である。 前者は事実の報告であり、後者は domain.md が禁じる推測にあたる。したがって:

  • 渡してよい: 「未所属カードが N 枚あり、そのうち M 枚は空間的に1つのまとまりを成している」という構造的事実。座標そのものは渡さない。
  • 渡してはならない: 生の x / y、および「この配置はこういう意味だと思われる」という解釈。
  • AIの応答は「まだ島になっていない塊があります」という気づきの提示までとし、島の中身を提案する場合も proposal-only（CVI-2）として人間の確定を待つ。

これは「AIが人間に梯子を登るよう促す」形であり、AIが勝手に梯子を登ることとは異なる。KJ法の主体性を侵さずにAIが貢献できる領域である。

5.3 例外 ── 出力が空間である場合

POST /ai/suggest-layout は出力が座標そのものであるため、入力に座標を含めることが妥当な唯一の例外である。 ただしこれは「例外」として明示されるべきで、既定ではない。加えて現状は座標を渡しながら関係を渡していないため、 「関係の近さを配置へ反映する」という配置提案の本来の根拠を欠いている。この例外においてこそ edges が必要である。

5.4 階層構造への含意

「AIにどの粒度で渡すか」は階層の設計と直結する。既存構造には次の非対称がある。

要素論理的定義空間表現
島cardIds（一次）shape は cardIds＋座標から導出され、generatedFrom.versionToken で陳腐化を追跡（polygon_stale.ts）
島の関係カード辺からの集約導出（getDerivedIslandEdges）描画時に線として表現
カード無し ── 論理的な「位置」を持たないx / y が一次

島は「論理が一次・空間が導出」という正しい向きで設計されているのに対し、カードだけが空間のみを持つ。 カードの論理的位置は「どの島に属するか」であり、それは Island.cardIds に逆方向で保持されている （functional-dependency-integrity-2026-08-06.html の F-5「島所属の関数従属性が強制されていない」と同根である）。 階層設計としては、カードの論理的所属を一次情報として扱えるようにすることが、AI投影の前提になる。

06

付随所見 ── 構造の欠如が生む代償

POST /ai/assess-card-importance（routes/ai.py:763-770）は、各カードを high / medium / low で評定するよう LLM に求めている。 これは明文の要求と抵触する。

AIは内容を採点せず、出典や文脈を推測せず…
── 00_Prompt/domain.md:88

（非目標）画像による自動分類、品質評価、重要度評価、感情判定。
── 00_Prompt/representative_visual_cue_requirements.md:28

本書の文脈で注目すべきは、この採点が「構造が無いこと」の代償として現れている点である。 AIに関係グラフが渡っていれば、「重要さ」は採点ではなく構造的観測として答えられる ── 「このカードは3つの島にまたがる5本の関係から参照されている」「このカードは2件の矛盾の当事者である」。 これは順位付けではなく事実の提示であり、反スコアリングと衝突しない。 論理投影を渡すことは、採点への誘因そのものを減らす。

本項は本書の主題（投影設計）に隣接する独立の課題である。エンドポイントの存廃は別途判断を要する。

検討課題（ADR / issue 化の候補）

提案
候補内容性質ADR-0047 ゲート見立て
C1 AI入力を DocumentV1 直渡しから論理投影経由へ切り替える。既存の buildAbstractMapExport / getDerivedIslandEdges をサーバ側へ持つか、ContextBundle を実装して接続するかを決める 設計判断。ADR が要る R-3（CE-0 の CE0-CTX-IF 契約と実装の乖離）

C3 suggest-card-groups に既存の島・階層・holdState を渡す。人間の既決と衝突する提案を減らす 同上 C1 に従属
C4 suggest-layout に edges を渡す（§5.3）。座標を渡す唯一の例外であることを契約へ明記 同上 C1 に従属
C5 「未言語化の近接」を座標なしの構造的事実として渡す仕組み（§5.2）。新機能であり、KJ法の主体性境界の判断を伴う 設計判断。ADR が要る 要判断。予測実装を避けるなら、C1 の実使用後に判断すべき
C6 assess-card-importance の採点と domain.md の整合（§06）。エンドポイント廃止か、構造的観測への置換か 設計判断。ADR が要る R-3（CVI 群と明文要求の境界）

推奨順序: C1 を先に決める。C2〜C4 は C1 の実装形が決まれば設計判断を伴わない適用作業になる。 C5 は C1 の実使用で「AIが構造を得ると何が変わるか」を観測してから判断するのが、ADR-0039 の予測実装回避と整合する。 C6 は本書と独立に進められる。

8.1 本書が到達していない範囲

  • 効果を測っていない。 「AIに関係を渡すと出力品質が上がる」は本書では未検証の仮説である。C1 の実装後にドッグフード（ADR-0042）で確認すべきである。
  • トークン量の見積もりが無い。 論理構造を渡すと入力が増える。代わりに座標を落とせる分と差し引きでどうなるか、代表規模（カード300・島30）での実測が要る。
  • フロントエンド実装をサーバへ移す是非を判断していない。 buildAbstractMapExport / getDerivedIslandEdges は TypeScript にある。API境界で投影するならサーバ実装が要り、TS↔Python の第2の契約ドリフト源（test_ts_python_contract_drift.py の対象）になりうる。C1 の主要な設計論点である。
  • MCP・外部エージェント連携との関係を扱っていない。 external_agent_collaboration_spec の AgentTaskPackage も同じ投影を必要とするはずだが、本書では突き合わせていない。
  • 本書は分析と提案であり決定ではない。 §07 の C1・C5・C6 は ADR を要する。
