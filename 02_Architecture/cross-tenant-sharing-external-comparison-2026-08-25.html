対象: Slack Connect（別ワークスペース間の共有チャンネル）/ Microsoft Entra ID B2B collaboration（ゲストアクセス）/ Google Workspace 外部共有（Drive）/ Notion のゲスト・cross-workspace共有。02_Architecture/collaboration-concurrency-comparison-2026-08-14.html（PGM-ITER-03-01）は同一組織内の共同編集並行性モデルのみを対象とし、組織境界を越えた共有・連携は対象外だった。本調査はその欠落を補い、第5反復（テナント間連携）の認可プリミティブ設計（ADR化）の判断材料を供給する。本調査自体は新しい認可プリミティブを設計・実装しない（issue の「実施しないこと」）。

0. 結論（先に）

4製品のうち3製品（Slack・Microsoft・Google）は「組織（IdP/ドメイン）単位の信頼」と「個人単位の信頼」を別々のプリミティブとして持つ。Notionは組織単位の信頼という概念自体を持たず、常に個人単位のみ。kj-atlas の resolve_verified_claim_tenant_context() は、この4製品のいずれとも異なり、個人単位の信頼を組織（IdP）単位の信頼から独立に表現する経路を持たない（§3で詳述）。

製品個人 vs 組織の信頼分離招待・承認フロー取り消し・失効信頼度

1. 製品ごとの調査結果

1.1 Slack Connect / Slack ゲストアカウント

Slackは実は2つの別々の仕組みを持つ。この区別自体が本調査にとって重要な発見である。

  • Slack Connectは、2つの別組織（ワークスペース/Enterprise Grid org）間でチャンネルを共有する仕組み。信頼は組織間関係として設定される。Org Owner/Org Adminが「誰が招待を送信・承認・管理できるか」を設定でき、Workspace Owner/Adminは特定の相手組織に対して自動承認/自動受諾のカスタム設定を適用できる。Slack自身も相手組織が有料プランかつ実在の事業であることを検証してから接続を許可する。
  • ゲストアカウント（single-channel guest / multi-channel guest）は全く別の仕組みで、招待された個人はどの組織にも属している必要がない。ホスト側ワークスペースの有料メンバー数に対して規定比率（例: 1有料メンバーあたり最大5名のsingle-channel guest）まで、メールアドレス単位で個別に追加される。これはIdPを一切介さない、純粋な個人単位の信頼である。

取り消しについて、host workspace からのunshareでチャンネルが切断され、各ワークスペースにはそれまでの履歴が残るが、切断後のチャンネルには新しいIDが割られる。Enterprise Key Management（EKM）契約者は鍵の利用停止によって事実上のアクセス遮断も行える。

出典: Understanding Slack Connect (docs.slack.dev) / Slack Connect security (slack.com) / Manage Slack Connect approval settings (slack.com/help) / Understand guest roles in Slack (slack.com/help) / Guests vs. shared channels (slack.com)

1.2 Microsoft Entra ID B2B collaboration

Entraは、認証（このゲストが本人であるとどこまで信じるか）と認可（このゲストがリソーステナント内で何にアクセスできるか）を構造的に分離している。

  • 個人 vs 組織の分離: リソーステナントには、ゲストが招待を redeem（受諾）した時点で #EXT# を含む UPN を持つ個人専用のユーザーオブジェクトが作られる。グループメンバーシップ・アプリ割り当て・Conditional Access の適用対象は、このリソーステナント所有のオブジェクトに紐づく——ホームテナントの状態と無関係に存続する。一方、認証（ログイン時に本人確認をどこに委ねるか）は既定でホームテナント（またはメール一回限りパスコード/Microsoftアカウント等のフォールバック）に委ねられる。さらに Cross-tenant access settings では、既定（すべての外部組織に適用）とは別に、組織別カスタム設定で「特定の外部ユーザー/グループのみ許可」に絞り込める（Microsoft Entra ID P1/P2が必要）——組織全体を信頼せずに個人を許可リストするための唯一の一次ソース確認済み経路。
  • 招待・承認フロー: 既定では自組織の全ユーザーが外部ゲストを招待できる（External collaboration settingsで役割を制限可能）。相手側のドメインが許可/拒否リストに載っていない場合、Cross-tenant access settingsのInbound/Outbound設定で最終的に許否が決まる。ホームテナント側の管理者による承認は既定では不要——ゲスト個人がredemption（同意プロンプト）を通過するだけで完了する。
  • 取り消し・失効: リソーステナントは、相手テナントの状態に関係なく、個人のゲストオブジェクトを単独で無効化・削除できる。Access reviews機能で非アクティブなゲストを自動的にdisable（既定の閾値超過後）→30日後に削除、というライフサイクル管理も可能。ホームテナントが削除された、または侵害された場合: 新規のサインイン・トークン発行は（ホームテナントが本人確認を提供できなくなるため）止まるが、すでに発行済みのトークン/セッションは有効期限まで残ることがある——これは公式ドキュメントでも認識されている残存リスクである。リソーステナント側のゲストオブジェクトと権限そのものは、リソーステナントが能動的に削除するまで残り続ける。

出典: What is Microsoft Entra B2B collaboration? (learn.microsoft.com) / Cross-tenant access settings (learn.microsoft.com) / Monitor and clean up stale guest accounts (learn.microsoft.com) / Manage guest access with access reviews (learn.microsoft.com)

1.3 Google Workspace 外部共有（Drive）

  • 個人 vs 組織の分離: Trust rules の条件（condition）で、(a)「検証済みドメインを持つ外部組織」＝組織単位、(b) allowlistedドメイン一覧、(c) 個人の外部アドレスを含むグループ＝個人単位、のいずれかをターゲットに選べる。さらに「visitor sharing / guest sharing」を有効にすると、Google Workspaceドメインの検証すら不要な個人（Googleアカウントを持たない相手も含む）に、共有された特定ファイルだけへの一時的な "visitor account" を発行できる——組織を一切介さない個人単位の信頼。
  • 招待・承認フロー: 共有する側（ユーザーまたはadmin）が単独で設定でき、相手組織側の管理者の承認は基本的に不要。相手が自分の受信設定を制限している場合のみ、相手側の設定が影響する。
  • 取り消し・失効: allowlistからドメインを外す、trust ruleの対象グループから個人を外す、または個別ファイルをunshareすることで取り消す。visitorアカウントはもともとファイル限定・一時的な性質を持つ。取り消しの伝播タイミング（既存セッションがどれだけ残るか）は一次ソースで確認できなかった。

出典: Create and manage trust rules for Drive sharing (Google Workspace Admin Help) / Manage external sharing for your organization (support.google.com)

1.4 Notion cross-workspace / ゲスト共有

  • 個人 vs 組織の分離: 分離という概念自体が存在しない。Notionは常に個人（メールアドレス/アカウント）単位でのみ信頼を与え、相手がどの組織・IdPに属するかを一切検証しない。ワークスペース同士を信頼する「連携」の仕組みはない。
  • 招待・承認フロー: ワークスペースOwnerがページ単位でメールを指定して招待する。Enterpriseプランではメンバーがゲスト追加を「リクエスト」でき、Ownerがページ単位・ゲスト単位で承認する。ゲスト本人は招待リンクを開くだけで実質的に受諾したことになり、Entraのredemptionのような明示的な同意プロンプトは確認できなかった。
  • 取り消し・失効: ワークスペースのゲスト一覧、またはページ単位のアクセス一覧から個別に削除する。削除は該当ページ（またはワークスペース全体からの削除であれば全ページ）に限定される。"temporary member" は設定した期間で自動的にアクセスを失うが、通常のゲストに自動失効の仕組みはないとヘルプ記載から読み取れる（複数ソースでの相互検証はできていない）。

出典: Manage members, admins & guests in Notion (notion.com/help) / Sharing & permissions settings in Notion (notion.com/help)

赤で強調した TenantIdentityProviderRow のゲートが、本調査が指摘する分離の欠落そのものである。このゲートは「IdP P をテナント T が信頼するか」というIdP単位・二値の判断であり、「IdP P に属する特定の1個人だけをテナント T が信頼するか」という判断を表現する経路がない。このゲートを通過した後の UserIdentityRow / TenantMembershipRow は個人単位で作成・失効できるため、いったん入った後の個人単位の失効は既に可能（TenantMembershipRow.lifecycle_state を該当ユーザーだけ inactive にすればよい）だが、入る前の個人単位の許可には、テナントがIdP全体を恒常的に信頼するという前提が必須になっている。

識別したギャップ

  1. 個人単位の認可レコードが、IdP登録と独立に存在しない。 Entraの#EXT#ゲストオブジェクト、Googleのtrust rule個人ターゲット/visitorアカウント、Slackの個別ゲストアカウント、Notionのページ単位ゲスト招待——4製品はいずれも「相手のIdP registrationとは別に、この1個人だけを表すレコード」を持つ。kj-atlasのUserIdentityRow＋TenantMembershipRowは個人単位のレコードだが、その作成にはtenant_identity_providersで当該IdPがテナントに対しactiveであることが前提になっており、「このIdPからの他の全員は拒否するが、この1人だけは通す」という経路がない。
  2. 「このIdPを発行者として信じるか」と「このテナントの人口全体を受け入れるか」が分離されていない。 Entraのcross-tenant access settingsは、既定（全外部ユーザー）とは別に「特定の外部ユーザー/グループのみ」への絞り込みを組織別カスタム設定として提供する（ライセンス要件付き）。kj-atlasのTenantIdentityProviderRowにはこれに相当するsubject単位の絞り込み列がなく、行がactiveになった時点でそのIdPが発行する全subjectが（後続のUserIdentityRow/membership作成という運用手続きを経れば）対象になり得る。
  3. ゲスト種別を表す構造がない。 4製品はいずれも「本来のメンバー」と「外部からのゲスト」を、監査・一覧・ライフサイクル管理の観点で区別できる（Slackの承認ダッシュボード、Entraのaccess review、Googleのtrust rule対象グループ、Notionのゲスト一覧）。kj-atlasのTenantMembershipRowは「通常メンバー」と「他テナントから来たゲスト」を区別する列を持たず、両者は同一の行として扱われる。

4. 第5反復への示唆（判断材料。決定ではない）

本調査は次を判断材料として供給する。新しい認可プリミティブの設計・採否はADRとして別途行う（本issueの「実施しないこと」）。

  • 4製品の実装は、「IdPを発行者として信じるか」と「そのIdPの特定個人を受け入れるか」を別レイヤーの判断として持つ（Notionを除く。Notionはそもそも組織単位の判断を持たない）。第5反復の認可プリミティブが「個人単位のゲスト受け入れ」を目指すなら、この2レイヤー分離が実現可否の分岐点になる。
  • Entraの「既定は全体、組織別カスタム設定でuser/group単位に絞り込める」という段階的な絞り込み構造は、既存のtenant_identity_providersを拡張する場合の参照点になり得る（採否はADR判断）。
  • Google の visitor sharing / Slackのゲストアカウントが示すように、「相手にIdPが存在すること自体を要求しない」個人単位の信頼経路も実在の選択肢である。第5反復のスコープが「テナント間（IdPを持つ組織同士）」なのか、「IdPを持たない個人ゲストも含む」のかによって、参照すべき精度モデルが変わる。
  • 取り消し（revocation）は、kj-atlasのTenantMembershipRow.lifecycle_stateによる個人単位の失効が既に構造的に可能——ギャップは「入る前」の許可経路にある。取り消し側の再設計は今回のギャップ分析の対象外。
  • Entraの「ホームテナント消失後も既発行トークンが残る」という残存リスクは、kj-atlasが今後どのような有効期限/再検証設計を採るにせよ、参考にすべき既知の落とし穴として記録する。

5. 未解決の問い（open questions）

  • Slack: Slack Connectの相手組織が消滅・侵害された場合、共有チャンネル参加者の既存セッション/トークンにどこまで即時の影響が及ぶか——一次ソースで確認できなかった。
  • Google: trust ruleやallowlistからの除外が、既存のアクティブな共有セッション/キャッシュされた権限にどれだけの遅延で反映されるか——一次ソースで確認できなかった。
  • Notion: Enterprise版の「ゲスト追加リクエストの承認」機能の正確な挙動（承認単位、承認者の範囲）は単一ソースのみで、複数ソースでの相互検証ができていない。
  • Slack: ゲストアカウント（single/multi-channel guest）を「組織境界を越えた共有」の一形態として数えるかどうかは定義次第——相手が組織に属していない前提の機能であり、Slack Connectの組織間モデルとは異なる次元の話である点を明記しておく。
