ドッグフーディング・生成AI協働の全体計画

区分: 計画 / 更新: 2026-08-08
正本は各ADRとissue。本書は全体像を俯瞰する計画ビューであり、内容が食い違う場合は個別ADR/issueを優先する。

目的: 本プロジェクト自体をkj-atlasの題材として用い（ADR-0042 ドッグフーディング）、 三要素牽制設計法（ADR-0067）に基づく設計改善と、DeepSeek API を中心とした生成AI協働によって、 開発の自律性を段階的に高める。最終目標は人間の関与がほぼゼロでの自律的開発である。

2. フェーズと優先順位

#項目優先度内容成果物
P1 生成AI向け文書の改善 P0 AGENTS.md / CLAUDE.md / RTK.md を、生成AIが自律的に判断・行動できる水準へ改訂。三要素牽制の視点を埋め込み、判断基準を明示する 改訂版 AGENTS.md / CLAUDE.md
P2 操作別モデルレベル定義 P0 KJ法の各操作（カード化・束ね・表札作成・関係線・島形成・ナラティブ・違和感検出）ごとに必要なAI推論深度を定義。安価な操作はDeepSeek、深い推論が必要な操作はより高性能なモデルを使用 モデルレベル対応表（AGENTS.md または ADR）
P3 DeepSeek API provider追加 P1 backendのllm/provider.pyにDeepSeek API対応を追加。環境変数 KJ_ATLAS_DEEPSEEK_API_KEY / KJ_ATLAS_DEEPSEEK_MODEL で設定可能にする PR（provider追加）
P4 ドッグフーディング開始 P1 本プロジェクトのADR・issue・設計文書をカード化し、kj-atlas上で構造化する。最初の題材は現在の未解決設計課題とその相互関係 プロジェクト管理用 kj-atlas 文書
P5 タイトル生成（簡易実装） P1 文書タイトルのAI提案。リアルタイム性不要、低品質許容。人間が書き換える前提。既存SuggestionPanelパターンに準拠 PR + issue DOMAIN-TITLE-01
P6 三要素整合チェックの半自動化 P2 設計判断の記述から三要素の不整合をAIが検出する仕組み。まずは手動でのチェックリスト運用から始め、パターンが固まったら自動化 チェックリスト + 自動化スクリプト
P7 コード生成の自動化 P2 三要素整合が確認された設計判断から、APIルート・フロントエンドコンポーネント・テストの自動生成 生成パイプライン
P8 ドキュメント同期の自動化 P3 実装変更から設計文書（api.md, schemas.md, ADR）への逆反映。契約と実装の乖離を自動検出 同期チェックCIジョブ
P9 自律開発ループの完成 P3 設計→実装→テスト→文書化→フィードバック→設計 の全サイクルをAIが自律実行。人間は方向指示と受入判定のみ 自律開発運用実績

3. 操作別モデルレベル定義

KJ法の各操作には異なる推論深度が必要である。安価なモデルで足りる操作と、高度な推論を要する操作を区別し、費用対効果を最適化する。

KJ操作必要推論深度推奨モデル根拠
カード化（RawNote→Card）低DeepSeekテキストの構造化。名詞止め→述語文への変換は規則的
表札作成（島ラベル）中DeepSeek / Sonnet複数カードの共通性抽出。分類名ではなく advocacy としての表札
束ね（2〜3枚のグループ化）低〜中DeepSeekカード間の近接性判断。空間配置があれば幾何的にも判定可能
関係線（related/negate/causal/mutual）中DeepSeek / Sonnetカード間の論理的関係の識別。5種類の語彙からの選択
違和感検出（Critique）中〜高Sonnet「なんとなく違う」の言語化。too_close / too_far / not_the_same / feels_off の識別
島形成（空間構造化）中DeepSeek / Sonnet束ねられたカード群の空間配置提案
ナラティブ（B型叙述）高Sonnet / Opus空間配置からの文章化。A型との照合を含む
矛盾検出（ContradictionSignal）中〜高Sonnetカード間の論理的矛盾の検出
文書タイトル提案低〜中DeepSeek内容を代表する短い文の生成。低品質許容・人間が書き換える前提
設計判断の三要素整合チェック中DeepSeek / Sonnet3次元からの制約チェック。構造化された判断記録が与えられれば規則的
コード生成中〜高Sonnet / Opus設計判断→実装。複雑度に応じてモデルを選択
DeepSeek API の位置づけ: KJ操作の60-70%は DeepSeek でカバー可能と見積もる。 低〜中の推論深度で足りる操作（カード化・束ね・関係線・タイトル提案・三要素チェック）を DeepSeek に委ね、 高深度の操作（違和感の言語化・ナラティブ・複雑なコード生成）により高性能なモデルを割り当てることで、 API費用を抑えつつ品質を維持する。ローカルLLMは理論上選択可能だが、 現時点ではノートPCでの実用的な推論速度と品質の両立は困難と判断する。

4. ドッグフーディング: kj-atlasでkj-atlasを管理する

4.1 最初の題材

現在の未解決設計課題とその相互関係を最初のKJ法題材とする。

ラウンド題材目的
R1: 問題提起現行の設計プロセスの摩擦は何かドッグフード記録・issue・ADRから素材を収集
R2: 現状把握設計判断はどのように行われ、どこで破綻しているか三要素牽制の未適用箇所を特定
R3: 本質追求なぜ設計判断の不整合が生まれるのか方法論の欠如・文書間の不整合・レビュー不足の根本原因
R4: 構想三要素牽制設計法をどう定着させるかプロセス・ツール・文書テンプレートの具体案
R5: 具体策各フェーズの実施手順本計画の各項目を具体化
R6: 手順実行順序と依存関係優先順位付けと実施計画

4.2 ドッグフーディングで得られるもの

  • kj-atlas自体の改善: 実際の開発管理に使うことで、不足する機能・UIの摩擦が可視化される
  • 設計判断の系譜: ADR・issue・設計文書の間の依存関係が空間配置として表現され、判断の流れが追跡可能になる
  • 違和感の早期発見: 設計上の緊張（例: 本文非表示 vs 識別必要性）がカードとして明示され、解決されないまま埋もれることを防ぐ
  • AIとの協働基盤: 構造化されたプロジェクト情報はAIが自律的に判断するための入力となる

5. 生成AI向け文書の改善方針

最終目標は「人間の関与がほぼゼロでの自律的開発」である。そのためには、AIが文書だけを頼りに正しい判断を下せるだけの情報密度と構造が必要である。

5.1 改善対象と方針

文書現状の課題改善方向
AGENTS.md文書の読み方を指示しているが、判断基準が不足三要素牽制の視点・操作別モデルレベル・自律判断の許容範囲を明記
CLAUDE.md / RTK.mdツール使用の手続きが中心設計判断の自律性をどこまで許容するかの段階的定義
00_Prompt/*.mdKJ法の原理は充実。AI向けの操作手順が未整理各KJ操作のAI実行手順（入力・出力・判断基準・停止条件）を追加
02_Architecture/*.md契約文書としては充実。AIが解釈するための構造化が不足API契約・スキーマの機械可読性向上。三要素整合チェック用のメタデータ付与
01_Plans/issues/*.md個別課題の記述。相互参照が手動issue間の依存関係を機械的に解決できる構造化

6. タイトル生成（簡易実装）

方針転換: 高品質なタイトルをAIが生成する必要はない。人間が書き換えることを前提とし、リアルタイム性も不要。遅延許容のバッチ的な提案で十分である。

観点当初設計簡易化後
品質要件AIが内容を反映した適切なタイトルを生成低品質許容。人間が必ず確認・編集する前提
リアルタイム性新規作成直後・編集中・共有前の各タイミング明示的な要求時のみ。遅延許容
モデル未指定DeepSeek（低〜中の推論深度で十分）
候補数2〜5件1〜3件で十分（人間が編集するため選択肢を増やす意味が薄い）
ローカルLLM想定せず理論上は選択可能。ノートPCの性能制約から実用的ではないが、アーキテクチャとしてはprovider abstractionの範囲内
