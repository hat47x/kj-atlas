この文書の位置づけ: 個別の設計判断を下す文書ではなく、判断の単位と順序を定める枠組みである。 個々の決定は各ADR・issueに残す。本書が担うのは (1) 何を設計対象とするかの全体像、(2) どの順で三要素分析にかけるか、 (3) 反復間で整合を失わないための引き継ぎ、の3点である。

1. 「MVP脱却」を定義する

「業務全体を包括的に実現する」は、そのままでは設計対象にならない。まず現状との差分を構造として定義する。

現行MVPが成立させているのは 「1人の実務者が、1つの文書で、KJ法を最後まで回せる」 ことである。 inquiry_journey_model.html のW型反復は、この単独実務者の時間軸方向の深化を既に設計済みである。

対して業務全体とは 「組織が、複数の主体と複数の探究を、統制の下で継続的に回せる」 ことを指す。 差分は3つの軸に分解できる。要件キーワード15項目はいずれかの軸に射影される。

拡張軸MVP → 業務全体該当する要件キーワード
主体の複数化 1人 → 組織（誰が・どの権限で・いつまで） システム初期状態 / テナント追加 / IdP連携・ユーザ設定 / 権限変更・組織変更 / ユーザ無効化
成果物の複数化 1文書 → 文書群とその生涯 マスタ設定 / キャンバス作成〜一覧〜管理 / キャンバス無効化
境界の外部化 ローカル完結 → 共有・外部連携・他組織 キャンバス公開・共有 / ユーザ間コラボレーション / 共同編集 / 生成AIコラボレーション / MCP利用 / CLI利用 / テナント間連携

この3軸は独立ではない。主体が確立しなければ成果物の帰属が決まらず、帰属が決まらなければ境界の外側へ何を出せるか決まらない。 したがって設計順序は原則としてこの並び順に従う。

業務実務の役割は engagement ごとに流動的である。同一人物が回によってファシリテーターにも分析者にもなるデータ: 役割を人に固定的に持たせると、付け替えコストが利用そのものを阻害する

構造的発見: 「無効化」は層ではなく横断的性質である。
要件キーワードは「ユーザ無効化」「キャンバス無効化」を他と並列に挙げているが、これらを独立した層として最後に設計すると、 それまでの全設計に穴が空く。「Xが無効化されたとき、Xに依存する全てはどうなるか」は、各層が自分の設計時に答えるべき問いだからである。 例: 共有中のキャンバスの所有者が無効化されたとき共有は生き続けるか、共同編集の最中に参加者が権限を失ったら編集中の変更はどうなるか — これらは「無効化の設計」では答えられず、「共有の設計」「共同編集の設計」が自ら答えねばならない。
→ 本プログラムでは無効化を独立反復に置かず、各反復の三要素分析に「無効化時の振る舞い」を必須項目として組み込む。 これは three-element-constraint-checklist.html への追加提案でもある（現行18項目に含まれていない）。

5. 第1反復: 制御プレーン背骨の三要素分析

5.1 起点に断裂がある（bootstrapの循環）

第1反復の起点「システム初期状態 → テナント追加」は、現状では成立しない。 ADR-0072 がコード実読で記録した事実は次のとおり:

  • saas-multitenant で認証を成立させるには identity_providers 行が事前に必要である
  • その行を登録する POST /admin/provision/identity-providers は、同プロファイルで 404 を返す
  • 起動時の警告文は、その到達不能なエンドポイントを使えと指示している
  • 結果として、DB直接操作以外にテナントを作る経路が存在しない
次元主張他次元への制約
業務運用者は新規デプロイに最初のテナントと最初の管理者を作る。この操作自体が監査対象である機能: 認可も証跡も無い経路（DB直接操作）を正規手順にはできない
データ初期状態は「テナント0・利用者0・IdP0」。この状態から最初の信頼点をどう作るかが定義されていない業務: 信頼点を誰が作ったか記録できなければ監査に耐えない
機能認証は IdP 行に依存し、IdP 行の登録には認証が要る（循環）データ: 循環を断つには「認証に依存しない初期経路」が構造として要る

三要素で見ると、循環を断てる点は機能次元にしかない。業務・データはいずれも「証跡が要る」という制約を出すだけで、 循環そのものは解けない。ADR-0072 の D1=A+B（静的admin bearerをbootstrap専用の最小権限経路として残し、 IdP登録後の通常運用は capability claim で行う二段構成）は、この断裂点に正しく対応している。

5.2 業務次元からの追加制約 — ADR-0072に欠けている視点

三要素分析で発見した設計上の欠落。
ADR-0072 は「管理面をどう認可するか」を論じているが、「最初の管理者は誰であり、その人物の正当性はどう確認されるか」 という業務次元の問いを扱っていない。そしてこの問いの答えは profile によって異なる。
profile最初の管理者とは誰か正当性の根拠
enterprise-production
（自己ホスト）		そのインスタンスをデプロイした人物物理的に自明。サーバへの到達権＝所有権。bootstrap token で十分
saas-multitenant
（共有基盤）		テナントを申し込んだ組織の代表者自明でない。組織の実在とドメイン所有の確認が要る。bootstrap token だけでは「申込者が本当にその組織の人か」を担保できない
ADR-0072 の D2 は「SaaSで管理面へ到達できるか」という機能の問いだけを立てており、この業務次元の差を明示していない。 同じ「bootstrap」という語で二つの異なる業務要件を指しているため、D2 のいずれの案を採っても SaaS 側は解ききれない。 → ADR-0072 採択時に、この profile 差を D2 の中で分離することを提案する。

5.3 初期状態の状態機械

「システムの初期状態」を、遷移可能な状態として定義する。第1反復の設計対象はこの遷移列である。

この状態機械が明らかにするのは、S1 を S3 到達後も開けたままにするか閉じるかという未決の判断である。 開けたままなら「IdPが壊れても復旧できる」（可用性）が、静的秘密が永続的な攻撃面として残る（機密性）。 閉じるなら攻撃面は消えるが、IdP障害時に系全体が復旧不能になる。 ADR-0063 D6 が identity 検証について「fail-safe設定を作らない＝可用性より機密性」と既に決めている以上、 その一貫性からは「閉じる」が整合するが、これは可用性の予算をどこで支払うかの判断であり、保守者の決定を要する。

6. 設計に先立って判明した構造的欠落

第1反復の三要素分析を進める過程で、第2反復以降が現行データ設計の上には載らないことが判明した。 枠組みの段階で記録し、第2反復の起点とする。

欠落: documents テーブルに「主体」と「生涯」が無い。
現行の DocumentRow（models.py）の列は tenant_id / id（複合主キー）／version / updated_at / payload_json のみである。 所有者列（created_by／owner_user_id）も lifecycle_state 列も存在しない。

対照的に、同一性の側は既にライフサイクルを持っている: identity_providers・tenants・ tenant_memberships 等5テーブルが lifecycle_state を持つ。 主体には生涯があり、成果物には無いという非対称が、現行データ設計に存在する。
要件キーワードこの欠落によって現状では設計できないこと
キャンバス一覧・管理「自分の文書」で絞り込めない。テナント内が常に平坦な一覧になる
ユーザ無効化「その人が所有していた文書をどうするか」が問いとして成立しない。所有が記録されていない
権限変更・組織変更文書をチーム間で移す操作が定義できない。移動元・移動先の帰属概念が無い
キャンバス無効化archive / trash / purge を表す列が無い（non-canvas-ui-flow-design.html §9 の「文書アーカイブUI: lifecycle state列なし」と一致）

なお共有側は document_access_metadata（visibility: Public / Unlisted / Org / Restricted ＋ policy_binding_id） が既に存在する。「誰に見せるか」は設計済みだが「誰のものか」が未設計である、という状態にある。 第2反復はこの非対称の解消から始める。

8. 第2反復: 作業の器の三要素分析

第2反復の出発点（documents の所有者・生涯）は、本プログラムの初版（第0版）と次版の間に、 ADR-0073 と issue-DATA-DOC-LIFECYCLE-01 として実装済みになっていた。 したがって本節の役割は空白を設計することではなく、実装済みのものを三要素法で検証し、見落としを見つけることである。 第1反復が ADR-0072 に対して行ったのと同じ検証を、ADR-0073 に対して行う。

8.1 決定事項（ADR-0073、Accepted 2026-08-13）

決定内容棄却した代替案
D1=C作成者（created_by）は不変の履歴事実。所有はテナントに属し、管理権は capability の話とする。個人への可変な所有列は持たないA: 可変な個人所有列（無効化時に孤立する）／B: テナント所有のみ（「自分の文書」が作れない）／D: チーム中間層（ADR-0043 の複雑性予算を超える）
D2=Aactive / archived の2値のみ。trashed / purged は持たない。物理削除UIは非目標（ADR-0033 と整合）—
D3=Acreated_by は nullable。移行済み既存文書は作成者「不明」（NULL）のままとし、既定管理者への遡及的な付け替えはしない（記録されていない事実を作らない）—
D1=C が構造的に持つ副作用: 「ユーザ無効化」の問いが消える。 所有が個人に乗らないため、「無効化された利用者が持っていた文書はどうなるか」という§6が立てた問いは、 答えるべき対象そのものが存在しなくなる形で解消された。これは第1反復で見た「循環を解く」型の解決とは異なり、 問いの前提を無くすことで問いを消す型の解決である。三要素分析としては正しい—— 「誰が持っているか」を業務要件として立てず、データ設計側から先に断ったことで、業務・機能の両方が追随する必要が無くなった。

8.2 発見した欠落: 一覧・アーカイブAPIが可視性・capabilityを経ない

三要素分析で発見した設計上の欠落。
単一文書の GET/PUT /docs/{doc_id} は _authorize_request() を経由し、 document_access_metadata.visibility と capability を access_control_adapter（PDP）へ照会する。 一方、新設された GET /docs（一覧）と POST /docs/{doc_id}/archive・/unarchive は _resolve_request_tenant() のみを呼び、tenant一致だけを確認して visibility も capability も照会しない （03_Implement/backend/src/kj_atlas_api/routes/docs.py）。 02_Architecture/api.md §2.2 自身がこれを「認可：tenant-scoped」と正直に記載している——嘘は書かれていないが、 同ファイル §2.4（DATA-MODEL-OPS-02 契約、実装より前に書かれた）は同じ GET /docs に対して 「対象集合：現認可主体がread可能な文書のみ」と逆の契約を今も記載したままである。
次元主張他次元への制約
業務テナント内の一利用者が、自分には read 権限の無い Restricted 文書の存在・タイトル・作成者を一覧で知り得て良いか、また他人の文書を archive できて良いかは、業務として決めた記憶が無いデータ: visibility を「表示可否」ではなく「存在の秘匿」まで含む境界として使うなら、一覧はその境界を素通りしている
データdocument_access_metadata.visibility（Public/Unlisted/Org/Restricted）は単一文書の読み取りだけをゲートする設計で作られ、一覧という集合演算を想定していなかった機能: 一覧を visibility 対応にするには「1件ずつ認可」ではなく「集合を絞り込む」新しい照会形が要る（既存 _authorize_request は単一 doc_id 前提）
機能_transition_lifecycle（archive/unarchive）はテナント一致のみで 204 を返す。書き込み相当の操作でありながら、PUT が要求する write capability の確認を経ない業務: 「管理権は capability」（ADR-0073 D1=C）という決定の実体が、archive/unarchive という具体操作には反映されていない

この欠落は情報漏出（本文は含まれない。行メタデータのみ）としては小さいが、 「同一テナント内の任意の利用者が、権限外の文書を archive/unarchive できる」という完全性の問題としては小さくない。 修正には「集合に対する認可」という、単一文書向けに作られた _authorize_request の型を拡張する設計判断が要り、 第3反復（協働）が扱う「複数主体が同一成果物へ関与するとき何が守られるか」と本質的に同じ問いである。 したがって本反復ではこれをissue-SEC-DOC-BOUND-06 として起票し、第3反復の入力とする（§9）。

部分対応（2026-08-18）: archive/unarchive は既存の _authorize_request（PUT が 使う認可経路）へそのまま切り替えることで対応済み。これは新しい設計判断を要しない再利用であるため、 第3反復を待たずに直した。一覧側のvisibilityフィルタは、単一文書向けの認可を最大500件へそのまま適用すると 1リクエストあたり最大500回の外部PDP呼び出しになり許容できないため、意図的に未対応のまま残す。 「集合に対する認可」という新しい形は第3反復の設計そのものであり、ここで場当たり対応すべきではない。

8.3 権限変更・組織変更（文書の移管）は依然未設計

§6 が挙げた4項目のうち、一覧・生涯・ユーザ無効化は本反復で解消した（一覧・生涯は実装、無効化はD1=C により問いが消滅）。 「文書をチーム間で移す操作」は未解決のまま残る。 ADR-0073 は D1=C の直接の裏返しとしてこれを明示的に非目標としている （「所有者を移す」という直感的操作は無く、管理権は capability 側の話になる）。 master-data-settings-ui-ux-concept.md も文書一覧UIから所有者移管を明示的に除外している。 これは設計忘れではなく意図的な保留であり、チーム中間層を要求する具体的な利用実態が生じるまで、 第4反復（成果物の複数化）以降で再検討する。

10.1 共同編集の並行性モデル（ADR-0076 の要約引用）

対象知見（3票反証検証済み）
FigmaOTもCRDTも採用せず、サーバ権威のproperty-level Last-Writer-Winsを採用（OTは「hard to understand / overkill」と明示的に却下）。各変更に連番を付与しサーバが順序・解決を強制。子要素の順序は分数インデックス（base-95）。利用者に見えるマージUIはない（不可視解決）。
Confluence保存時LWW。競合時はOverwrite/Merge/Discardの手動選択UIがあり、文書化された障害（CONFSERVER-32286：並行保存がバージョン履歴を黙って破損）が実在する。
Miro並行性の基盤機構は一次ソース未確認（open question）。ボードは単一owner・譲渡可・5段階ロール（Owner/Co-owner/Editor/Commenter/Viewer）。
Notion / Slack / Jira並行性モデルは一次ソースが3票反証検証を通過せず未確認のまま（推測しないと明記されている）。

ADR-0076 D1 はこれを根拠に「サーバ権威LWW＋既存CAS拡張」（Figma式）を推奨している。 kj-atlasは既にサーバ権威・単一正本（DocumentV1を保存しETag/If-Matchで 楽観的並行制御済み）であり、Figmaと同型の構成という判断は妥当である。

三要素分析で発見した欠落: ADR-0076 の三要素表は、LWWと第2反復までの不変条件の 衝突を検討していない。
Figma型のproperty-level LWWは「後着の書き込みが先着を無条件に上書きする」ことと同義である—— Confluenceの障害例（CONFSERVER-32286）が示すように、これは実装を誤ると履歴そのものを黙って破損する。 ADR-0076 の三要素表（データ設計行）は「クライアント側CRDT状態を永続正本にしない」ことは 述べているが、「サーバ権威で確定した後着優先の上書きが、先着側の入力（カード本文・保留・違和感）を 破棄することになるか」を検討していない。 しかし DOM-CORE-01（保留）・ DOM-CORE-03（可逆性）・DOM-CRIT-06/07（違和感はデータとして保存し破棄しない）は、 入力を失うことそのものを禁じている。

幸い、ADR-0076 D2 は近い将来の実装範囲を「保存時同期（既存のETag/CAS）」に限定しており、 これは文書全体を単位とする楽観的ロック（先着が保存→後着は409で拒否・再読込が必要）であって、 Figmaが行うプロパティ単位の無条件上書きではない。つまりD2の近未来スコープでは この懸念は実害化しない——後着は拒否されるだけで、何かを黙って失うことはない。 懸念が生じるのは、将来「保存時同期」から「プロパティ単位のリアルタイム同期」へ進める判断をする時点である。 その時点で、この三要素の衝突を必須の検討事項として扱うことを、本版はD2の判断基準へ追加提案する （§11.2）。

10.2 組織モデル・チーム階層（第2反復の再検証・第5反復向け）

Notionは Workspace Owner（最上位）→ Teamspace（チーム単位のアクセス境界。Open/Closed/Private の3種） → メンバーという3層構造を持つ。ADR-0073 D1=C はまさにこの「チーム中間層」を代替案Dとして 検討し、ADR-0043 の複雑性予算を理由に棄却していた。Notionの実例は代替案Dが実在し機能することを示すが、 同時にその複雑さ（5種のユーザ種別、Teamspace作成権限の別設定、3種の可視性）も示す。 棄却の判断は変えない。棄却の理由（複雑性予算超過）が具体例で裏付けられたと捉える。

10.3 権限つき一覧の実現方法（issue-SEC-DOC-BOUND-06 の再検討材料）

第2反復（§8.2）で「集合に対する認可には新しい照会形が要る」と判断したが、業界の標準解は既に存在する。
Google Cloud Search・Slack企業内検索はいずれも、ACL（可視性メタデータ）をコンテンツと一緒に索引し、 クエリ時にローカルでフィルタする方式を採る。行ごとに外部PDPへ問い合わせるのではなく、 「誰が何を見られるか」の判定に必要な情報を先に索引側へ持たせておく。

kj-atlasの document_access_metadata.visibility は文書ごとにローカルDBへ既に保存されている。 したがって Public/Unlisted は無条件表示、Org はテナント一致（既に判定済み）で表示、 Restricted のみが個別粒度の判定を要する——この最後の1件だけが本当に難しい。 issue-SEC-DOC-BOUND-06 が一覧対応を全面的に見送った判断は再検討の余地がある。 「外部PDPへ最大500回問い合わせる」という悪いフレーミングを避け、「ローカルのvisibility列だけで Public/Unlisted/Orgを即時フィルタし、Restrictedのみ保留（一覧から除外）する」 という段階的対応が、外部PDP契約の変更なしに実現できる。第3反復（§11.3）で扱う。

10.4 テナントbootstrapの代替（第1反復の再検証）

Slackのワークスペース作成は、静的な共有秘密ではなくメール所有権の検証を 信頼の起点にする（メールへ確認コードを送り、応答した者がPrimary Ownerになる）。 第1反復 §5.3 は「bootstrap用の静的経路（S1）をS3到達後も開けたままにするか閉じるか」を未決としていた。 Slack型の代替は、この二択（開ける/閉じる）そのものを回避する——恒久的な静的秘密を持たず、 検証可能な実世界の事実（メール所有）を都度の起点にする。 これは第1反復の決定を変える理由にはならないが （ADR-0072 は既にAccepted）、将来この経路を見直す際の代替案として記録する。

11. 第3反復: 協働の三要素分析

第3反復の対象は「公開・共有・ユーザ間コラボレーション・共同編集」、問いは 「複数主体が同一成果物へ関与するとき何が守られるか」である（§4）。 第1反復・第2反復と異なり、本反復には出発点となる実装済みの決定が既にある—— ADR-0076（並行性モデル、Proposed）と document_access_metadata （可視性、実装済み）。したがって本反復の役割は3つに分かれる: (1) ADR-0076 の採否判断、 (2) 第2反復から持ち越した「集合に対する認可」の設計、(3) 「ユーザ間コラボレーション」の範囲を 実際に確定させること（現状は未設計であり、設計すべきかどうかも含めて判断する）。

11.1 並行性モデル: ADR-0076 D1 の採択を提案し、D2 に判断基準を追加する

§10.1 の検証済み知見と、kj-atlasが既にサーバ権威・単一正本であるという事実の一致から、 D1=A（サーバ権威LWW＋既存CAS拡張）の採択を提案する。 新しい並行制御機構を導入せず、 既存の ETag/If-Match（document）・revision（inquiry bundle）を そのまま共同編集へ拡張するだけであり、第2反復までに確立した不変条件と衝突しない （§10.1で確認したとおり、D2の近未来スコープは文書単位の楽観的ロックであり、プロパティ単位の 無条件上書きではない）。

次元主張他次元への制約
業務複数利用者が同じ文書を編集するjourneyは「先に保存した側が勝つ。後の側は409を受けて再読込し、自分の変更を再適用する」。これは既存のPUT契約そのものであり、利用者への新しい説明は「複数人編集時は保存が早い者が反映される」の一文で足りる機能: 新しいUI（マージ画面・競合解決ダイアログ）を作らない。Confluence式の手動merge（選択肢C）は採らない
データ正本は常にサーバ側のrevision/version。クライアントの一時状態を正本にしない業務: 「保存に失敗した側の入力」は消えない——ローカルに残ったまま再適用の対象になる。破棄されるのはサーバへの反映だけであり、利用者の入力そのものではない
機能既存の409応答をそのまま使う。新規エンドポイント・新規並行制御コードは追加しないデータ: 409時にクライアントが最新版を取得し、利用者の未保存編集をどう再適用するかはフロントエンドのUI設計として残る（本ADRの範囲外）
D2への判断基準の追加提案: D2は「保存時同期で十分。リアルタイムプレゼンスは同時利用の 実測後に判断する」としている。この判断基準に、§10.1で発見した確認事項を明記することを提案する—— 「プロパティ単位の同期・マージへ進める場合は、その方式が保留・違和感・少数意見を 無条件上書きで失わないことを、実装前に確認する」。 今は空欄の判断基準だが、 将来この判断をする人が同じ調査をやり直さずに済む。

11.2 集合に対する認可: issue-SEC-DOC-BOUND-06 の一覧フィルタを設計する

§10.3 の知見（ACLをコンテンツと一緒に索引し、クエリ時にローカルでフィルタする）を適用する。 document_access_metadata.visibility は文書ごとに既にローカルDBへ保存されているため、 外部PDPへの追加照会なしに次の段階的フィルタが成立する。

visibility一覧への表示根拠
Public表示する定義上、誰が見ても良い
Unlisted表示する「リンクを知っていれば見られる」であり、一覧非表示を意味しない。既に同テナント内である前提と矛盾しない
Org表示するテナント一致は _resolve_request_tenant が既に確認済み。「Org」の意味は「テナント内なら見える」であり、追加判定は不要
Restricted作成者本人以外には表示しない（一覧から除外）誰が対象かは policy_binding_id 経由で外部PDPしか知らない。ローカル情報だけでは対象者を判定できないため、判定できない場合は表示しない（fail-closed。既存のADR-0063 D6の方針と一貫する）

この対応は外部PDPの契約変更を要さない——visibilityという既に持っている 列だけで判定できる。Restrictedを作成者本人にだけ見せるのは、「対象者が分からないなら 安全側に倒す」という保守的な近似であり、正確な対象者判定（PDPが本来担うべき仕事）の代替ではない。 正確な対象者判定を一覧へ持ち込む場合は、そのときに初めて集合向けPDP契約の拡張を検討すればよく、 今それを先取りする必要はない。

11.3 ユーザ間コラボレーション: 個別招待は本反復の範囲としない

現状、特定の個人へ文書を共有する手段はvisibilityの4段階のみであり、名前を指定した 招待・共同編集者リストは存在しない（document_access_metadataにそのための列がない。 SharePanel.tsxも可視性の選択のみを提供する）。

三要素分析の結論: 個別招待の欠如は、見落としではなく既存アーキテクチャの意図的な委譲先である。
visibility=Restricted は policy_binding_id 経由で外部PDPへ判定を委譲する設計 （ADR-0059）である。「特定の個人へ共有する」という要求は、kj-atlas自身が 招待・メンバーリストを実装するのではなく、外部PDPが解釈するpolicy_binding_idの 意味として表現される——たとえば「このpolicyは山田さんとテナントAの3名にのみreadを許可する」 という判断は、外部PDP側の設定であり、kj-atlasのスキーマに新しい列を追加する話ではない。

したがって業務設計は成立する（Restrictedというレバーは既にある）。データ設計も成立する （policy_binding_idで表現可能）。機能設計はPDPが実際に配線されていない プロファイル（local-dev・PDP未設定のenterprise-production）では この経路が機能しないという限界がある——ただしこれは新しい欠落ではなく、 ADR-0059が既に「PDP未設定時はRestrictedをfail-closedで拒否する」と 決めている範囲内の話である。

kj-atlas自身が独自の招待UI・メンバー管理を実装することは、本反復では行わない。 具体的な利用実態（外部PDPを持たない単独利用者間で、特定の個人とだけ共有したいという要求）が 生じた場合に、別issueとして再検討する。

12. 第3反復から第4・第5反復への引き継ぎ

  1. 採択が必要: ADR-0076（D1=A採択を提案。D2へ§11.1の判断基準追加を提案）。
  2. 実施すること: issue-SEC-DOC-BOUND-06 の残作業（一覧のvisibilityフィルタ、§11.2の表のとおり）。 これで同issueの受入条件が全て満たせる見込み。
  3. 意図的に対応しないこと: ユーザ間コラボレーションの個別招待UI（§11.3）。 外部PDPへの委譲が既存の設計であり、具体的な需要が出るまで再検討しない。
  4. 第4反復（成果物の複数化）への入力: 第4反復は issue-PGM-ITER-04-01 としてスコープ済みであり、第2反復（documents所有・lifecycle）への依存が明記されている。 第3反復（本反復）への直接の依存は無い。
  5. 第5反復（テナント間連携）への入力: issue-PGM-ITER-05-01 は第3反復と 同じ外部比較調査（§10）を前提にしており、その調査は完了済み。また §2 で「他組織の協働者」を capabilityで表現できない構造的に新規な役割として第5反復へ委ねている。§11.3の「外部PDPへの委譲」 という設計方針は、複数組織が絡む第5反復ではそのまま使えない可能性がある——他組織のPDPをどちらの テナントが信頼するかという、第1反復のbootstrap問題と同型の循環が生じ得るため、第5反復の着手時に 再確認する。
