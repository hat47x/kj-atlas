kj-atlas ・ Architecture Spec ・ ADR-0057

反復的探究のデータモデル

W型累積KJ法を支援するデータ境界の採択済み設計目標。日常編集するDocumentV1と長期探究の履歴を分離し、操作単位ではなく人が意味を確認した節目の成果を不変スナップショットのDAGとして残す。

採択済み設計目標（Phase 2実装中） L0: Planned（実装・移行・CRUD揃うまで）

本書が正本（新規設計文書はHTML単独。AGENTS.md §3）。Decision: ADR-0057-w-type-cumulative-inquiry-model.md ・ Requirements: w_type_iterative_inquiry_requirements.md ・ Implementation: issue-DOMAIN-W-ITERATION-01

01

この文書の位置づけと設計要点

この文書はW型累積KJ法を支援するデータ境界の採択済み設計目標を定める。現時点のDocumentV1、API、保存形式へこの型が実装済みであることを示す文書ではない。実装・移行・運用CRUDが揃うまでは、すべてL0: Plannedとして扱う。

  1. 日常編集する DocumentV1 と、長期探究の履歴を分離する。
  2. 操作を一件ずつ記録するのではなく、人が意味を確認した節目の成果を不変スナップショットとして残す。
  3. 前段階への戻り、同段階の再試行、複数案の展開を、過去成果の上書きではなく有向非巡回グラフ（DAG）の分岐として表す。
  4. ローカル保存とファイル交換を中核に置き、サーバーだけに存在する参照を必須にしない。
02

比較した方式

評価は、KJ法への忠実性、停止・再開、可搬性、後方互換、安全共有、性能、将来の共同作業、実装・運用負荷の8観点で行った。

方式強み主な問題判断
DocumentV1 へ履歴を埋め込む一ファイルで扱いやすい文書が肥大化し、validator・共有・削除・SafeModeへ波及不採用
ラウンドごとに文書を複製する現行保存を流用できる系譜・分岐・再開がファイル名と人手管理に依存不採用
操作単位のイベントソーシング詳細な監査と再生が可能イベント進化・再生・削除・投影・競合解決の負担が過大不採用
独立manifestから可変文書を参照現行文書と履歴を分離できる参照先の編集や削除で過去成果が変化・欠落単独では不採用
独立探究 + 不変スナップショットDAG + 自己完結bundle意味のある履歴、分岐、可搬性、現行契約の分離を両立新しい検証、容量管理、共有範囲UIが必要採用

イベントソーシングは将来も全面採用を既定としない。共同編集や監査で操作意図の履歴が必要になった場合に限り、対象を限定して別ADRで再評価する。

03

論理構造

InquiryJourneyV1

探究全体のmanifest。journeyId・title・originSnapshotIds（出発成果）・roundRecords・headRoundIds（現在先端の分岐集合）・defaultHeadRoundId?を持つ。単一のactiveRoundIdを全体の真実にしない ─ 複数分岐を同時に保持でき、表示中ラウンドはview stateとして別に扱う。

RoundRecordV1

stage（r1_problem_setting〜r6_procedure_planning）・iteration（段階番号とは独立した実施回数）・parentRoundIds（循環禁止。通常1件）・status（working | paused | handed_off | superseded。completedは品質保証と誤解されるため使わない）・theme・inputSnapshotIds・outputSnapshotId?・handoff?。段階番号が小さくなる親子関係も許容し、差し戻しではなく分岐として表示する。

RoundSnapshotV1

人が「ここまでを残す」と確認した意味のある中間成果。snapshotId（内容から独立したランダムID）・document（その時点を再現できるDocumentV1 payload）・canonicalDigest（sha256:<64桁小文字16進数>）。作成後に変更しない。訂正は新しいラウンド成果として残す。選択状態・開閉パネル・hoverは含めず、カード・配置・島・関係・文章化・保留・違和感・根拠は含める。

RoundHandoffV1

carryoverRefs・heldRefs・unresolvedQuestions・fieldworkRequests・understandingDelta。担当者・期限・承認状態を必須にしない。正式な組織承認は別契約として扱う。

CardLineageEdgeV1

スナップショットを越えた由来を接続。種類: carried（同一性維持）・edited（表現/解釈変更）・derived（観察・根拠から仮説/方針を導出）・split・merged・new・retired。derivedを独立させることで、後段階の解釈を前段階の観察本文の編集として扱わない。

04

保存と交換

4.1 アプリ内保存

論理的には (1) DocumentV1=現在の可変作業文書、(2) InquiryJourneyV1=ラウンドDAG・引継ぎ・系譜、(3) RoundSnapshotV1=内容不変の成果blob、を別集約として扱う。初期実装ではJSON集約/blobでよく、正規化テーブル化はroundtripと容量計測後に決める。

境界値
警告境界5 MiB超は読込禁止せず、時間がかかる旨を伝える
絶対上限20 MiB超は拒否（payload_too_large）。UI/parser/exportで同一境界を適用（import/export対称）
実測（300カード・30島）6ラウンド 1,460,390 bytes ／ 12ラウンド 2,785,220 bytes ／ 18ラウンド 4,110,050 bytes

4.2 export bundle

共有・移行用成果物は、選択したラウンド/分岐に必要な要素（対象範囲のmanifest・全参照snapshot・Handoff/FieldworkRequest/CardLineageEdge・schema version・digest・共有範囲とSafeMode結果）を一つの自己完結bundleへ含める。外部共有用bundleのみ任意のInquiryExportInfoV1を持つ（ローカル保存bundleは持たない）:

scope記録内容
full探究全体。{ scope: "full", safeModeApplied: true }
round選択ラウンドまで。{ scope: "round", selectedRoundId, safeModeApplied: true }。selectedRoundIdは派生bundleの唯一のhead兼default headと一致必須

safeModeAppliedはtrue以外を許可せず、strict importは同じSafeMode変換を再適用してbundleが固定点であることを確認する。raw本文を残したままmetadataだけを付加したbundleは拒否する。SafeModeマスクは元スナップショットを変更せず、マスク後の内容に新しいdigestを付ける。

4.3 削除と保持

不変性は通常編集に対する規則であり、個人情報・機密情報の削除、保持期限、利用者の削除要求より優先しない。探究全体の削除を最小の完全削除単位とする。子孫を持つラウンド/成果だけを削除する場合は、依存する分岐をまとめて削除するか、機微情報を除いた置換探究を作り参照を閉じた状態で検証後に元探究を削除する（参照切れのまま保存しない）。削除後の監査情報は削除日時・対象種別・実行結果など本文を含まない最小メタデータに限定する。

05

SafeMode / Import / 部分共有 契約

4.4 SafeMode派生bundle契約

SafeModeは既定ONの安全機構であり、探究bundleを他者と共有する前に適用される。実装（inquiry_bundle_safe_mode.ts deriveInquirySafeModeBundle()）と一致しなければならない。

原則: (1) 元bundleを変更しない・派生bundleは独自digestを持つ、(2) マスク後に各snapshotのcanonicalDigestを再計算、(3) 秘匿性をdigest/IDに依存しない。

ポリシー意味
preserveそのまま複製。構造的/参照/識別/時刻フィールドに適用
redactSafeModePolicy.redactText()でマスク。タイトル・theme・カード本文・narrative・critique・問い・理解変化記述に適用
omitフィールドごと削除。再提案diff・矛盾判定は内容を安全に列挙できないため全体をomit
rebuild子オブジェクトを再帰的にSafeMode処理。journey・snapshots・cardLineage・handoff等の複合型に適用

新規フィールド追加時はコンパイル時に網羅性が強制される（satisfies Record<keyof T, FieldPolicy>パターン。human_reviewed状態・review attribution・provenanceフラグはSafeMode派生で変更しない。未知CardLineageEdgeV1種別は表示用既定値relatedへ正規化する。

4.5 Import strict validation契約

import（inquiry_bundle_io.ts parseInquiryBundleJson()）はすべての入力bundleを3段階で検証する。検証失敗は受理しない（fail-closed）。

往復対称性: exportされたbundleは必ずimportでき、importされたbundleを変更なく再exportすると同一のJSON表現とdigestが得られる。

4.6 部分共有契約

部分範囲の共有（inquiry_bundle_projection.ts deriveInquiryRoundBundle()）は、選択ラウンドとその祖先に限定した自己完結bundleを作成する。範囲外snapshotへの依存が存在する場合、投影はdependency_outside_scopeで失敗し未解決snapshot IDの一覧を返す（依存を黙って削除しない・別分岐を暗黙追加しない）。元bundleとsnapshotは変更しない（structuredCloneによる深い複製）。

06

UI原則

  • 通常モードへ6段階、進捗率、履歴パネルを追加しない。
  • 高度機能を有効にしたときだけ「現状把握・2回目」のような現在位置を一行で示す。
  • 全体は直線progress barではなく、要求時に開く分岐図で示す。
  • 節目の確認は、持ち越し、保留、未解決点、現場への問いを一件ずつ扱う。
  • 過去成果を開いた状態では読取専用を明示し、編集開始は「この成果から分岐」とする。
  • 分岐開始時は、選択した出力snapshotを可変作業文書へ明示的に復元し、その同じ内容を新しい子snapshotとして記録する。
  • 再開ブリーフは導出表示とし、各項目から元カード・成果へ移動できる。
  • ラウンド比較は不変な出力snapshot同士の読取専用投影とする。件数を品質点数や改善率へ変換しない。
  • マウス、キーボード、390px幅で同じ意味の操作を完了できることを実装ゲートにする。
07

不変条件

  1. 過去の RoundSnapshotV1 を後続編集で変更しない。
  2. R1からR6の順序や回数を品質点数にしない。
  3. ラウンド段階をカード固有属性、権限、事実確認、レビュー済みの根拠にしない。
  4. AI提案は人が採用するまでmanifest、成果、系譜、レビュー状態を変更しない。
  5. KJ_ATLAS_LLM_PROVIDER=none で作成、引継ぎ、停止・再開、分岐、比較が成立する。
  6. bundleの参照は内部で閉じ、外部サーバーがなくても検証・閲覧できる。
  7. 個人情報・未レビュー本文の削除またはマスクを、不変性を理由に妨げない。
  8. SafeMode派生は元bundleを変更しない。マスク後snapshotのcanonicalDigestは再計算される。
  9. export/importは対称である。変更なく再exportすると同一のJSON表現とdigestが得られる。
  10. 削除は内容を含む成果物を生成しない。削除後の監査情報は削除日時・対象種別・結果コードに限定される。
08

段階的導入

Phase内容永続化
0型、fixture、不変条件、分岐検証なし。メモリ内のみ
1高度機能内の低忠実度UI、初期表示差分0の確認なし
2独立集約と自己完結bundleのroundtrip、strict import、容量計測ローカル成果物
3backend保存/API、保持・削除、障害復旧実装判断後
4proposal-only AI支援中核操作とは分離
5実需が確認された場合だけ共同編集方式を再検討別ADR

Phase 0・1で操作模型が理解されない場合は永続契約へ進まない。Phase 2で性能予算を満たさない場合は、スナップショット圧縮または差分格納を内部最適化として比較する（外部契約は完全な成果を再構成できることを維持）。

実装状況（2026-08-02）: Phase 2のうち、inquiry_bundle_io.ts にローカルexport/import境界を実装。試作パネルから正式bundle作成・ラウンドsnapshot記録・カード系譜記録・JSON保存/再読込・2ラウンド比較・非破壊分岐・分岐一括取消・カード系譜表示・再開ブリーフまで操作可能。300カード・30島・6ラウンドで1成果73,955 bytes、bundle 1,460,390 bytesは許容範囲。画面読込の最大長時間タスクはPERF-INQUIRY-01でstrict validationとdigest照合をworkerへ移し、単独実行93〜95ms（並列CI 125ms、退行上限150ms、設計目標100ms）。保持・削除の標準UIとbackend永続化は未実装のため、Phase 2全体とL1昇格は未完了。

Backend lifecycle checkpoint (2026-08-06): tenant-scoped opaque bundle save/read and inquiry-level delete with content-free deletion audit are implemented. Retention policy, expiry enforcement, and purge/history-retention operations remain unspecified or unimplemented; Phase 2 and L1 promotion remain incomplete.
