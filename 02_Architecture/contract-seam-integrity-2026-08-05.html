kj-atlas ・ Architecture Analysis ・ 契約継ぎ目の健全性

データ・業務・機能をまたぐ契約は、どこで守られ、どこで破れたか

DocumentV1 契約が実装横断でどう保たれているかを実コードに当てて検査した。検出した実欠陥は2件。いずれも「手で保守されたリスト同士を突き合わせるガード」の盲点で発生しており、根本原因は共通している。

F-1 サーバ保存でフィールド消失（実害・進行中） F-2 RLSガードが自己参照 対策=導出へ寄せる

本書が正本（新規設計文書はHTML単独。AGENTS.md §3）。検証は推論ではなく実行による再現・フィールド集合の実測に基づく。

01

三位一体の継ぎ目 ─ 契約は7箇所に分散している

データ（DocumentV1）・業務（KJ法の意味論＝保留・違和感・レビュー状態・系譜）・機能（UI・エクスポート面）は、それぞれ別の実装物として存在する。三者が一致し続けるかは、その継ぎ目がどう保守されているかで決まる。Island 契約は次の7箇所に現れ、型から導出されているのは1箇所だけである。

決定的な事実として、representativeCue を types.ts へ追加した際にコンパイルを停止させたのは緑の1箇所だけだった。 

error TS1360: Type '{...}' does not satisfy the expected type
'Record<keyof Island, FieldPolicy>'.
  Property 'representativeCue' is missing

残る6箇所は「気づいて直す」ことが前提であり、Pydantic 側で実際に気づかれなかった。導出された継ぎ目はドリフトせず、手保守の継ぎ目はドリフトした。これは規律の問題ではなく構造の問題である。

02

F-1 ─ Island.representativeCue がサーバ保存で消える

Pydantic Island に representativeCue が無い。put_document は検証後に document.model_dump_json() を保存するため、未知フィールドは捨てられた結果が永続化される。実行して再現した。

段階representativeCue
リクエスト payloadあり
Pydantic 検証後の model_dump_json()なし（実測）

影響: DOMAIN-VISUAL-CUE-01 T7 の小PR 1〜6件目（契約先行の型・基本図形・手描きIndexedDB・review pack同梱・利用者画像・性能回帰）はすべてこのフィールドの上に構築されている。ローカル保存では成立するが、サーバ保存を伴う経路（Compose / enterprise-production）では毎回失われる。機能テストがローカル経路のみを検証していたため緑だった。

これは3度目の再発である。models.py の Edge.type にはコメントが残っている ─ 「Rejecting here was the second data-loss vector alongside the frontend validator」。同じ障害型がフロントエンド検証器と Pydantic の両方で既に発生し、修正されていた。

03

同じ既定が、安全制御にもデータ損失にもなる

最も重要な非対称性はここにある。Pydantic の extra="ignore" は、同一の既定値でありながら正反対の役割を担っている。

型未知フィールドを捨てる意味根拠
CardMeta 意図的な安全制御 models.py のコメントが明記 ─ 「§15.3's fail-closed rule … subject/provenance keys are dropped rather than persisted」。起票者・所有者などの主体メタが import 経由で永続化される抜け道を塞ぐ。
Island 事故的なデータ損失 契約済みの正当なフィールドを破棄している。意図した挙動ではない。

コードを読んでも両者を区別できない。意図が型に符号化されていないため、「捨ててよい」と「捨ててはいけない」が同じ書き方（何も書かないこと）で表現されている。

04

F-2 ─ RLSカバレッジ契約が自己参照になっている

テナント分離は多層防御で設計されている。しかし最下層のRLSについて、完全性を保証するはずのガードが、手保守リスト同士の一致しか検査していない。

tenant_id を持つ表RLS
documentsあり
merge_decision_logsあり
document_access_metadataあり
document_access_admin_audit_eventsあり
tenant_membershipsなし
tenant_identity_providersなし

後者2表はcontrol-plane側であり、Workspace Data Planeの文書行とは性質が異なる。したがって「直ちに脆弱」とは断定しない。問題は、現在のガードがその判断が意識的に行われたのかを区別できないことにある。新しいtenant従属表を追加した実装者がRLS migrationと定数の両方を忘れた場合、テストは緑のまま通過する。

05

対策の方向 ─ 継ぎ目を「導出」へ寄せる

個別修正では3度目の再発を4度目にしないだけである。SafeMode方針の継ぎ目が守られた理由（型から導出）を、他の継ぎ目へ移植する。実装判断はMaintainer。

#対策内容
1 F-1の直接修正 Pydantic Island へ representativeCue を追加。schemas.md §19 が正本であり、加算のみで version: 1 を維持できる。
2 TS↔Python ドリフト検査の機械化 両側のフィールド集合を比較する契約テスト。今回の監査スクリプトが雛形になる（11型中10型の同期を確認し、1型のドリフトを検出できた）。フル型生成より安価で、既存の二重定義を壊さない。
3 「捨ててよい」の明示化 fail-closed を意図する型には extra="forbid" か明示表明を、passthrough を意図する型には別の表明を与え、Pydantic既定への暗黙依存をやめる。現状は同じ既定が正反対の意味を持つ。
4 F-2のガード導出化 RLS_PROTECTED_MODELS を手書きせず、SQLAlchemy metadata から tenant_id 列を持つ表を列挙して導出。control-plane表を除外する場合は除外理由付きの明示allowlistとして残し、「忘れた」と「意識的に外した」を区別可能にする。
∑

総括

データ・業務・機能の三位一体は、三者を揃えて書くことでは達成されない。今回の実測が示すのは、揃えて書いた6箇所のうち1箇所が黙ってずれ、機能が本番経路で成立しなくなったという事実である。一方、型から導出された1箇所はビルドを止めて実装者に宣言を強制し、ずれなかった。

三位一体を保つのは規律ではなく導出関係である。継ぎ目ごとに「何から何が導かれるか」を決め、導けない継ぎ目には差分を検出する機械を置く。この原則は既に architecture-coherence-synthesis がCVI-1の砦について指摘したものと同型であり、契約継ぎ目にも同じ弱点が存在することが今回確認された。
