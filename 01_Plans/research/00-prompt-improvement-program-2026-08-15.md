# 00_Prompt 改善施策 — 憲法層の価値を高め、計画層へ接続する

- 区分: 施策整理 / 版: 第1版 / 作成: 2026-08-15
- 対象: `00_Prompt/` 全13文書
- 関係: `01_Plans/product-trajectory-research-2026-08-15.md`（本施策の契機）、`AGENTS.md`（読み順の正本）

## 1. 診断

### 1.1 参照は多いが、粒度が粗い【実測】

`01_Plans/` と `02_Architecture/` から `00_Prompt/` への参照は活発である。

| 参照先 | 件数 |
|---|---|
| `domain.md` | 64 |
| `ai_cognitive_externalization_requirements.md` | 34 |
| `kj_technique.md` | 18 |
| `representative_visual_cue_requirements.md` | 14 |
| `qualitative_card_quality_requirements.md` | 12 |

**しかし `domain.md` への64件のうち、約50件はファイル名だけの裸参照である。** 節も識別子も指していない。

さらに悪いことに、行番号による参照が3件ある（`domain.md:88`）。**行番号は編集で腐る参照であり、無いより悪い。**

### 1.2 安定した識別子を持つ文書が少ない【実測】

| 文書 | 識別子 | Status |
|---|---|---|
| `w_type_iterative_inquiry_requirements.md` | **WIR-01〜09** | Normative |
| `ai_cognitive_externalization_requirements.md` | 7個（MMR-*等、部分的） | **なし** |
| `representative_visual_cue_requirements.md` | 5個（部分的） | **なし** |
| `qualitative_card_quality_requirements.md` | 4個（部分的） | Normative |
| **`domain.md`** | **0** | **なし** |
| **`kj_technique.md`** | **0** | Normative |
| **`ai_kj_execution_procedures.md`** | **0** | Normative |

**最も参照される `domain.md` に識別子が1つもない。** 不変条件——保留・違和感・可逆性・AIの禁止事項——はすべて散文の中にあり、指し示す手段がない。

`product-trajectory-research-2026-08-15.md` は不変条件を参照する必要が生じたとき、**I1〜I5 という識別子をその場で発明せざるを得なかった。** これは接続の失敗が実際に表面化した事例である。

### 1.3 Status 語彙が統制されていない【実測】

7文書中3文書に `Status` がない。ある3文書のうち2つは括弧書きで別情報を混ぜている（`Normative（ADR-0057 Accepted、実装は…で追跡）`）。**語彙の定義も検証もない。**

`01_Plans/issues/` は `issue_memo_status.py` で `Draft/Open/In Progress/Done` を統制し、`validate_active_issue_memos.py` が検証している【内部根拠】。**憲法層だけが無統制である。**

### 1.4 索引が存在しない【実測】

`00_Prompt/README.md` も `index.md` も無い。読み順は `AGENTS.md` の表に外部化されており、**00_Prompt 自身は自分が何を含むかを述べない。**

### 1.5 二種類の文書が混在している

| 種別 | 文書 | 読者 | 変更頻度 |
|---|---|---|---|
| **製品憲法** | domain, kj_technique, qualitative_card_quality, representative_visual_cue, w_type, ai_cognitive_externalization, cognitive_frame_and_evolution_criteria | 人間＋AI（製品を作る者） | 低い（変えてはならない） |
| **エージェント運用** | system_prompt, agent_collaboration, agent_handover, handoff, codex_skill_operations | AIエージェント | 高い（道具の変化に追随） |

**両者は権威も変更頻度も異なるのに、同じ階層に平置きされている。** 「00_Prompt は憲法層」という説明が、実際には半分しか当たっていない。

### 1.6 憲法層に実装詳細が入り込んでいる

`ai_cognitive_externalization_requirements.md` は629行あり、§7 以降は ContextBundle の構成要素や IR の仕様といった **`02_Architecture` の粒度**を含む。憲法が実装詳細を抱えると、実装の変更が憲法の変更を要求するようになり、**憲法の安定性が失われる。**

### 1.7 検証が及んでいない【実測】

`docs_contract_checks.py` は `00_Prompt` をパス集合に含むが、適用される規則は汎用のもの（リンク解決、パス前置など）である。**憲法層固有の検証——Status の語彙、識別子の一意性、参照の解決——は存在しない。**

対照的に ADR には `DC-ADR-001`（番号重複）が、issue memo には Status 検証がある。

## 2. 問題の構造

診断を1つの文に畳むと次になる。

> **憲法層は「読まれる」ようには作られているが、「参照され、検証され、追跡される」ようには作られていない。**

これは `direction-review-2026-08-13.md` が全層で見つけた構造——**主張した保護範囲 > 実際の保護範囲**——の憲法層での現れである。

- 憲法は「これは不変条件である」と主張する。
- しかし**どの計画がどの不変条件に依拠しているかを機械的に辿れない。**
- したがって不変条件を変更したとき、**何が壊れるか分からない。**
- 逆に、計画が不変条件に違反していても**検出されない。**

`DOMAIN-SCORING-SURFACE-01`（画面に「健全性 N%」が出荷されていた件）は、この帰結の実例である。`domain.md` と `ui_design_handoff.md` が採点を禁じているのに、**禁止と実装を突き合わせる経路が無かった**ため4か月以上気づかれなかった。

---

## 3. 施策

優先度は「接続の欠落を埋める効果 ÷ コスト」で決めた。

### P1: `domain.md` に不変条件の識別子を与える（最優先）

**なぜ最優先か**: 最も参照される文書に識別子が無いことが、接続不能の中心的原因である。他のすべての施策がこれに依存する。

**内容**:
- `§2 基本思想` の3概念と `§7 AIの役割定義` の禁止事項に、安定識別子を付す。`w_type_iterative_inquiry_requirements.md` の `WIR-01` 形式に倣う。
- 命名は `DOM-` 接頭辞。例: `DOM-HOLD-01`（保留）、`DOM-DISCOMFORT-01`（違和感は説明責任を伴わない）、`DOM-REV-01`（可逆性）、`DOM-AI-PROHIBIT-01..n`（AIの禁止事項を1項目1IDで）。
- **既存の散文は変えない。** 識別子を付けるだけとし、意味の変更を伴わせない。`domain.md §9` の変更ルール（実装都合で変えてはならない）に抵触しないため。

**効果**: issue・ADR・チェックリストが「どの不変条件に依拠/抵触するか」を名指しできるようになる。

**コスト**: 小。1文書への追記。

**注意**: 識別子を付けた時点では**何も検証されない**。P3 とセットで初めて効く。単独で終えると「識別子はあるが誰も使わない」状態になる。

---

### P2: 識別子体系を憲法層全体へ広げる

**内容**: `kj_technique.md`（検査手順に `KJT-` を付す。特に §3 表札検査・§4 空白の列挙・§5 A/B照合・§6 失敗の徴候12項目）、`ai_kj_execution_procedures.md`（`AKP-`）、および部分的にしか持たない3文書の体系を揃える。

**なぜ kj_technique が重要か**: `direction-review` が「製品の中核は検査であり、それが最も薄い」と結論した。**検査に識別子が無い限り、どの検査が未実装かを計画側から追跡できない。** 現に §6 の失敗の徴候12項目のうち機械化されているのは1項目だけだが、この事実は識別子が無いため一覧化できていない。

**コスト**: 中。5文書。

---

### P3: `00_Prompt` 固有の検証を `docs_check` へ追加する

**内容**:

1. **Status 語彙の統制** — `Normative / Informative / On-demand / Superseded` を定義し、全文書に必須化。issue memo の `issue_memo_status.py` と同じ形。括弧書きの補足は別フィールド（`Tracked-by:` 等）へ分離する。
2. **識別子の一意性** — `00_Prompt` 全体で識別子が重複しないことを検証。ADR の `DC-ADR-001` と同じ性質の規則。
3. **参照の解決** — issue・ADR・設計文書から `DOM-*` / `KJT-*` 等を参照したとき、その識別子が実在することを検証。**これが接続の要である。**
4. **行番号参照の禁止** — `00_Prompt/xxx.md:88` 形式を検出して落とす。腐る参照を新たに作らせない。

**なぜ P3 が決定的か**: P1・P2 は識別子を**作る**だけであり、使われる保証がない。P3 は**使われた識別子が正しいことを保証する**。`DOGFOOD-METRIC-01` の能力カナリアと同じ考え方——主張と実効範囲を一致させる機構である。

**コスト**: 中。`docs_contract_checks.py` への規則追加とテスト。

---

### P4: `00_Prompt/README.md` を置き、二種別を明示する

**内容**:
- 憲法層が何を含むかの索引。
- **製品憲法**と**エージェント運用**の区別を明示する。前者は変更にADRを要し、後者は道具の変化に追随してよい、と権威の差を書く。
- 各文書の Status と、依拠する識別子体系を一覧する。
- `AGENTS.md` の読み順表とは役割を分ける（あちらは「いつ読むか」、こちらは「何があるか」）。

**コスト**: 小。

**注意**: 物理的なディレクトリ分割（`00_Prompt/product/` と `00_Prompt/agent/`）は**行わない**。全リポジトリの参照64件超が壊れ、利得に見合わない。**README による論理的な区別で足りる。**

---

### P5: 憲法層から実装詳細を分離する

**内容**: `ai_cognitive_externalization_requirements.md` の §7 以降（ContextBundle 構成、IR 仕様、MMR ルーティング要件）を `02_Architecture/` へ移し、憲法側には原則と参照のみを残す。

**なぜ**: 憲法が実装詳細を抱えると、実装変更のたびに憲法を触ることになり、**「憲法は変えてはならない」という規律そのものが摩耗する。**

**コスト**: 中〜大。参照34件の追随が要る。

**優先度が低い理由**: 実害が出ているわけではなく、P1〜P4 が接続の欠落を直接埋めるのに対し、これは衛生の問題である。**P1〜P4 の後に行う。**

---

### P6: 計画側に「依拠する不変条件」欄を設ける

**内容**: `01_Plans/issues/TEMPLATE.md` と ADR テンプレートに、次の欄を追加する。

```
- Norms: DOM-AI-PROHIBIT-03, KJT-INSPECT-02
```

P3 の参照解決規則がこれを検証する。

**効果**: 逆引きが可能になる——「`DOM-DISCOMFORT-01` を変更したら、どの計画が影響を受けるか」に答えられる。現在この問いには**答えられない。**

**コスト**: 小（テンプレート）＋運用（記入の習慣）。

**注意**: **必須化は P1〜P3 の完了後**とする。識別子が無い段階で欄だけ作ると、`TBD` で埋まる欄が増える。`SEC-ADMIN-PLANE-01` の `Source Issue: TBD` が docs-check に引っかかった件と同じ失敗になる。

## 4. 実施順序と依存

```
P1（domain.md へ識別子）
 └→ P2（体系を全体へ）
      └→ P3（検証を追加）★ここで初めて機構として成立
           └→ P6（計画側に欄を設け必須化）
P4（README・二種別の明示）  ← 独立。いつでも可
P5（実装詳細の分離）        ← P1〜P4 の後
```

**P3 に到達しない限り、P1・P2 は「識別子はあるが誰も使わない」状態で終わる。** P1 だけを実施して満足しないこと。

---

## 5. 意図的にやらないこと

- **ディレクトリ分割**（P4 注記）— 参照64件超が壊れ、利得に見合わない。
- **既存の散文の書き換え** — P1・P2 は識別子の付与に限る。`domain.md §9` は実装都合での変更を禁じており、識別子付与はその例外ではなく**意味を変えない操作**として実施する。
- **`00_Prompt` の網羅的な再構成** — 憲法層は安定していることに価値がある。接続の欠落を埋める最小の変更に留める。
- **識別子体系の事前完全設計** — `DOM-` / `KJT-` の粒度は、P1 の実施中に実物を見て決める。机上で完全な体系を作ろうとしない。

## 6. 測定

本施策が効いたかは、次で判定する。

| 指標 | 現在値 | 目標 |
|---|---|---|
| `domain.md` への参照のうち識別子を伴うもの | **0 / 64** | 新規参照は識別子必須（既存の遡及修正は求めない） |
| 行番号参照（`00_Prompt/*.md:NN`） | 3 | 0（P3 で機械的に禁止） |
| Status を持つ憲法層文書 | 3 / 7 | 7 / 7 |
| 識別子の解決検証 | **無し** | `docs_check` で検証 |

**注意**: これらは**存在を数える指標**である。`ADR-0075` の L2 昇格条件②（三要素検証節の適用数）が遡及適用で構造上100%へ飽和した失敗と同じ性質を持つ。したがって次を併記する。

> **効果の指標**: 不変条件を1つ変更したとき、**影響を受ける計画文書を機械的に列挙できるか。** これができないうちは、識別子がいくつ増えても接続は成立していない。
