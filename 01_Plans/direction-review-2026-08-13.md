## 0. 結論（先に）

**方向は正しい。順序が反転している。**

`02_Architecture/post-mvp-business-scope-design-program.html`（2026-08-10）が定めた3拡張軸——主体の複数化 → 成果物の複数化 → 境界の外部化——は、依存関係から導かれた正しい順序であり、7観点はすべてこの枠組みへ射影できる。枠組みを作り直す必要はない。

問題は**力の流れ方**にある。直近3日間のコミット206件のうち、実装は `03_Implement/backend` 176件に対し `frontend` 45件、設計正本 `02_Architecture` は10件台である。同期間に起票されたドッグフーディング系9件は全て同日に Done となった。一方でプログラム第1反復の残作業（`ADR-0072` 採択）は 2026-08-09 の起票以来 Proposed のまま、第2反復の起点（`documents` に所有者と生涯が無い）は 2026-08-10 に特定されて以来コード上まったく動いていない。**第3・第4・第5反復に対応する issue は1件も存在しない。**

つまり、**判断を測り・検証し・統治する仕組みへ力が流れ、その仕組みが判断すべき対象そのものが止まっている。** これは怠慢ではなく構造である。メタ作業は常に着手可能で、実作業は判断待ちで着手不能だからである。

したがって最優先は実装ではない。**決定キューを空けることである。**

## 1. 到達点の評価（何が本当にできているか）

過小評価を避けるため、まず事実を置く。

**強い部分。**

- **KJ法の A型モデルは本物である。** カード・型付き関係（`negate` による対立を含む5種）・多角形島・階層・**表札をカードとして重ねる設計**（`placardCardId`）・保留/批評/退避の可逆性。この領域のツールとして高い水準にある。
- **単独実務者の業務フローは完成している。** 「1人が、1つの文書で、KJ法を最後まで回せる」は成立済み。
- **運用文書はこの規模のプロジェクトとして例外的に良い。** 7製品分の backup と**隔離リストア**手順、障害分類5種、診断バンドル契約。しかも復旧演習が実テストで裏付けられている（`test_data_maintenance_recovery_exercise.py`）。

- **ドッグフーディングは実際に本物のバグを捕まえた。** 旧版文書の素の500（`DOGFOOD-02`）、MCP HTTP のステートレス破壊、レート制限の実証。装置は機能している。

**この評価があるうえで、以下を述べる。**

## 2. 全層に共通する単一の構造

7観点を別々に調査したが、見つかった欠陥はすべて**同じ形**をしていた。

> **守っていると宣言している範囲より、実際に守っている範囲が狭い。**

`DOGFOOD-METRIC-01` と `dogfood-analysis-synthesis-2026-08-12.md` §2 が既に一般形を掴んでいる——「測定器と測定対象が同一主体の管理下にあり、測定器を弱めることで指標を満たせる」。本レビューはこれを一段広げることを提案する。

> 弱められるのは測定器だけではない。**保護・検査・ゲートのすべてが、その実効範囲を誰も測っていないとき、主張だけが残る。**

## 3. 製品としての最重要事項

方法論の正本 `00_Prompt/kj_technique.md` は、この技法の核心を一文で述べている。

> カードは「ちがう」と言えない。（`:66-71`）

だから検査が要る、という論理構成になっている。**検査は方法の付属物ではなく、方法が方法であるための機構である。** 「検査を省くことは、耳を塞ぐことと同じである」（`:70-71`）。

その検査が、実装で最も薄い。

| 検査 | 方法論での位置 | 実装 |
|---|---|---|
| **空白の列挙**（§4） | 「この技法の最大の産物のひとつ」。ゼロは失敗の徴候 | **データモデルに表現が存在しない**。`DocumentV1` に空白を保持できる場所が無い |
| **表札の戻し検査**（§3） | 1枚でも「ちがう」と返れば表札は無効。決定的な検査 | 転置検査（半分）は良く実装されている。**戻し検査は、カードが特定の表札を拒否したことを記録する構造が無い** |
| **A/B照合**（§5） | 双方向。**報告は件数で**。ゼロは疑うべき | 型無しの平坦なリスト。方向フィールドも件数も無く、**「ゼロなら疑う」を評価できない** |
| **停止条件・問い返し**（§0, §7） | 5つの問い返し起点、各操作に3回失敗の停止条件 | `routes/ai.py` は単発生成。**停止条件の実装ゼロ** |

さらに、**実行時のAIプロンプトが方法論を運んでいない。**

- `routes/ai.py:1060`: `"Group these KJ-method cards into thematic islands"` — **"thematic"（主題別分類）は、方法論が最大の失敗として名指ししている枠組みそのもの**（`kj_technique.md:21-33`）。1段目2〜3枚の制約も、孤立カードを残す指示も渡っていない。
- `routes/ai.py:1042`: `"clearer and more concise"` — 方法論はモデルの流暢さこそが素材を上書きする機構だと警告している。「簡潔に」はそれを積極的に招く。名詞止め禁止は渡っていない。
- `routes/ai.py:281-295`（表札）: 転置検査も戻し検査も無く、`"Prefer the strongest supporting card ids"` という順位付け表現が入っている。

`00_Prompt/ai_kj_execution_procedures.md` は Status: Normative であり、これらの制約を全て規定している。**規定は実装へ届いていない。**

そして構造的に重要な点——**これはドッグフーディングでは見つからない。** `01_Plans/dogfood/adopting-org-patterns.md:9-15` が自ら記録している通り、題材が「本プロジェクト自身の設計判断・issue・ADR」である限り、**未分化な「違和感」「保留」「曖昧な意味」を扱う操作は起動しない**。設計判断は既に分化した対象だからである。`DOMAIN-SCORING-SURFACE-01`（出荷中の健全性%）がドッグフーディングを素通りしたのは、その予測が的中した実例にあたる。

加えて、**AI伴走者の経路（MCP）は、まさにこの核心価値を運べない。** 未レビューカードは `safeMode:false` でも全 constraint で `cards=0`（`DOGFOOD-05` 実測）、`holdState` と `critique` は投影スキーマに無い（`DOGFOOD-08`）。**AIは人間が既に確定させた内容しか見られない——AIの助けが最も要らない領域だけを見ている。**

安全境界（`SEC-CONTEXT-PROJECTION-01` の fail-closed）自体は正しい。問題は、**その境界のもとで製品の中核提案が成立するかを誰も設計していない**ことにある。`DOGFOOD-05` は「適用範囲の明示」で閉じられており、これは記録であって解決ではない。

### 優先1 — 観測基盤（`OPS-OBSERV-01`）

7観点のうち**4つ（操作経路・規模・複数テナント・管理容易性）が共通に依存する土台**であり、かつ安い。

現状: ログ設定が存在しないため `extra={...}` で渡した8箇所の構造化情報が**全て捨てられている**（監査失敗の警告すら、どのテナントの何が失われたか出力されない）。`logger.error` はゼロ件。リクエストIDが存在しないため、利用者の「14:32に開けなかった」を突き合わせる手段が無い。`/healthz` は定数を返すだけで、DBを失っても `{"status":"ok"}`。メトリクスは皆無で、監視・アラート・SLOに言及するADR/issueが**リポジトリ全体で0件**。

**全ての運用手順が「ログを見る」で終わり、そのログに情報が無い。** 運用文書が良いだけに、この乖離が効いている。

最初の4項目（ログ設定 / リクエストID / `/readyz` / `KJ_ATLAS_APP_REVISION` の配線）はいずれも小さく、**特にログ設定は既に計算して捨てている情報をコード変更なしで有効化する**。

### 優先2 — 出荷中の不変条件違反を閉じる（`DOMAIN-SCORING-SURFACE-01`）

新機能ではなく、既に宣言している不変条件と実装の齟齬である。`AI-IMPORTANCE-SCORING-01` が同じ不変条件でバックエンドの採点を削除した一方、**画面の「健全性 N%」は誰も検査していない**。書き出し境界とMCP経路では `score`/`rank`/`confidence`/`priority` の混入を明示検査しているのに、利用者が最も長く見る面に検査が無い。**防御の周縁が中心より厚い。**

方法論は既に正しい提示形式を指定している——`kj_technique.md:185`「報告は件数で」。点数を件数へ変えるだけで、検査ロジックを一切失わずに整合できる。

### 優先3 — 検査の実装（三要素で見て最大の不均衡）

「三要素分析法を通した有効なデータ・機能拡充」という観点への回答は、**方法論自身が既に指し示している**。業務設計が完全に規定済みで、データ設計・機能設計が追随していない領域を並べると、上位はすべて §3 の検査群になる。

1. **空白（voids）** — 業務✓✓ / データ✗ / 機能✗。追加型の `DocumentV1.voids?: VoidEntry[]`（`schemas.md` §14以降の追加オプション方式に一致）と、決定論的（provider=none可）な空白候補検出、ゼロ空白の注意喚起。これは `RoundHandoffV1.unresolvedQuestions` に文書レベルの供給源も与える。
2. **A/B照合の方向と件数** — `NarrativeCheckIssue.direction` と `counts` の追加。プロンプトは既に双方向を要求しているのに応答が畳んでいるだけなので、**変更は小さい**。
3. **表札の戻し検査** — カード→表札の異議記録（既存の `CRITIQUE_TAGS` の `not_the_same`/`feels_off` を再利用可能）。
4. **実行時プロンプトを `ai_kj_execution_procedures.md` に一致させる** — "thematic" の除去、2〜3枚制約、名詞止め禁止、転置・戻し検査。**Normative文書が既にあるので設計は不要で、実装のみ。**

### 優先4 — プログラム第2反復以降を issue へ落とす

第3・第4・第5反復に issue が1件も無い。第2反復の起点は `ADR-0073` 採択（優先0）で解ける。第3反復（協働・共同編集）はプログラム自身が「Miro/Notion/Figma/Slack/Atlassian の外部比較なしに判断すべきでない」と明記しており、**その比較調査が未実施**である。着手前に必要。

## 5. 明示的に決めるべきこと（現状どちらでもないもの）

- **規模拡大は目標か非目標か。** 現状は在庫上も文書上もどちらでもない。代表規模は約300カード／30島で固定され、その先の要件・予算・測定が空白。監視の計画はゼロ。一方で複数テナントSaaSの実装は在庫最大の投資先になっている。「小規模自己ホストに徹する」も正当な判断であり、その場合は**非目標として明記する**ことで多くの issue が閉じられる。
  なお 2026-08-13 に上限系が前進した——`KJ_ATLAS_MAX_DOCUMENT_BYTES`（20 MiB）と `KJ_ATLAS_MAX_DOCUMENT_CARDS`（10000）が `SEC-DOC-BOUND-01` で導入され、`KJ_ATLAS_ALLOW_JIT_PROVISIONING` の実装既定値が `true` → `false` へ変更された（`SEC-RATE-LIMIT-01`。既定でヘッダー1本から利用者を自動生成できる経路が閉じた）。個別の上限は入り始めたが、**レート制限は未実装のまま**（`SEC-RATE-LIMIT-01` は Draft）で、テナント単位の資源予算という概念は依然存在しない。同期プロセス40スレッド／DB接続15本に対しLLM呼び出しのtimeoutが60〜120秒であり、1テナントが全テナントを飽和させ得る構造は残っている。
- **`ROADMAP.md` の陳腐化。** 「近接フェーズ（Next 1–2 Releases）」に挙がる島の折りたたみ・多角形島・視座プリセット・Trace Analytics は**いずれも既に Done**。非目標に `SaaS依存設計` とある一方、実際の最大投資先が `SAAS-TENANT-*` 13件＋ADR 6本。**公開している方向と実際の方向がずれている。** この Repo は設計正本と実装の乖離を検出する仕組みを何層も持つが、**「宣言した方向」と「実際の方向」の乖離を検出する仕組みだけが無い。**
- **ドッグフーディングの題材。** 自己言及題材では核心価値が起動しない（本レビューで実例2件）。`adopting-org-patterns.md` の Org-A（自治体政策・50枚超）が未着手のまま。**外部題材を1つ通すことが、他のどの検証よりも多くを明らかにする。**
- **`ai_eval_results.md` の正本。** 記入済み結果と空テンプレートが同一ファイルに併存し、どちらが正本か文面から判別できない。
- **改善件数の不一致。** 同じ「改善点」の件数が4箇所で 45 / 12 / 11 / 8 と食い違っている。
- **`AGENTS.md:58` と `dogfood/README.md:61-62` の指標値が食い違っている**（警告1件 vs 2件、ADR 75/75 vs 76/76）。
- **自律性の降格条件が存在しない。** `ADR-0075:47` は「降格条件も明示」と自ら書いているが、リポジトリ全体に定義が無い。L4の「人間の介入率5%未満」にも測定器の定義が無い。

## 6. 週次サイクルについて

L3昇格条件③は「週次ドッグフーディング運用3ヶ月継続」である。第1回（2026-08-11〜12）以降、第2回が実行されていない。起点を 2026-08-11 とすると**最短でも 2026-11 まで L3 到達は不可能**であり、中断すればその都度リセットされる。

現在の運用にはもう一つ観察がある。AIが「仮承認」で選択肢を採択し同日に Status: Done とする運用のため、**DOGFOOD系9件がすべて Done となり、プロセスに未解決バックログがゼロになっている**。完了しているように見える一方で、週次第2回未実施・月初未到来・R2〜R6の反復ゼロといった**未実行フェーズが可視化されない**。仮承認に対する否認・補正の期限も、未レビュー仮承認の一覧も無い。

また2系統のドッグフーディングが交差していない。系統A（`ADR-0042` の実使用走行、`dogfood-log-2026-06-26/07-08/07-10`、UX摩擦4件を産出）と系統B（W型自己管理）があり、**系統Aで見つかった実使用の摩擦が、系統BのR1カード群に一切入っていない**。R1 の17カードは全て設計プロセス由来である。実使用の摩擦がプロセスへ還流する経路が閉じていない。

## 7. まとめ

- **枠組みは正しい。** post-MVP プログラムの3拡張軸と5反復は作り直す必要がない。
- **律速は判断であって実装ではない。** ADR 4本の採否で P0 2件・P1 4件が同時に解ける。
- **観測基盤が4観点の共通前提であり、最も安い。**
- **製品の核心——素材が「ちがう」と言い返す機構——が最も薄く、かつ自己言及ドッグフーディングでは永久に見つからない。** 外部題材の投入が要る。
- **「主張した保護範囲 > 実際の保護範囲」が5件以上再発している。** 能力カナリアを検出器スクリプト以外——特に三要素ゲート自身——へ広げる必要がある。
- **宣言した方向と実際の方向の乖離を検出する仕組みだけが無い。** 設計正本と実装の乖離には何層も検出器があるにもかかわらず。
