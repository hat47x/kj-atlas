# 1. CLIの目的（Why）

`kj-atlas` CLI は、Webアプリ（フロントエンド）以外の経路から kj-atlas を操作・検査・管理できるようにする。

直近の狙いは次の3点に限定する（GUIの代替を目指さない）：

1. **運用（Ops）**：バックアップ、移行、検証、バッチ処理、保守作業の自動化
2. **統治（Governance）**：公開範囲、監査・証跡、レビュー状態、エクスポート制御
3. **構造（Structure）**：KJ法データ構造の検査・整合性チェック・差分・集計

※ 原理的にはGUIでできることもCLIでできるべきであり、長期的にはその実現を目指していく方針。
※ GUIで実現すると画面数が増える、操作が複雑になる、あるいはリアルタイム性が求められるもので、管理者以外の利用頻度が限定的な機能については、CLIでの提供を優先する方針とする。
※ 特に「構造」に関しては、GUIでは提供しづらい高度な分析・検査機能を想定する。

# 2. 射程・適用範囲（Scope）

## 2.1 対象ユーザー

- 主対象：管理者 / 運用担当 / パワーユーザー
- 副対象：CI/CD を扱う開発者
- 非対象：一般利用者（一般職員・市民等）

## 2.2 対象リソース

CLIが扱う対象は **kj-atlasの正規データモデル** に限定する。

- Document（図解データ）
- View（視座・レビュー・可視性・診断結果など）
- Pack / Export bundle（共有・配布用）
- etc...

## 2.3 APIキーに関するデータモデルの青写真

- まずは「全権限マスターキー（特権プリンシパルに紐づく単一キー）」として実装速度を優先
  - データモデルの完成を待たずに実装が可能（先に完成させることが望ましいが）
- 「ユーザー」と「APIキー（認証情報）」の間に「プリンシパル（主体）」という抽象レイヤーを挟む
  - ヒューマンアクセスとマシンアクセスの分離
  - APIキーごとに権限を細かく設定できるようにする
- 「サービスアカウント（独立したプリンシパル）」がAPIキーを持つ形を想定
  - ユーザーアカウントとAPIキーの紐付けは必須ではない
- 「ユーザー」に紐づく形のAPIキーも将来的には想定
  - APIキーの発行権限をもつユーザーはあらかじめロール設定などにより限定される（権限制御の仕組み自体は実装済の想定）
  - APIキーの有効期限やローテーション、不正利用検知の機構についても要検討

## 2.4 非対象（Non-Scope）

- APIが提供する機能以外をCLIで固有に提供すること
  - ロジックの散逸を防ぐため、CLIはあくまでもAPIのクライアントの位置づけとし、APIが提供する機能を呼び出すことに専念する
  - 複数のAPIを組み合わせるような複雑な操作については、原則としてユーザサイドでのシェルスクリプトでの実現を想定する
    - ただしAPIとして提供することが自然であったり、パフォーマンス等の観点から独立したAPIとすることが望ましい場合は、APIおよびCLIの両方を拡充する方針

# 3. 導入フェーズ（Phased Adoption）

## 3.0 フェーズ横断の前提条件（Gate）

- **Gate-A（アーキ整合）**：`02_Architecture/api.md` と `schemas.md` にCLIで呼ぶ対象APIが明記されている。
- **Gate-B（安全整合）**：`THREAT_MODEL.md` と矛盾しない認証・監査・ログ方針が定義されている。
- **Gate-C（運用整合）**：`04_Documentation/operations.md` に運用者向けのキー管理・失効手順が追記されている。

> 注：Gate未充足の段階では、CLI実装を開始しても「実験扱い」に留め、正式機能として公開しない。

## Phase X-0：仕様・骨格確立

- データモデル設計（APIキー、プリンシパル、権限間の整合）
- コマンド名前空間設計（AWS CLI相当の拡張性）
- 入出力フォーマット方針（json/yaml/zip、stdin/stdout）
- エラー体系（exit code, error code, human-readable message）
- セキュリティ基本方針（鍵の扱い、ログの秘匿）

成果物：データモデル設計書（既存への追記）、CLI仕様書（新規）

完了条件（ドラフト）：
- APIキー／プリンシパル／ロールのERまたは同等モデルが文書化され、少なくとも管理者キーのライフサイクル（発行・失効・ローテーション）が記述される。
- `kj --help` の情報設計（トップレベルnamespace、共通オプション、exit code）が仕様書として固定される。
- 監査ログに含める最小フィールド（timestamp/principal/action/resource/result/request_id）が合意される。

## Phase X-1：全権限マスターキー＋データ移行用APIの実現

目的：
- 管理者がバックアップやデータ移行のために用いる機能を優先的に実現する

対応（確定ではない）：
- エクスポート/インポート/ドキュメント一覧取得機能
  - まずは単一のdocument単位のエクスポート/インポートを実装
  - ドキュメント一覧取得機能と合わせることで全件エクスポート/インポートを実現可能
  - 安全なインポートのためのスキーマ検証（validate）
  - 安全なエクスポートのための検査（safeMode関連の静的検査）

完了条件（ドラフト）：
- 管理者キーで `doc export` / `doc import` / `doc list` がCLI経由で実行できる。
- import時にschema不整合を検出し、exit code=1（validation failed）を返せる。
- export時にsafeMode違反の兆候を検知した場合、明示的な警告または失敗を返す挙動が仕様化される。

## Phase X-2：サービスアカウントに紐づく権限制御付APIキー＋API機能の拡充

目的：
- 管理者が明示的にサービスアカウントの払い出しを受けたユーザが、各種運用を可能にする

対応：
- APIが提供する主要機能のCLI対応
- 監査ログ抽出など

完了条件（ドラフト）：
- サービスアカウント単位で権限を分離し、読み取り専用キーで書き込み系APIが拒否されることを確認できる。
- `kj audit ...` 名前空間で、期間・principal・actionを軸に監査ログを抽出できる。
- 権限不足時のエラー形式（auth error）と運用者向けメッセージ方針が統一される。

## Phase X-3：ユーザに紐づくAPIキー＋職掌業務のオートメーション化対応

目的：
- 部門管理者やパワーユーザが自身でAPIキーを発行できるようにする
- 自身の職掌に限定されたデータアクセスのもと、業務効率化のためのAPIを安全に利用可能とする

対応：
- APIを組み合わせることで、下記のような要求を実現可能とする
  - documentに対するレビュー自動承認
  - エクスポートしたドキュメントの外部LLMを用いた独自検証
  - 生成AIエージェントによる業務代行
  - Redmine等のタスク管理ツールとの連携

完了条件（ドラフト）：
- APIキー発行主体がユーザー/サービスアカウントで区別され、監査上追跡可能となる。
- 業務自動化で必要な最小コマンドセット（例：list/export/review/audit）が定義される。
- 自動化スクリプトの再実行安全性（冪等性または重複実行時の方針）が明文化される。

## Phase X-4：MCPサーバの導入

目的：
- APIサーバとCLIの間にMCPサーバを挟むことで、AIエージェントによる業務代行をよりシームレスに実現する

対応：
- kj コマンドをラップした「KJ MCPサーバー」を立てることで、MCP対応のAIエージェントが、標準化されたインターフェースを通して kj コマンドをネイティブなツールとして呼び出せるようになる

完了条件（ドラフト）：
- MCPサーバーから利用可能なCLIコマンド範囲が allow-list で管理される。
- 機密情報（キー・トークン）がMCPの入出力に露出しない設計になっている。
- エージェント利用時の監査帰属（どの主体が実行したか）が追跡できる。

## 3.5 優先順位（現時点案）

1. Phase X-0（仕様固定）
2. Phase X-1（移行・バックアップ最低限）
3. Phase X-2（権限制御と監査）
4. Phase X-3（ユーザー起点の自動化）
5. Phase X-4（MCP連携）

理由：
- 運用安全性を担保する前に自動化を進めると、権限逸脱・監査欠落のリスクが上がる。
- MCPは価値が高い一方、基盤APIとCLIの安定が前提となる。


## 3.6 フェーズ横断リスクと先行緩和策（ドラフト）

- リスク1：認証モデル未確定のまま実装を先行し、後方互換を壊す
  - 緩和：Phase X-0でキー寿命・失効・権限境界を先に仕様化する
- リスク2：監査項目不足で、インシデント時に追跡不能になる
  - 緩和：最小監査フィールドをX-0で固定し、X-1から必須記録とする
- リスク3：CLI独自ロジックが肥大化し、APIと挙動乖離が発生する
  - 緩和：Non-Scope原則（CLIはAPIクライアント）を破る提案は、API側拡張と同時審査に限定する

# 4. コマンド体系（Namespace Design）

CLI名は `kj` とする。

## 4.1 設計原則

- AWS CLI等にならい、対象領域ごとに **サブコマンド** を設ける
- 将来の拡張に備え、名前空間を広く保つ
- コマンド追加で破壊的変更を起こさない（後方互換重視）

## 4.2 たたき台：トップレベル名前空間案（確定ではない）

- `kj doc ...`：Document 操作
- `kj view ...`：View 操作
- `kj policy ...`：公開範囲/安全設定の検査・適用支援
- `kj audit ...`：監査ログ関連

※ 個別機能名はここでは確定しない。必要なら各名前空間配下で再検討する。
※ サブコマンド名は原則としてAPIの階層名を踏襲する方針とする。

## 4.3 共通I/F方針

- `--format json|yaml|text`（デフォルトは用途別に定義）
- `--input -` / `--output -` による stdin/stdout 対応
- `--quiet` / `--verbose` / `--debug` の整備
- exit code：0=success, 1=validation failed, 2=usage error, 3=runtime error, 4=auth error（暫定）

追加検討（現時点での具体化）：
- `--profile <name>`：複数環境（local/staging/prod）を安全に切り替える。
- `--api-base-url`：緊急時の明示上書き。通常は設定ファイル優先。
- `--request-id`：監査追跡のため、外部システム側トレースIDを受け取る。
- `--dry-run`：変更系操作の事前検証（可能なAPIのみ対応）。

互換性原則：
- 既存コマンドの引数意味は変更しない。
- 非推奨化は最低1フェーズ維持してから削除可否を判断する。


## 4.4 Phase X-1向け最小コマンドセット（案）

- `kj doc list`：document一覧取得（ID・更新時刻・状態）
- `kj doc export --doc-id <id> --output <path|->`：単一documentエクスポート
- `kj doc import --input <path|->`：単一documentインポート
- `kj doc validate --input <path|->`：インポート前検証

制約：
- 上記はAPI提供範囲に一致する場合のみ実装対象とする。
- `validate` は「受理可否」を返す機能に限定し、自動修復は対象外とする。

# 5. セキュリティ・運用要件（最低限）

- 管理者キー等の秘密情報を **ログに出さない**
- `--debug` でも秘密情報は必ずマスク
- 設定は環境変数 / 設定ファイルで指定（優先順位を明確化）
- API利用時には大原則として監査ログを残すため、CLIからAPI呼出時もそのまま監査ログに載る形を想定

優先順位（高→低）：
1. CLI引数（明示指定）
2. 環境変数
3. 設定ファイル
4. デフォルト値

最小運用ルール（案）：
- 設定ファイルの権限はOS標準でowner read/writeのみを推奨する。
- 監査ログ抽出結果を外部共有する場合は、principal識別子のマスキング方針を用意する。
- CIでCLIを使う場合、長期キーではなく短命トークンまたは定期ローテーション前提とする。
