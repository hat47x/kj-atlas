# ADR-0022: Documentation Change Governance（文書変更ガバナンス）

- Status: Proposed
- Date: 2026-03-08
- Deciders: Project Maintainers
- Scope: `01_Plans/`, `02_Architecture/`, `04_Documentation/`, `AGENTS.md`

## Context

DOC-OPS-04 の前処理監査では、ADR候補D（Documentation Change Governance）として次の課題が確認された。

- 更新DoD・同期責務・承認責務が Issue 単位で再定義されやすい。
- 文書横断更新時に「誰が何を承認し、どの段階で停止すべきか」が曖昧化しやすい。
- AUTH-OPS-03 / DOC-OPS-02 で固定化した用語・役割・導線・固定値（D1〜D4）が、将来変更時に再ドリフトするリスクがある。

加えて、以下の AC/DoD 不足がある。

- AC不足: 文書変更タスクでの「恒久ルール決定」と「実行記録」の境界定義が不十分。
- DoD不足: 承認段階ごとの停止条件と、未承認時の引き渡し情報の最小要件が不十分。

主要選択肢:

1. 既存運用のまま、Issueごとに都度判断する。
2. **文書変更ガバナンスをADRで固定し、Issueは実行追跡のみに限定する。**（採用）
3. CIゲートだけを強化し、責務分離と承認段階は明文化しない。

加えて、ADR-A（`ADR-0022-doc-ops-04-documentation-information-interface.md`）で固定した
DOC-OPS-04 情報設計I/F（用語・見出し・判定メタ）との整合を、本ADR-Dの受入条件に含める。

## Decision

**文書変更は「責務分離 + 段階承認 + 固定順序同期 + 停止条件」を共通ガバナンスとして運用する。**

### 1) Plan（AC/DoD補完）

文書変更タスクは着手時に、少なくとも次を明記する。

- AC-1: 変更対象文書と対象外文書（非目標）
- AC-2: 上流正本（SSOT）と下流追随文書
- AC-3: 承認段階（G0〜G3）と通過条件
- AC-4: 「恒久ルール変更（ADR）」と「実行記録（Issue/PR）」の記載境界
- AC-5: ADR-Aで固定した用語I/F（正本 / 暫定メモ / 決裁入力 / 例外承認）との整合
- DoD-1: 境界曖昧性がない（責務分離・承認段階）
- DoD-2: 同期順序と実施結果を再現可能に記録
- DoD-3: 未承認停止時の引き渡しメモを残す
- DoD-4: 停止理由・停止時刻・再開条件を監査可能な形で記録
- DoD-5: Verify時にゲート整合チェックリスト（G0→G3）を添付し、未充足項目を明示
- DoD-6: 例外承認の発動条件・承認者・失効条件を明記し、通常フローとの差分を監査可能に記録

境界定義（AC-4）:

- ADRに記載する内容: 恒久ルール（What/Why）、役割、承認段階、停止条件、最小引き渡し要件。
- Issue/PRに記載する内容: 実行日時、差分、承認依頼ログ、未解決論点、再開時の作業メモ。

補完提案（運用テンプレート）:

- ACは `対象/非対象` `SSOT/追随` `ゲート条件` `記載境界` の4区分で記述する。
- DoDは `境界明確性` `同期再現性` `停止時引継ぎ` `監査可能性` `ゲート整合` の5区分で記述する。
- 用語I/Fは ADR-A の固定語彙（正本 / 暫定メモ / 決裁入力 / 例外承認）を優先し、別名を併記する場合は初出で対応表を示す。
- AC/DoD未記載のタスクはG0不通過として着手不可。

### 2) Execute（責務分離）

役割を以下に固定する。

- **Spec Owner**: 仕様正本（02_Architecture）更新責任。
- **Doc Owner**: 利用者向け文書（04_Documentation）同期責任。
- **Plan Owner**: 計画・追跡文書（01_Plans）同期責任。
- **Gate Approver**: 段階承認の判定責任（実行者と分離）。

責務分離ルール:

1. 正本更新なしに下流文書だけを先行変更しない。
2. 実行者と最終承認者を同一人物にしない（二者承認）。
3. ADRは恒久ルール（What/Why）のみを保持し、進捗・日次メモはIssueで管理する。
4. 各ゲートで「作成者（Executor）」と「承認者（Approver）」を明示し、同一ゲート内で兼務しない。
5. 承認者不在時は代理承認者を事前指定し、未指定の場合はG0で停止する。
6. 差し戻し対応（修正実行）と再承認判定は別担当とし、再承認時も兼務を禁止する。
7. 例外承認（緊急修正・期限制約など）を発動する場合は、決裁入力に「例外理由・適用範囲・失効条件」を必須記載する。

### 3) Verify（承認段階）

承認段階を G0〜G3 で固定する。

- **G0: Scope Gate**
  - 変更範囲・非目標・影響範囲を確定。
  - 役割割当（Spec/Doc/Plan/Gate Approver）と代理承認者を確定。
- **G1: Source-of-Truth Gate**
  - 02_Architecture の正本更新を先に完了。
  - 正本差分に対する承認ログ（誰が何を承認したか）を記録。
- **G2: Cross-doc Sync Gate**
  - 固定順序 `02_Architecture -> 04_Documentation -> 01_Plans -> AGENTS.md` で同期。
  - 同期結果を順序付きで記録し、順序逸脱があれば差し戻し。
- **G3: Closure Gate**
  - ドリフト4観点（用語/役割/導線/固定値）を確認し、DoDを満たした場合のみ完了。
  - 未解決論点が1件でも残る場合は完了不可。

いずれかのゲートで未承認の場合、次ゲートへ進まず停止する。

ゲート整合チェックリスト（必須）:

- G0整合: AC/DoD、役割、代理承認者、非目標の4点が埋まっている。
- G1整合: SSOT差分と承認記録が1:1で対応している。
- G2整合: 同期順序ログが `02_Architecture -> 04_Documentation -> 01_Plans -> AGENTS.md` と一致している。
- G3整合: ドリフト4観点の結果、未解決論点、DoD判定が同一記録に束ねられている。

Self-Correction（最大3回）:

1. Verifyで不整合検知時、修正→再検証を1サイクルとして記録する。
2. サイクル上限は3回とし、3回で解消しない場合はFail-safeを発動する。
3. 3回目失敗時は「未解消項目・阻害要因・必要な上位判断」を引き継ぎメモに必須記載する。
4. ゲート判定者間で承認結果が競合した場合（同一ゲートで相反判定が併存）は、回数に関わらず即時停止して競合報告へ移行する。

停止条件（Fail-safe）:

1. 必須承認者が未割当、または承認記録が欠落している。
2. 固定順序同期に逸脱がある（飛ばし・逆順・同時更新）。
3. ドリフト4観点のいずれかで不一致が解消していない。
4. 未解決論点に「判断者不在」または「再開条件未定義」が残る。
5. 例外承認の根拠（例外理由・適用範囲・失効条件）のいずれかが欠落している。
6. 同一ゲートの承認記録に相反判定（承認/差し戻しの併存）があり、優先判定者が確定していない。

上記いずれかに該当した時点で作業を停止し、G0へ巻き戻して再計画する。

停止条件の厳守ルール:

- 停止条件該当後に文書更新を継続してはならない（即時停止）。
- 停止後は「停止宣言（理由/時刻/ゲート）」を先に記録し、その後に引き継ぎメモを記録する。
- 停止解除はGate Approverの再開承認があるまで実施不可。
- 競合検知時は「競合当事者/競合判定/優先判定未確定理由/解消に必要な上位判断」を停止報告に必須記載する。

### 4) Proceed（引き渡しメモ）

停止または完了時には、以下を最小セットとして残す。

- 実施済みゲートと未通過ゲート
- 未解決論点（判断が必要な項目）
- 必要承認者と依頼内容
- 再開手順（次に行う1〜3ステップ）
- 停止条件への該当有無（該当時は根拠）

引き渡し最小要件:

1. どのゲートで停止したか（G番号）
2. 次に必要な承認アクション（承認者名/判定観点/期限）
3. 再開時の先頭手順（最初に確認すべきSSOTと差分）
4. Self-Correctionの実施履歴（実施回数、各回の修正内容、未解消有無）
5. 競合検知の有無（有の場合は競合報告IDと解消待ち論点）

### 非目標

- 文書本文の書き方（文体・表記ゆれ）を一律に規定すること。
- すべての文書変更を重い承認フローへ統一すること。
- 実装コードのレビュー規約を本ADRで再定義すること。

## Consequences

期待効果:

- 文書変更時の責務境界と承認責務が明確になり、判断の属人化を減らせる。
- 固定順序同期により、AUTH-OPS-03 / DOC-OPS-02 の再ドリフトを検知・抑止しやすくなる。
- 未承認停止時でも引き渡しメモにより、次担当者が再開しやすくなる。
- ADR-Aの情報設計I/Fに合わせることで、D単体レビューでもA/B/Cとの比較可能性を維持できる。

副作用/制約:

- 変更前にゲート定義を書く初期コストが増える。
- 軽微修正でも「正本確認」が必要になり、即時反映の速度は下がる可能性がある。
- 役割分離（二者承認）を満たせない体制では、完了判定が遅延し得る。
- 例外承認の記録要件が増えるため、短期運用ではドキュメント記載負荷が上がる。

## Verify (Phase 1)

- 判定: **Ready for approval / Not accepted yet**
- 根拠:
  1. A-I/F整合: 用語I/F（正本 / 暫定メモ / 決裁入力 / 例外承認）への準拠要件を AC/運用テンプレートに追加した。
  2. 用語ゆれ対策: 固定語彙優先と別名併記時の対応表ルールを明記した。
  3. 例外条件明確化: Execute/Verify の双方で、例外承認の必須記録項目と停止条件を明示した。
- 未充足:
  - `Status: Proposed` のため、Deciders承認待ち。

## Proceed (Gate)

- 承認依頼先: Project Maintainers（Gate Approver）
- 停止宣言:
  - 現在ゲート: **G3手前（承認待ち停止）**
  - 停止理由: ADR本文更新は完了したが、`Status` を `Accepted` に変更する最終決裁入力が未承認。
  - 再開条件: Gate Approver による承認後、`Status` 更新と統合フェーズへの引き渡しを実施すること。

## Approval request

- Request: 本ADR-Dを `Accepted` に変更する可否を、Project Maintainersへ承認依頼する。
- Required evidence:
  1. ADR-Aの用語I/Fとの整合（正本 / 暫定メモ / 決裁入力 / 例外承認）。
  2. 役割分離（二者承認）と停止条件（Fail-safe）の監査可能性。
  3. 例外承認の発動条件・責務・失効条件が本文で明示されていること。
- Gate rule: 承認完了まで本ADRは `Status: Proposed` のまま据え置き、統合ファイル更新は統合フェーズへ持ち越す。
