# 継続dogfood記録 — 2026-09-02 第2ラウンド

## 位置づけ

この記録は、KJ Atlas自身を日常的な開発対象としてKJ法で検討する継続dogfoodの第2ラウンドである。

第1ラウンドでは、外部AIとの共同思考における提案の受け渡しを扱った。今回は視野を広げ、現在のP0課題と初回導線を同じ場に置き、「次に不足しているのは新しい中核機能か、それとも価値を現実の利用へ接続する工程か」を検討した。

Case 001〜003の統制比較とは目的が異なる。今回も既知の設計判断や価値仮説を含むため、比較実験の入力には使用しない。生成AIの外部APIも使用していない。

## 今回の問い

> KJ Atlasの開発をよりよい方向へ進めるうえで、現在の律速はどこにあり、内部dogfoodから安全に今すぐ改善できることは何か。

「新機能を増やす」ことを初期仮説には置かない。現在のP0課題、dogfoodの到達点、READMEとgetting startedの初回体験を並べ、意味の近いものから統合した。

## 島1 — 内部の改善循環は回り始め、P0の未完は比較測定と第三者実証に残る

R1〜R7とCase 000を見ると、dogfoodで得た観察をカードからissue、契約、実装へ戻す循環は繰り返し利用できるようになっている。

一方、現在のP0には、人間の認知成果を条件比較する `COGNITIVE-EVAL-01` と、作者ではない第三者が自分の実資料を持ち込んだときにも価値が成立するかを確かめる `VALUE-REALNESS-01` が残っている。

このため、内部の改善循環が回ることと、外部の利用者に価値があることを分けて考える必要がある。

## 島2 — 暫定価値は定性資料の探索だが、最初の題材は作業手順に寄っている

`PRODUCT-POSITION-01` では、一次利用仕事を次のように暫定定義している。

> まとまりきらない定性資料や観察を、早すぎる分類・要約・合意で潰さず、出典・異論・保留・人間の判断権を残したまま構造化し、後から根拠へ戻れる共有可能な理解へ育てる。

同issueは、READMEとgetting startedが最初の10分でこの価値の一部を体験できるかを検査対象にしている。

しかし、現行getting startedの固定サンプルは「ユーザー課題を集める」「観察メモをカード化する」「似ている内容を近くに置く」であり、観察の中身ではなく作業手順に近い。教程として操作は学べるが、一次利用仕事との対応は弱い。

追加確認の結果、この3枚はgetting startedだけに書かれた例ではなく、`App.tsx` の `createDefaultDocument` に組み込みサンプルとして直接定義されていることも分かった。したがって、文書だけを変更すると画面と教程が食い違う。

## 島3 — 操作手順を増やさず、観察メモを使えば一次価値の一部まで体験できる

現行教程は、2枚を島にまとめ、1枚を未決のまま外に残し、保存・再読込・共有前確認へ進む。操作の流れ自体は、KJ Atlasの重要な性質を短時間で確認できるようにできている。

したがって、手順を増やさず、3枚の中身だけを「少し関係しているが、すべてを一つにまとめるべきではない観察メモ」へ変える。

例として、次の架空の観察メモを使う。

- インタビュー後、メモがチャットの奥に流れて、見つけ直すのに時間がかかった。
- 結論は残っているのに、どの発言を根拠にしたのか後から分からなくなった。
- 一人だけ違う意見だったので、そのまま議事録から落ちた。

前二つは「後から根拠へ戻りにくい」という近さを持つ。三つ目も記録の損失に関係するが、少数意見の消失という別の含みを持つため、教程では無理に同じ島へ入れず、`未決`として残す。

これにより、島を作る操作と同時に、「似て見えるものをすべてまとめない」「決めきれない観察を消さない」という使い方を体験できる。

なお、これは実在する利用者の証拠ではない。教程内でも「架空の観察メモ」と明記する。

## 島4 — 初回体験は整えるが価値を証明したとは扱わず、外部実証へ重心を置く

組み込みサンプルとgetting startedを暫定価値へ近づけることは、機能契約を増やさずにできる改善である。ただし、両者は同じ題材を共有しているため、文書だけを先に変えてはならない。画面上の固定サンプルと教程を一体で更新し、実際の初回導線で一致を確認する必要がある。

この改善だけで第三者価値や認知改善が証明されたことにもならない。

今回の内部dogfoodだけを理由に、`COGNITIVE-EVAL-01`、`VALUE-REALNESS-01`、`PRODUCT-POSITION-01` の状態や優先度は変更しない。

現在のP0群を並べたとき、新しい中核機能を増やすことよりも、比較測定と第三者実証を完了し、暫定価値を外部現実へ接続することが次の大きな未完領域に見える。ただし、これも内部dogfoodから得た仮説であり、外部実証の結果によって修正され得る。

## 課題の振り分け

| 観察 | 判定 | 対応 |
| --- | --- | --- |
| 組み込みサンプルが作業手順に寄り、一次利用仕事を体験しにくい | F1 | `PRODUCT-POSITION-01` に実使用証拠を追加し、組み込みサンプルと教程を一体で修正する |
| 初回教程で少数意見や保留の意味を体験しにくい | F1 | 既存の「島2枚＋未決1枚」の流れを保ち、題材だけを観察メモへ変える |
| getting startedだけを変更すると画面と文書が不一致になる | F1 | `App.tsx` の組み込みサンプルを同じ変更単位に含める |
| 内部dogfoodでは第三者価値を証明できない | 既存境界 | `VALUE-REALNESS-01` を維持し、状態・優先度を変更しない |
| 認知改善の因果を内部dogfoodでは証明できない | 既存境界 | `COGNITIVE-EVAL-01` を維持し、状態・優先度を変更しない |
| 現在の重心が外部実証へ移っているように見える | 継続観察 | P0群の実行結果を待ち、プロダクト位置づけを再評価する |

## 今回の判断

1. **新しいオンボーディングissueは作らない。** `PRODUCT-POSITION-01` が明示的にgetting startedを対象としているため、F1として戻す。
2. **初回導線の操作手順は増やさない。** 既存の短い導線を保ち、固定サンプルだけを観察らしい内容へ変える。
3. **組み込みサンプルと教程は一体で変更する。** 文書だけを先に変えて、画面との不一致を作らない。
4. **架空の例であることを明記する。** 教程を外部価値の証拠として扱わない。
5. **P0の状態・優先度を変えない。** 比較測定と第三者実証を内部dogfoodで代替しない。
6. **第三者実証後に教程も見直せる余地を残す。** 現在の一次利用仕事を固定的なマーケティング文言へしない。

## 戻し検査

- 「今は機能追加が不要」と言い切っていないか → R8のカードでは、P0群から見える現在の重心という仮説にとどめている。新たな実使用課題が出れば別途評価できる。
- 教程を書き換えることで価値を証明した扱いになっていないか → `c11`、`c12`、`c16` に外部実証との境界を残している。
- 少数意見を「必ず島の外へ置く」という新しい規則にしていないか → 今回は教程上の一例であり、一般規則にはしていない。
- 既存issueへ戻せる課題を新規issueへ増殖させていないか → `PRODUCT-POSITION-01` へF1として戻す。
- 文書だけを整えて実装との差を残していないか → `App.tsx` の組み込みサンプルとgetting startedを同じ変更単位として扱うことを明記した。

## 次回以降に観察すること

- 初見利用者が、教程後に「何をまとめ、なぜ一枚を残したか」を自分の言葉で説明できるか。
- 「未決」を単なる未操作状態ではなく、意味のある保留として受け取れるか。
- 架空の固定サンプルから、自分の仕事で扱う観察や資料を想起できるか。
- `VALUE-REALNESS-01` の第三者実証で、暫定一次利用仕事が支持・修正・棄却のどれに向かうか。
- その結果に合わせて、READMEとgetting startedの例を狭めたり置き換えたりする必要があるか。
