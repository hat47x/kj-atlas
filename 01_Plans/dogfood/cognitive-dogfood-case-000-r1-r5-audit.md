# Cognitive Dogfood Case 000: 既存R1–R5の認知dogfood監査

- Status: Observational audit
- Audit date: 2026-08-29
- Source artifacts: `doc_kj_atlas_dogfood_r1.json` ... `doc_kj_atlas_dogfood_r5.json`
- Related: `COGNITIVE-DOGFOOD-01`, `COGNITIVE-EVAL-01`, `cognitive-dogfood-case-001-product-purpose.md`

## 位置づけ

R1〜R5は、本比較計画より前に行われた探索的dogfoodであり、対照条件を持たない。したがって「KJ Atlasの認知増分を証明した成功例」とは扱わない。

一方、KJ Atlas自身の現実の設計・実装・開発運用を材料に、R1 問題提起 → R2 現状把握 → R3 本質追求 → R4 構想 → R5 具体策までを別々のキャンバス文書として外部化しており、後続のissue/ADR/実装へ接続した痕跡もある。このため、比較実験前の **Case 0（自然発生的・探索的観察）** として監査する価値がある。

## 監査で確認できること

### O1 時間をまたいだ思考状態が外部化されている

各ラウンドが独立したJSON文書として保存され、前ラウンドのカードIDや論点を参照しながら問いが進んでいる。

これは通常チャットの単一時系列と異なり、「その時点で何を問題と見ていたか」を後から比較できる状態を作っている。

ただし、この性質がKJ Atlas固有か、版管理された構造化文書でも同程度に成立するかは未比較である。

### O2 主張に出所を付ける行動が広く行われているが、Case 0は現行DocumentV1相当の制約下にある

R1〜R5ではカードの `meta.source` にADR、issue、設計文書、コード、セッション観察等が広く記録されている。

現行 `02_Architecture/schemas.md` も、`DocumentV1` は記録者・記録時間等の出自情報を保持せず、`Card.meta.source` は「外部の元記録へ戻る任意の手がかり」と位置づける。したがってR1〜R5のfree-text sourceは現行契約と矛盾しないが、commit SHAや当時の内容を常に再生成する不変provenanceではない。

一方、これは「KJ Atlasに系譜設計がない」という意味ではない。`ADR-0057` / `inquiry_journey_model.html` は、日常編集する `DocumentV1` と長期探究履歴を分離し、人が意味を確認した節目を不変 `RoundSnapshotV1` のDAGとして残し、`CardLineageEdgeV1` も扱う設計目標をすでに採択している。ただし実装・移行・CRUDが揃うまでは `L0: Planned` である。

したがってCase 0で観察したのは、**長期系譜の設計欠落ではなく、R1〜R5が使った現行artifactでは不変snapshot/lineageをまだ利用できないという実装・運用上の時点差**である。

### O3 前ラウンドの問題が部分解決として次ラウンドへ戻されている

R1の問題提起の一部は、R2で「部分的解決」として明示的に再評価されている。静的な課題一覧ではなく、対象側の変化によってカードの意味状態を更新している。

これは `COGNITIVE-EVAL-01` の M4（早期収束耐性）・M6（再訪/訂正可能性）に関係する正の兆候である。

ただし、R1〜R5 artifactだけから全カードの棄却・修正系譜を機械的に復元することは難しい。

### O4 思考成果が開発契約へ変換された例がある

R3では「三要素牽制設計法が存在してもissueテンプレートに三要素チェック欄がなく、使用を強制できない」という問題が置かれている。

現在の `01_Plans/issues/TEMPLATE.md` には `ADR-0067` を参照する「三要素整合（Business/Data/Function）」欄が存在する。

したがって少なくともこの論点では、dogfood上の問題提起と後続の開発プロセス契約との対応を確認できる。

これは M8（決定への変換品質）の観察例であるが、「KJ Atlasを使わなければ発見・実装されなかった」とまでは言えない。

### O5 デバッグ対象ではなく、プロジェクト自体が観察対象になっている

カードはUI/APIバグだけでなく、設計原理の硬直、文書同期、人間の認知バイアス、AI自律性、文脈窓、開発プロセスなどを対象にしている。

このためR1〜R5は、すでに「KJ AtlasをKJ Atlasの開発について考えるために使う」という自己参照的dogfoodになっている。

## 認知評価上の弱点

### W1 対照条件がない

同じ資料・問いを通常チャット、通常文書、別の図解手法等で解いた成果がない。したがって、発見した論点をKJ Atlas固有の増分として帰属できない。

### W2 問いの段階構造による誘導を分離できない

R1〜R5は問題提起→現状把握→本質追求→構想→具体策という問いをあらかじめ持つ。

この段階化自体が探索を深めた可能性があり、キャンバス/KJ外部表象の効果と分離できない。Case 001以降では4armすべてに同じ問い条件を与え、KJ Atlasだけが段階的問いを持つ状態を避ける。

### W3 採用されなかったAI提案をCase 0 artifactから十分に観測できない

最終カードからは「何が残ったか」は見えるが、R1〜R5 artifactだけではAIが何を提案し、人間が何を棄却・修正したかの完全な履歴は分からない。

KJ Atlasには別系統として proposal/audit の契約が存在するが、Case 0の保存成果物には比較評価に必要なproposal ledgerがまとまっていない。このためM5（AI依存校正）をCase 0から評価することは困難である。

### W4 生カードと分析カードの境界が一部曖昧

`claimType` は存在するが、内部資料に基づく事実、セッション観察、根本原因の推論、規範判断が近い表現強度で並ぶ場合がある。

例として「人間の認知バイアスに根ざしている」のような根本原因カードは、対象資料から直接確認できる事実ではなく推論である。Case 001以降では provenance と epistemic status を別々に保持する必要がある。

### W5 Case 0のsource再取得可能性は均一でないが、将来設計上は対処方向が存在する

`meta.source` が文書名やissue名だけの場合、後の版で内容が変化すると「当時何を読んでこのカードになったか」が曖昧になる。

Case 001では比較実験そのものの再現性を確保するため、共通ソーススナップショットをcommit SHAで固定し、主要主張は可能な範囲でpath + stable identifier + snapshotへ戻せるようにする。

これは直ちに新しい製品機能要求ではない。長期的には採択済みの `InquiryJourneyV1` + 不変 `RoundSnapshotV1` DAG + card lineage が同種の問題を扱う設計であるため、まずその実装・dogfoodが成立した時点で再評価する。

### W6 KJ操作の実行自体と対象側増分を分けていない

R1〜R5が段階を完遂したことは事実だが、束ね・表札・図解を行ったこと自体は価値の証拠ではない。

Case 001以降では「操作したか」ではなく、操作後に新しい生存所見、重要な反証、空白、判断変更が生じたかで評価する。

### W7 後続実装への変換は確認できても因果帰属はできない

dogfoodカードと後続変更が対応していても、その変更がdogfoodだけを原因として生じたとは限らない。

したがってCase 0では「変換経路の存在」を記録し、「KJ Atlasが変更を引き起こした」という因果主張はしない。

## M1〜M9の暫定監査

| 指標 | Case 0での観察可能性 | 暫定所見 |
|---|---|---|
| M1 生存所見 | 一部可 | 後続プロセスへ残った論点はあるが基準線との差は不明 |
| M2 根拠接地 | 中 | R1〜R5では `meta.source` が広く使われるが不変snapshotではない。長期snapshot/lineageは設計済み・L0 Planned |
| M3 異論・残差保持 | 不十分 | 全カードを精査可能だが「最終成果から消えた異論」の対照履歴が弱い |
| M4 早期収束耐性 | 一部可 | R1→R2の部分解決/再評価は正の兆候。段階誘導との分離不可 |
| M5 AI依存校正 | 不可 | Case 0 artifactに比較用rejected proposal ledgerがない |
| M6 再訪・訂正可能性 | 中〜高 | ラウンド別artifactがあり時間差比較が可能 |
| M7 注意・探索制御 | 一部可 | 技術だけでなくプロセス/認知へ探索が広がるが基準線との差は不明 |
| M8 決定への変換品質 | 中〜高 | 三要素テンプレート等の後続変更へ接続した例あり |
| M9 認知摩擦 | 不可 | 操作負担・有益な立ち止まりの記録が不足 |

数値スコアへ集約しない。

## Case 0からCase 001へ引き継ぐ設計要件

1. **同じ問い・同じ資料を複数armへ与える。**
2. **内部資料だけのRound 1と、外部研究/競合を加えたRound 2を分ける。** 先に市場カテゴリや外部言説へアンカリングしない。
3. **AI提案の採用・修正・棄却を比較用に保存する。** M5を観測可能にする。
4. **provenanceとepistemic statusを分離する。** 出典があることと、そのカードが事実であることを混同しない。
5. **最終叙述から元材料への戻し監査を行う。** 消えた異論・孤立・不確実性を調べる。
6. **KJ操作を行った回数を成果指標にしない。** 対象側で生存した差だけを見る。
7. **実装反映後にrevisitする。** 判断が実装・第三者利用で耐えたかを後から確認する。
8. **既存のInquiryJourney設計を無視して重複機能を起票しない。** Case 001で不足が出た場合も、L0 Plannedの設計で解くべきか、新しい要求なのかを先に分ける。

## Case 0の結論

R1〜R5は、KJ Atlasが「自分自身の複雑な開発問題を時間をまたいで外部化し、再訪し、具体策へ変換する」用途へ既に自然発生的に使われていることを示す。

しかし、現段階で確認できるのは**実用可能性の兆候**であり、認知増分の因果証拠ではない。

最も価値のある成果は、Case 0を成功物語として使うことではなく、そこに欠けていた対照・比較用棄却履歴・実行snapshot・摩擦観察をCase 001の設計へ戻しつつ、すでに採択済みの長期探究snapshot/lineage設計を重複して再発明しないことである。
