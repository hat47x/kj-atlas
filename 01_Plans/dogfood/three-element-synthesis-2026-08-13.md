# 三要素分析法によるドッグフーディング結果の統合 — 設計への回収と抜け漏れの再回収

- 区分: 結果分析（R3 本質追求）の三要素版 / 更新: 2026-08-13
- 対象: 2026-08-12〜13 のドッグフーディング全発見（DOGFOOD-01〜08, METRIC-01, DX-DESIGN-CHECK-01, DX-CONTRACT-DRIFT-01, SEC-AI-SAFEMODE-01, SEC-LLM-AUDIT-01, SEC-HEADERS-01, SEC-RATE-LIMIT-01, SEC-DOC-BOUND-01, DOMAIN-CARD-TEXT-01, UI-RESILIENCE-01 ほか）
- 方法: `ADR-0067` 三要素分析法（業務設計／データ設計／機能設計の相互牽制）。正本 `01_Plans/adr/ADR-0067-three-element-constraint-design-method.md`
- 関連: `dogfood-analysis-synthesis-2026-08-12.md`（原因A/B の一般形はこちらで定義済み）

## 1. 目的

`dogfood-analysis-synthesis-2026-08-12.md` は「検証経路の正常系偏重」と「測定器と測定対象の同一管理」を根本原因として抽出した。本分析はこれを**三要素分析法のレンズで読み直し**、(a) 各発見がどの次元の不整合か、(b) どの設計規則へ回収できるか、(c) そこから見える抜け漏れを何として再びドッグフーディングへ回収するか、を定める。

## 2. 三要素による横断分類

ADR-0067 の核心は「**三者が揃わない設計判断は着工しない**」。ドッグフーディング発見の大半は、この原則が**実装レベルで破られた**事例である。以下、次元別に分類する。

| 次元 | 発見（番号は dogfood README の改善記録に対応） | 不整合の本質 |
|------|------|------|
| **業務→機能 の未強制** | SEC-AI-SAFEMODE-01（未レビュー本文のAI入力禁止が API に未実装）、SEC-LLM-AUDIT-01（外部LLM送出が監査未配線）、JIT provisioning（未認証ユーザー作成禁止が既定値に未反映） | 業務の「何をしてはならないか」が機能設計の API 契約・ミドルウェアに落ちていない |
| **データ↔機能 の非対称** | DOGFOOD-02（GET/PUT 検証非対称）、DOMAIN-CARD-TEXT-01 タイトルギャップ（backend 無界 vs frontend 500）、SEC-DOC-BOUND-01（カード件数無界）、SEC-HEADERS-01（本番 docs 常時有効） | 同一データフィールドの read/write・frontend/backend で境界が非対称 |
| **機能=検出器 vs 業務=指標 の同一管理** | DX-DESIGN-CHECK-01 / DX-CONTRACT-DRIFT-01（検出器を弱めて指標を満たす）、DOGFOOD-METRIC-01（構造の定式化） | 測定器と測定対象が同一主体の管理下にあり、弱体化が改善に見える |
| **機能=検証 が 業務=実使用 を検証しない** | DOGFOOD-03/04/06（検証スクリプトが正常系のみ） | 検証機能が「経路の存在」だけを見て「実際に使えるか」を見ない |
| **境界の適用範囲が未明示** | DOGFOOD-05（MCP 未レビュー不可視）、DOGFOOD-07（.gitignore 無アンカー）、api.md 記述先行（assess-card-importance 未実装） | 安全境界・データ境界の帰結が文書化されていない |

## 3. 共通根本原因（三要素版）

`dogfood-analysis-synthesis` の原因A/B（正常系偏重・理想状態前提）は、三要素で読むと次に集約される:

> **「一次元の変更・実装が、他の二次元との牽制（三要素整合）を通っていない」**

- 業務の禁止事項（SafeMode・監査・レート制限）を**機能へ実装しても、実行時に強制する契約・テストまで落としていない**（Cluster 1）。
- データ境界（上限・検証）を**片方の実装（frontend or read or write）にだけ入れ、対称化していない**（Cluster 2）。
- 検出器（機能）と指標（業務）を**別々の主体として牽制していない**（Cluster 3）。

これは ADR-0067 が設計時に防ごうとした失敗が、**実装・運用の層で再発**していることを示す。設計判断の三要素検証は ADR 化済み（ADR-0075 で 76/76）だが、**実装の三要素検証（着工前チェック）が実行時まで貫徹していない**。

## 4. 設計への回収（設計規則として抽出）

| # | 設計規則 | 根拠となった発見 | 回収先 |
|---|---------|-----------------|--------|
| R1 | **業務の禁止事項は「機能に実装する」だけでなく「実行時に強制する」**。API 契約に明示パラメータ/ミドルウェアとして存在し、テストで固定する | SEC-AI-SAFEMODE-01, SEC-LLM-AUDIT-01, JIT provisioning, SEC-RATE-LIMIT-01 | AGENTS.md §7（安全不変条件）に「実行時強制」を明記検討 |
| R2 | **データ境界と機能検証の対称性**。同一フィールドの read/write・frontend/backend・各エンドポイントで境界を対称にする | DOGFOOD-02, DOMAIN-CARD-TEXT-01, SEC-HEADERS-01 | AGENTS.md §5（変更時の追随範囲）に「対称性」を追記検討 |
| R3 | **測定器ごとに能力カナリアを置く**。既知の陽性を検出し続けることをテストで固定 | DX-DESIGN-CHECK-01, DX-CONTRACT-DRIFT-01 | 既に DOGFOOD-METRIC-01 案A で採択・2測定器に適用。`codegen/ai_eval` 手記録系は別途 |
| R4 | **検証経路は正常系＋異常系の両方を assert** | DOGFOOD-03/04/06 | 既に dogfood README「検証経路の追加規約」で採択 |
| R5 | **境界の適用範囲を明示**。fail-closed の帰結（何ができないか）を文書化 | DOGFOOD-05, DOGFOOD-07 | 既に DOGFOOD-05 案A で MCP に適用。他境界へ横展開 |

## 5. 抜け漏れの再回収（新たなドッグフーディングターゲット）

三要素分析から、以下が**未回収の抜け漏れ**として浮かび上がった。これらを再びドッグフーディングへ回収する。

| # | 抜け漏れ | 三要素上の欠落 | ドッグフーディングへの回収方針 |
|---|---------|---------------|------------------------------|
| G1 | **SEC-AI-SAFEMODE-01（P0）が最大の三要素不整合のまま** | 業務禁止事項が機能未実装 | ADR-0068/0069 採択後に「未レビュー本文を送ると実行時に拒否/マスクされる」ことを実APIで検証する。現在は判断待ち |
| G2 | **新規実装の三要素検証（着工前チェック）が手順化されていない** | 実装層の三要素整合 | JIT fail-closed・レート制限・エラーバウンダリ等の実装に、業務/データ/機能の三要素検証欄を適用する規約を dogfood README に追加するか検証 |
| G3 | **文書サイズ/カード件数の上限値が未決定**（SEC-DOC-BOUND-01） | データ境界の値 | Org-A 大量カード（50/500/20,000枚）の**実際の利用実態**をドッグフーディングで実測し、上限値の判断材料を供給する |
| G4 | **逆方向ドリフト（api.md 記述先行・陳腐化）を検出する能力が無い** | 機能（検出器）の盲点 | `check_contract_drift.py` は routes→api.md 方向のみ。api.md→routes 方向の検出を追加するか、ドッグフーディングで判断する |
| G5 | **W型 inquiry が prototype のまま業務領域カバレッジから脱落** | 業務（価値経路）が機能（SaaS前提・frontend未統合）と不整合 | single-tenant で W型保存が使える要件をドッグフーディングで検証し、production 化の優先度を判断する |
| G6 | **逆方向の文書化（未実装機能の api.md 記述）を網羅的に洗い出す** | データ（契約文書）と機能（実装）の乖離 | `assess-card-importance` 以外の記述先行エンドポイントが無いか、横断監査をドッグフーディングの対象にする |

### G4/G6 の監査結果（2026-08-13 実施）

api.md 全53エンドポイント × backend 全42ルートの横断監査を実施。**逆方向ドリフト（api.md 記載・backend 未実装）は全11候補中、真の未マーカーは `POST /ai/assess-card-importance` のみ（前巡で「未実装（計画）」を付与済み）**。

| 候補 | 判定 |
|------|------|
| `POST /ai/assess-card-importance` | 真の逆方向ドリフト（未実装をマーカー無しで記載）→ 修正済み |
| `POST/GET/DELETE /admin/agent-registrations` | §9.5 が「契約先行固定（実装は EXT-CONN-02）」と明記 → 整合 |
| `POST /v1/audit/proposals:verify` | §2.7.2「contract-only」と明記 → 整合 |
| `POST /docs` | §52「将来候補」と明記 → 整合 |
| `GET /healthz` / `/docs` / `/openapi.json` / `/redoc` | main.py・FastAPI 標準（監査スコープ外） |
| `GET /tenant-admin/document-access` | 実装済み（空パスのルートを監査 regex が拾えず偽陽性） |

→ 逆方向ドリフトは**よく管理されており**、残る課題は「手動監査に依存」というプロセス面のみ。`check_contract_drift.py` に自動の逆方向チェックを追加するか、手動監査を定期化するかは維持者判断（自動化は「計画」と「漏れ」の区別が人間判断を要するため、偽陽性が多くなる）。

## 6. 次の一手

1. G1（SEC-AI-SAFEMODE-01）は ADR-0068/0069 の採択が唯一のアンブロック手段 — 人間判断待ち。
2. G2〜G6 は本ドッグフーディングループで直接着手可能:
   - G4/G6: 逆方向ドリフト検出の横断監査（実装可能・低リスク）
   - G3: カード件数の実利用実態の計測（判断材料の供給）
   - G2: 実装の三要素検証規約の追加（プロセス改善）
   - G5: W型の single-tenant 検証（業務領域カバレッジ）
3. R1/R2（実行時強制・対称性）は AGENTS.md の安全不変条件・追随範囲への追記として人間判断を仰ぐ。
