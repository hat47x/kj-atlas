# ドッグフーディングのパターン多様化 — 導入組織の具体的イメージに基づく分析

- 区分: 分析 / 更新: 2026-08-12
- 目的: 現在のドッグフーディングが「開発者自身による自己言及（kj-atlasでkj-atlasを管理）」の単一パターンに偏っていることの是正。
  導入組織の具体的なイメージを複数固定し、それぞれのドッグフーディングパターンを具体化する。
- 関連: `01_Plans/dogfood/README.md`（W型サイクル）, `02_Architecture/dogfooding-ai-collaboration-plan.html`, `ADR-0042`
- 背景: README の想定利用者は「複雑な問題の初期探索 / 定性情報の整理 / チーム・個人の思考可視化 / 研究・企画・設計・政策・プロダクト検討の前段整理」。

## 1. 現状の問題

- ドッグフーディングの題材は全て「本プロジェクト自身の設計判断・issue・ADR」。
- そのため KJ 操作（カード化・束ね・表札・関係線・島形成）のうち、**開発文書管理で使われる操作だけが毎回走る**。
- 未分化な「違和感」「保留」「曖昧な意味」を扱う操作（Critique 検出・Hold 状態・未整理の維持）や、
  定性データを大量に投入する操作は、自己言及題材では起動しにくい。
- 結果、R1〜R6 の「結果分析」が開発プロセス摩擦に偏り、本ツールの根幹価値（曖昧さを殺さない）の検証が偏っている。

## 2. 導入組織の具体的イメージ（4種）

README の想定利用者を4つの具体的組織イメージへ分解する。

### Org-A: 地方自治体の政策企画課（3〜5人チーム）

- **課題**: 住民意見・アンケート自由記述・各課のヒアリングメモという不定形な定性情報から、政策の論点構造を探索。
- **使う局面**: 最初の論点が固まっていない段階で、意見の「違和感」「対立」を殺さずに俯瞰したい。
- **期待される KJ 操作**: 大量カード投入 → 束ね → 表札 → 関係線（特に「矛盾」「対立」）→ 島形成。政策決定前の合意形成資料。
- **ドッグフーディングパターン**: 自由記述データのバッチ投入（Web の一括カード作成 / API での投入）、50枚超のカード操作、Critique 検出の実運用。

### Org-B: プロダクト開発チームのユーザーリサーチ担当（1人＋分析支援）

- **課題**: インタビュー記録・利用ログ所見・サポート問い合わせから、ユーザー価値と課題の初期仮説を探索。
- **使う局面**: 定量データが出る前の仮説段階。個人の「なんとなく違う」を言語化する。
- **期待される KJ 操作**: インタビュー発言のカード化 → 保留（Hold）を多用して確定を先送り → 個人の違和感メモ → チーム共有。
- **ドッグフーディングパターン**: Hold / Critique 状態を多く残したまま保存・再読込する操作の長期連続利用。共有前確認（レビュー境界）の日常化。

### Org-C: 研究機関の共同研究者グループ（2〜3名の非同時利用）

- **課題**: フィールドノート・文献メモという研究者個人の記録を、共同で構造化したい。
- **使う局面**: 研究者各人が個別にカードを積み、一定間隔で合流して島構造を作る。
- **期待される KJ 操作**: 個人作業（非同時）と共同俯瞰の往復。文書単位のアクセス制御。
- **ドッグフーディングパターン**: 非同時・複数人利用。保存文書を他メンバーが開いて島形成する導線。**現在は single-tenant であり、multi-org 相当の分離は検証不能**。

### Org-D: 企業の新規事業企画（個人による思考の外部化）

- **課題**: 漠然とした事業アイデアを、結論を急がずに構造化したい。
- **使う局面**: 一人で長時間、曖昧なまま思考を進める。途中で「分からない」を明示的に残す。
- **期待される KJ 操作**: 低深度のカード化を DeepSeek に委譲 → 違和感の言語化 → ナラティブ（B型叙述）で俯瞰。
- **ドッグフーディングパターン**: AI 提案（proposal-only）の実使用。DeepSeek 実APIの長時間利用。ナラティブ生成の品質評価。

## 3. パターン多様化の観点（Org 別 × 利用経路 × 検証軸）

| Org | 主経路 | 主操作 | 現在の検証状態 | 具体化の第一歩 |
|-----|--------|--------|---------------|----------------|
| A 自治体政策 | Web（大量カード） | バッチ投入・島形成・Critique | 未着手（Web の大量カード操作は既存 e2e でも未カバー） | 50枚自由記述投入のドッグフードログ |
| B プロダクトUX | Web（Hold/Critique） | 保留・違和感の長期保存 | **実走行済み（2026-08-12）**: APIでHold/Critique週跨ぎ保存→再読込を確認（held2/shelved1/critiqued2・テキスト無傷） | Hold/Critique を残したままの週跨ぎ利用。MCP面は作業状態非出力（DOGFOOD-08） |
| C 研究共同 | API（非同時利用） | 文書共有・島形成合流 | **multi-org は ADR-0074/SAAS-TENANT-01 のゲート待ち** | single-tenant での共有導線の先行検証 |
| D 新規事業 | MCP（AI委譲） | DeepSeek カード化・ナラティブ | 部分（ai_eval_results.md で 2 操作実用可） | MCP 経路での AI 提案活用の実走行 |

### 利用経路の多様化との対応（DOGFOOD-02/03/04 の知見）

- Web 経路: 主として Org-A/B。UI の摩擦は QA-MONKEY-10 等で実証済み。
- API 経路: Org-C の非同時利用・バッチ投入。`verify_api.sh` が route 存在チェックを提供（DOGFOOD-04 で 503 の見逃しを起票）。
- MCP 経路: Org-D の AI 委譲。`verify_mcp.mjs` が isError 応答を正しく扱えない（DOGFOOD-03）。

## 3.5 実走行の知見（2026-08-12、Org-Aバッチ投入 + Org-DのMCP委譲）

Org-Aのバッチ投入パターンを実走行した（`PUT /docs/dogfood_orga_batch_20260812`、50枚の自由記述カード、0.14秒）。

### 発見1: APIバッチ投入は正常動作

- 50カードを一括PUTで保存できた（HTTP 200、0.14s）。Webの一括カード作成UIを介さないAPI経路は、Org-Aの「自由記述の一括投入」に十分な性能。
- MCPの`get_context_projection`も50カード文書に対して正常動作（bundleHash計算・反スコアリング語彙なし）。

### 発見2: MCP経路は未レビューカードを一切露出しない（Org-Dの価値ギャップ）

`safeMode: false` でも `reviewed-only` / `evidence` / `contradiction` / `summary` の全constraintで
**未レビュー50枚のカードが `cards=0`** になる。レビュー済み3枚に変えると `cards=3` で実テキストが出る
（`safeMode: true` では `[REDACTED]`）。これは SEC-CONTEXT-PROJECTION-01 の意図通りのfail-closed設計。

- **業務設計**: READMEは「LLMを伴走者として、違和感・保留・未分化な意味を起点に思考を深める」ことを謳う。
- **データ設計**: SEC-CONTEXT-PROJECTION-01 は未レビューカードのid/refすらMCP出力に含めない。
- **機能設計**: MCP経路は実質 `reviewed-only` 制約しか使えず、初期探索（未レビュー段階）ではAIに何も見えない。

→ **三要素不整合**: 業務設計上の「AI伴走者が初期探索で協働する」価値と、データ/機能設計の
「未レビュー内容はAIへ一切開示しない」が衝突する。MCP経路はOrg-Dの「AI委譲による初期探索」を
現状では支援できない（レビュー後でないとAIが素材を見られないため）。

このギャップは「安全境界の緩和」ではなく「経路の適用範囲の明示」として扱うべき。
現状のfail-closedを維持したまま、MCP経路が「初期探索では何も見られない」ことをドキュメント化し、
AI委譲の対象を「レビュー済み以降の整理」に限定するか、または別途、未レビューを別の安全境界で
扱う探索専用経路を設計するかが判断になる。

## 3.6 実走行の知見（2026-08-12、Org-BのHold/Critique週跨ぎ）

Org-Bの「保留・違和感を残したまま週跨ぎで開き直す」パターンを実走行した
（`PUT/GET /docs/dogfood_orgb_hold_20260812`、5カード: held2/shelved1/critiqued2）。

### 発見1: API（永続化）は価値経路を満たす

- 保存→再読込で **Hold/Critique 作業状態が完全に維持**される（held2/shelved1/critiqued2・全テキスト無傷）。
- 「確定させない状態を週跨ぎで保つ」根幹価値が API 経路で成立することを初めて実証。

### 発見2: MCP（AI協働）は作業状態を出力しない → DOGFOOD-08 起票

- `get_context_projection`（`safeMode:false`・`reviewed-only`）はレビュー済みカードの実テキストは返すが、
  **`holdState` も `critique` も出力しない**（`ProjectedCard` スキーマに無いため）。
- AI伴走者が「どのカードを確定させず残すか」を読めないため、Org-B の協働支援に使えない。
- これは DOGFOOD-05（未レビュー不可視・fail-closed）とは独立のスキーマ欠落。→ `issue-DOGFOOD-08`

## 4. 複数組織の同時利用（multi-org）

- 現状: `saas-multitenant` は settings.py では受理されるが、`ADR-0074`（server-owned SaaS session）が Proposed、
  `SAAS-TENANT-01` が In Progress であり、**実装・検証のゲート未達**。runtime_parameter_registry の
  「`saas-multitenant` は現行releaseで選択不可」が実態を表す。
- ドッグフーディング上の意味: **Org-C（研究共同）は現在の single-tenant では実地検証できない**。
  multi-org を検証する前提として、まず「同一インスタンスで複数文書を別アクセス境界で運用できること」を
  single-tenant のアクセス制御（ADR-0059 等）で先行検証する段階が残っている。
- 推奨: multi-org の設計検証は ADR-0074 採択後に再開し、その前に「文書単位の共有境界」の dogfood を進める。

### 実地確認（2026-08-12）: saas-multitenant の起動ゲートは fail-fast で機能する

`KJ_ATLAS_RUNTIME_PROFILE=saas-multitenant` で backend を起動すると、必須アダプタ欠損時に
起動拒否されることを実地確認した:

```
RuntimeError: trusted SaaS runtime policy is incomplete: PostgreSQL tenant DB guard,
disabled JIT provisioning, external access control, deny fail-safe mode, external
document policy binding, external tenant capability resolution
```

- ADR-0063 D9 の「不足時は fail-fast」と `runtime_parameter_registry.md` の「無視して local-dev や in-memory へ
  fallback しない」が実装どおり機能することを確認。
- **multi-org の実利用はここで確実に遮断されている**。つまり Org-C（研究共同）の同時利用は、このゲートを
  満たす外部アダプタ一式（PostgreSQL + external PDP/binding/capability + JIT無効 + deny fail-safe）が揃うまで
  実地検証できない。本確認は「選択不可」が文書上の言い分だけでなく実装の強制であることを実証する。

## 5. 三要素分析（パターン多様化における整合）

| 次元 | 主張 | 制約 |
|------|------|------|
| 業務設計 | 各導入組織が「曖昧さを殺さずに探索する」同じ根幹価値を、異なる操作配分で使う | パターンは題材（定性データ vs 開発文書）を変えて検証する必要がある |
| データ設計 | 大量カード・長期保留・複数人共有は、文書・カード・状態のデータ境界を変える | 現在の document 契約（DocumentV1）は多人数共有を前提としない |
| 機能設計 | Web/API/MCP の経路ごとに検証経路を分離する | 検証経路自身のエッジ（DOGFOOD-02/03/04）が未完成 |

## 6. 次の一手（R5 具体策候補）

1. **Org-A のバッチ投入ドッグフード**: 50枚の自由記述を投入し、島形成までを通す記録（Web 経路の大量カード検証）。
2. **Org-B の週跨ぎ保留ドッグフード**: Hold/Critique を残した文書を翌週に開き直す操作を記録。
3. **Org-C の共有導線先行検証**: single-tenant のまま「文書を別メンバーが開く」操作を検証（multi-org ゲート前の先行）。
4. **Org-D の MCP 経路活用**: MCP 経由で AI 提案を実際に使い、提案品質を記録（DOGFOOD-03 の修正後）。
