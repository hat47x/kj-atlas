# 高度ドッグフーディング・シナリオ設計（E2Eテスト題材）

本資料は、これまでのドッグフーディング（iteration 176〜238・シナリオ106〜168）で**浅かった領域**を三要素分析（ADR-0067: 業務/データ/機能設計）の観点から洗い出し、次段階の高度ドッグフーディングとして**E2Eテスト題材に転用できるシナリオ群**を設計したものである。

KJ法の題材は一貫して **「kj-atlas 自身のプロダクト改善」** とする。調査対象は本プロジェクトの全文書（`00_Prompt`〜`04_Documentation`）・ソース（`03_Implement`）・コミット履歴（`git log`）・計画文書（`01_Plans`）である。

## 1. これまでのドッグフーディングで浅かった領域

既存の `verify_business_flow_e2e.sh`（シナリオ1〜168）は、各シナリオが**単一の想定人物・単一業態・4カード程度の小規模キャンバス**で、1〜7個のAI操作を固定してきた。以下の領域が未到達または浅い。

| 領域 | 現状 | ギャップ |
|------|------|---------|
| **組織内の複数部署** | 単一業態・単一人物のみ | 部署（開発/運用/サポート/営業等）が各々の視点でカードを出し、1キャンバスへ統合するフローが未到達 |
| **大量カード** | 各4カード程度 | 30〜50枚のカードを1キャンバスで扱い、束ね・島統合の実物大フローが未到達 |
| **階層化（parentIslandId）** | 単層の島のみ | 島→上位島→さらに上位 の階層化・A型図解が未到達（`schemas.md` に `parentIslandId` 契約はあるがE2E未固定） |
| **A型図解→B型文章化** | ナラティブ生成のみ | 図解の関係線（5種別）を踏まえたA型図解の作成→B型文章化の一気通貫が未到達 |
| **高度KJ法の複数ラウンド** | 3ラウンド循環（発散/構造化/深化）のみ | W型6ラウンド（R1問題提起〜R6手順計画）・ラウンド間の戻り・途中保存再開が未到達 |
| **ロール区分** | 管理面/業務面分離の単体テストのみ | システム管理者/業務管理者/一般ユーザ/閲覧専用ユーザ の4区分で**1つのKJ実践を貫く**境界固定が未到達 |
| **洞察の質・コラボレーション性・可読性** | 操作の正パス・接地（機械的検証）のみ | 生成AI単独より質の高い洞察・人間×AIの協働性・AI出力の人間による読み解きやすさ の評価が未到達 |

### 1.1 本質的価値と評価基準（評価軸としての位置づけ）

kj-atlas を生成AIから利用できるようにすることの本質的価値は、**最終的に得られる洞察の質が生成AI単独よりも高い**ことにある。これは `00_Prompt/ai_cognitive_externalization_requirements.md`（生成AIの認知外在化環境）と `02_Architecture/value_traceability.md`（V1外在化→V2構造化→V3レビュー→V4共有と学習）が定義する価値判断に直結する。したがって、高度ドッグフーディングでは三要素分析（業務/データ/機能）に加えて、次の3つを**第4の評価軸**として設ける。

| 評価基準 | 意味 | 上流の価値判断（正本） | E2Eでの検証観点 |
|---------|------|----------------------|----------------|
| **洞察の質** | 人間×生成AIの協働で得た洞察が、AI単独の自動生成より深い・妥当である | 認知外在化・「意味を急いで確定しない」 | AI自動生成の解答と、人間が保留・違和感・採否を残して得た解答の差を固定 |
| **コラボレーション性** | AIが人間の判断を先取りせず、人間が介入・採否できる余地が十分に残る | 「人間の判断を優先する」（proposal-only・`human_reviewed` 人手昇格・中間処理/最終判断の二層化） | auto-apply なし・レビュー状態の明示・AI由来/人間由来の区別 |
| **可読性** | AIの解答内容・画面表示が、人間の立場から分かりやすく・読み解ける | V4「読者が確定点・保留点・根拠を理解できる」・表札の代弁性・ナラティブの接地 | 表札が島を代弁する述語文・ナラティブが図解に接地・保留/根拠の明示 |

> これらは機械的な assert だけでは評価しきれない側面を含む。E2Eでは**決定性の担保できる部分**（proposal-only・レビュー状態の明示・接地・AI由来/人間由来の区別）を固定し、**定性的な質評価**（洞察の深さ・読み解きやすさ）は人間評価の観点として別途記録する（`AI-EVAL-01` の枠組みを再利用）。

## 2. ロール区分と三要素の対応

`ADR-0072`（管理面認可分離）・`ADR-0059`（SaaSテナント認可境界）・`SEC-ADMIN-PLANE-01` より、kj-atlas のロールは**構造境界**（管理面/業務面）と **IdP由来の transient 権限**（roles/groups→`effectiveCapabilities`）で構成される。高度ドッグフーディングでは、これを以下の4区分で整理する。

| ロール | 業務設計（何をして何をしないか） | データ設計（境界） | 機能設計（API経路） |
|--------|-------------------------------|-------------------|-------------------|
| **システム管理者** | テナント/モデル/IdPの登録・allowlist・監査照会。文書の内容には触れない | 管理面（control plane）のみ。業務面の文書データへ到達しない | `/admin/provision/**`（`X-Admin-Api-Key`） |
| **業務管理者** | テナント内の文書ライフサイクル・共有設定・モデル利用可否の運用。文書内容の編集はしない（原則） | テナント境界内の管理面データ（allowlist・監査） | 管理API（テナントscope）＋ read-only な監査参照 |
| **一般ユーザ** | 文書の作成・カード化・島化・AI提案の採否。KJ実践の主体 | 自テナントの文書（CRUD）+ AI操作の入力 | `PUT/GET /docs/**`・`POST /ai/**`・`/ai/proposals/**` |
| **閲覧専用ユーザ** | 読む（投影・監査・島・ナラティブの参照）のみ。書けない・採否できない | read-only。文書への write・AI提案の決定は不可 | `GET /docs/**`（`X-Read-Only`）・read-only MCP |

> 三要素牽制の要点: **業務設計**（ロールの責務）と**機能設計**（到達経路）と**データ設計**（境界）が一致し、一般ユーザが管理面へ、閲覧専用ユーザが write へ、システム管理者が文書内容へ それぞれ**到達できない**ことを E2E で固定する。

## 3. シナリオ群

以下の4群・13シナリオを設計する。各シナリオは既存のシナリオ表形式（業態/想定人物/業務領域/操作内容/注意事項）に沿い、E2Eアサーションへ落とせる粒度で記す。

### シナリオ群 A: 複数部署×1キャンバス統合（大量カード→島→階層化→A型図解→B型文章化）

**共通題材**: kj-atlas のプロダクト改善。4部署（開発・運用・サポート・営業）が、ドッグフーディング運用で各々が観察した課題をカードとして持ち寄る。

#### A-1 複数部署の声を1キャンバスに大量カード化→束ね→島統合

| 軸 | 内容 |
|----|------|
| 業態 | ソフトウェア開発組織（kj-atlas プロジェクト自身） |
| 想定人物 | プロダクトオーナー（4部署の声を統合） |
| 業務領域 | 開発（モック検証深度）・運用（CLI/admin console）・サポート（エラー回復）・営業（SaaS採用）の課題カードを1キャンバスに統合 |
| 操作内容 | 文書作成 → **40枚のカード作成**（4部署×10枚） → 束ね(suggest-card-groups) → 島要約(suggest-island-summary) → 読戻し |
| 注意事項 | 大量カード（40枚）でも**束ねがカードを欠落させない**・**島要約が全メンバーへ接地**することを固定。カードは部署名を接頭辞（dev/ops/sup/sales）で保持し、束ね後に部署帰属を失わない |

**三要素**: 業務=部署横断の合意形成、データ=40カード・島の全接地、機能=suggest-card-groups/island-summary の大規模入力。

#### A-2 島の階層化（parentIslandId）→A型図解

| 軸 | 内容 |
|----|------|
| 業態 | ソフトウェア開発組織 |
| 想定人物 | プロダクトオーナー |
| 業務領域 | A-1で得た島（4部署の島）を**上位島**へ統合し、階層化 |
| 操作内容 | 文書作成（階層島） → 島間関係要約(summarize-island-relation) → 島の親子関係（parentIslandId）の往復保持 → 読戻し |
| 注意事項 | **parentIslandId が save/reload で往復保持**される（`schemas.md:864`）。階層化された島の関係線（因果/対立）をA型図解として固定 |

**三要素**: 業務=階層による抽象度の上昇、データ=parentIslandId の往復保持、機能=summarize-island-relation・島の親子。

#### A-3 A型図解→B型文章化（ナラティブ）

| 軸 | 内容 |
|----|------|
| 業態 | ソフトウェア開発組織 |
| 想定人物 | プロダクトオーナー |
| 業務領域 | A-2の階層化されたA型図解（島＋関係線）から、B型のナラティブ（改善の提言）を生成 |
| 操作内容 | ナラティブ(generate-narrative) → A/B照合(check-narrative) → 読戻し |
| 注意事項 | **階層化された図解の読み順に沿った叙述**・**A/B照合が複数階層の島の取りこぼしを検出**（b_missing_in_a/a_missing_in_b） |

**三要素**: 業務=図解→文章の提言、データ=階層島を読み順に叙述、機能=generate-narrative/check-narrative。

### シナリオ群 B: 高度KJ法の複数ラウンド（W型6ラウンド）

**共通題材**: kj-atlas の「W型累積KJ法の到達度」を問いとして深める。`00_Prompt/w_type_iterative_inquiry_requirements.md`（R1問題提起〜R6手順計画）に沿う。

#### B-1 R1問題提起→R2現状把握→R3本質追求（前半ラウンド）

| 軸 | 内容 |
|----|------|
| 業態 | ソフトウェア開発組織（kj-atlas 自身） |
| 想定人物 | 調査研究員（W型探究の主体） |
| 業務領域 | R1（なぜW型6ラウンドが未到達か）→ R2（現状の3ラウンド循環と6ラウンドの差）→ R3（本質=「ラウンド間の引き継ぎ・戻りの支援不足」） |
| 操作内容 | inquiry-bundle 作成 → 各ラウンドの RoundRecord 保存 → ラウンド成果（RoundSnapshot）の保存 → 読戻し |
| 注意事項 | ラウンド段階（R1/R2/R3）と反復番号の分離、**ラウンド成果が読取専用で保存**される（`WIR-03`）ことを固定 |

**三要素**: 業務=問いの深化（段階×反復）、データ=RoundRecord/RoundSnapshot の保存、機能=inquiry-bundle の CAS。

#### B-2 R4構想計画→R5具体策→R6手順計画（後半ラウンド）

| 軸 | 内容 |
|----|------|
| 業態 | ソフトウェア開発組織 |
| 想定人物 | 調査研究員 |
| 業務領域 | R4（構想: ラウンド間引き継ぎUI）→ R5（具体策: 各ラウンド成果の読取専用スナップショット）→ R6（手順: 実装計画） |
| 操作内容 | 後半ラウンドの RoundRecord 保存 → ラウンド成果の保存 → 読戻し |
| 注意事項 | 6ラウンド全段階の保存・**後続ラウンドが前段階の情報を辿れる**（出典・根拠の traceability）ことを固定 |

**三要素**: 業務=手順化への収束、データ=6ラウンドの履歴、機能=RoundRecord の traceability。

#### B-3 ラウンド間の戻り・途中保存再開（非直線進行）

| 軸 | 内容 |
|----|------|
| 業態 | ソフトウェア開発組織 |
| 想定人物 | 調査研究員 |
| 業務領域 | R5の検証で仮説不支持→**R3へ戻る**（後続知見から前の問いへ戻る）→ 中断→再開 |
| 操作内容 | 同一段階の複数回反復（RoundIteration）→ 古い If-Match での並行編集検出（409）→ 再開 |
| 注意事項 | 同じ段階を複数回反復でき（`WIR-02`）、**中断後も同じラウンド成果から再開**できる。楽観的並行制御（CAS）を固定 |

**三要素**: 業務=フィードバックの往復、データ=RoundIteration・CAS、機能=If-Match の並行制御。

### シナリオ群 C: ロール区分の操作境界

**共通題材**: 上記A/B群のKJ実践（kj-atlas プロダクト改善）を、4ロールがそれぞれの境界でどう関わるか。

#### C-1 システム管理者（control plane）の境界

| 軸 | 内容 |
|----|------|
| 業態 | SaaS運用（kj-atlas を提供する事業者） |
| 想定人物 | システム管理者 |
| 業務領域 | テナント登録・モデル allowlist・IdP登録・監査照会 |
| 操作内容 | `/admin/provision/models` 登録 → テナント allowlist 設定 → 監査照会（`GET /admin/provision/audit`） |
| 注意事項 | **業務面の文書へ到達しない**・**業務キー（business-plane key）では管理面へ到達できない**（401 `control_plane_unauthorized`）ことを固定 |

**三要素**: 業務=管理責務の分離、データ=管理面データのみ、機能=control-plane 認可。

#### C-2 業務管理者（business admin）の境界

| 軸 | 内容 |
|----|------|
| 業態 | SaaS運用 |
| 想定人物 | 業務管理者（テナント責任者） |
| 業務領域 | テナント内のモデル利用可否・監査照会・文書ライフサイクル |
| 操作内容 | テナント allowlist 参照 → 監査照会 → 文書アーカイブ（書込→423） |
| 注意事項 | テナント境界内のみ。**他テナントの文書へ到達できない**（IDOR防止）。文書内容の編集はしない |

**三要素**: 業務=テナント内運用、データ=テナント境界、機能=テナントscope認可。

#### C-3 一般ユーザのKJ実践境界

| 軸 | 内容 |
|----|------|
| 業態 | ソフトウェア開発組織 |
| 想定人物 | 一般ユーザ（開発者/プロダクトオーナー） |
| 業務領域 | 文書作成・カード化・島化・AI提案の採否 |
| 操作内容 | 文書作成 → カード化 → 島要約 → AI提案（propose-island-summary）→ adopt/hold |
| 注意事項 | **管理面へ到達できない**・**AI提案は proposal-only（自動適用しない）**・**未レビュー文はSafeModeで422** を固定 |

**三要素**: 業務=KJ実践の主体、データ=自テナント文書、機能=docs/AI/proposals。

#### C-4 閲覧専用ユーザの read-only 境界

| 軸 | 内容 |
|----|------|
| 業態 | ソフトウェア開発組織 |
| 想定人物 | 閲覧専用ユーザ（外部監査人/上司） |
| 業務領域 | 文書・島・ナラティブ・監査の参照のみ |
| 操作内容 | `GET /docs/**`（`X-Read-Only`）→ 島・ナラティブの参照 → 監査参照 |
| 注意事項 | **書けない**（write は 403/拒否）・**採否できない**・**AI提案を決定できない** ことを固定。read-only MCP 経由の投影読み取り |

**三要素**: 業務=読むだけ、データ=read-only、機能=`X-Read-Only`・read-only MCP。

### シナリオ群 D: 洞察の質・コラボレーション性・可読性（第4の評価軸）

**共通題材**: kj-atlas の「W型6ラウンド未到達」を問いとし、AIが自動生成した解答と人間×AIの協働で得た解答を対比する。評価基準は §1.1 の3軸（洞察の質/コラボレーション性/可読性）。

#### D-1 洞察の質：AI単独 vs 人間×AI協働の対比

| 軸 | 内容 |
|----|------|
| 業態 | ソフトウェア開発組織（kj-atlas 自身） |
| 想定人物 | プロダクトオーナー（人間×AI協働）／ 外部監査人（閲覧専用） |
| 業務領域 | 同じ題材（W型未到達の原因）について、**AIが自動生成した解答**と、**人間が保留・違和感・反対視点を残しつつ得た解答**を対比 |
| 操作内容 | AI提案（propose-opposing-viewpoint）→ 人間の保留/採否 → ナラティブ → A/B照合 → 読戻し |
| 注意事項 | **AI自動適用をしない**（proposal-only）ことで、人間が「意味を急いで確定しない」余地が残り、結果としてAI単独より質の高い洞察（未検証の主張を含まない）に到達できることを固定 |

**三要素**: 業務=洞察の深さ、データ=保留・違和感・根拠の保存、機能=proposal-only・human_reviewed 人手昇格。

#### D-2 コラボレーション性：AIが人間の判断を先取りしない

| 軸 | 内容 |
|----|------|
| 業態 | ソフトウェア開発組織 |
| 想定人物 | 一般ユーザ（開発者） |
| 業務領域 | AI提案（表札・反対視点・統合）に対する人間の採否 |
| 操作内容 | AI提案（propose-island-summary）→ 提案が `status=proposed` のまま → 人間が adopt/hold/reject → レビュー状態の明示 → 読戻し |
| 注意事項 | **auto-apply なし**・**AIが `human_reviewed` を自動付与しない**・**AI由来/人間由来の区別**（`ai_cognitive_externalization_requirements.md` §11.2）を固定。人間の介入余地が十分に残ることを E2E で担保 |

**三要素**: 業務=人間の判断優先、データ=reviewState・出典の区別、機能=proposal-only・patch+approval。

#### D-3 可読性：AIの解答・画面表示を人間が読み解ける

| 軸 | 内容 |
|----|------|
| 業態 | ソフトウェア開発組織 |
| 想定人物 | 閲覧専用ユーザ（上司・外部監査人）／ 一般ユーザ |
| 業務領域 | 生成された表札・ナラティブ・レビューパックを、人間が読み解けるか |
| 操作内容 | 島要約（表札）→ ナラティブ → A/B照合 → レビューパック export → 読戻し |
| 注意事項 | **表札が島を代弁する述語文**（名詞止めでない）・**ナラティブが図解に接地**（読み順の島を参照）・**レビューパックが確定点/保留点/根拠を明示**（V4）することを固定。読者が「どの主張が確定し、どれが保留か」を読み解ける |

**三要素**: 業務=読者の理解可能性、データ=接地・reviewState の明示、機能=表札・ナラティブ・review pack。

## 4. E2Eテストへの展開方針

各シナリオは、既存の検証ハーネス（`verify_business_flow_e2e.sh` 等）へ**新しい自己完結E2Eスクリプト**として固定する。従来の「1シナリオ=1業態=7チェック」の枠を、以下へ拡張する。

| 観点 | 従来（シナリオ1〜168） | 高度ドッグフーディング（本設計） |
|------|----------------------|-------------------------------|
| カード規模 | 4枚程度 | **40枚（A-1）**・階層島（A-2） |
| 島構造 | 単層 | **階層（parentIslandId）** |
| ラウンド | 3ラウンド循環 | **W型6ラウンド＋戻り（B群）** |
| ロール | 単一人物 | **4ロールの境界（C群）** |
| 評価軸 | 操作の正パス・接地のみ | **＋洞察の質・コラボレーション性・可読性（D群）** |
| 検証の主眼 | 操作の正パス・接地 | **境界の fail-closed**（未認可拒否・read-only拒否・管理面分離）＋**人間の判断優先・可読性**（proposal-only・接地・reviewState明示） |

### E2E実装の指針

1. **A群**: `verify_advanced_multi_dept_e2e.sh` を新設。40枚のカード投入→束ね→島統合→階層化→A型図解→B型文章化を一気通貫で検証。`parentIslandId` の往復保持・束ねのカード非欠落・島要約の全接地を assert。
2. **B群**: `verify_advanced_wtype_e2e.sh` を新設。inquiry-bundle で6ラウンド（R1〜R6）を順次保存し、RoundRecord/RoundSnapshot・ラウンド間戻り（RoundIteration）・CAS を assert。
3. **C群**: `verify_role_boundary_e2e.sh` を新設。4ロールの資格情報を切り替えながら、到達可能経路と拒否（401/403/422/423）を assert。管理面/業務面/read-only の境界を fail-closed で固定。
4. **D群**: `verify_collaboration_quality_e2e.sh` を新設。proposal-only（自動適用なし）・`human_reviewed` 自動昇格なし・AI由来/人間由来の区別・表札の代弁性・ナラティブ接地・reviewState明示を assert。定性的な「洞察の質」は人間評価（`AI-EVAL-01` 方式）と併用し、E2Eは決定性の担保できる部分（コラボレーション性・可読性の機械的検証）を固定する。

### モック拡張の指針

高度ドッグフーディングでは、既存の `mock_local_llm.py` に加えて以下が必要になる（いずれも三要素分析を経て起票する）。

- **階層島の接地**: `suggest_island_summary` が親島・子島の関係を保持（`parentIslandId`）。
- **大量カードの束ね**: `suggest_card_groups` が40枚規模でもカテゴリ別に全カードを束ねる（DOGFOOD-20 の拡張）。
- **W型の叙述**: `generate_narrative` が6ラウンドの読み順・階層を叙述。

> D群（コラボレーション性・可読性）は**モックの応答ではなく、backed/UI の既存契約**（proposal-only・reviewState・接地・AI由来/人間由来の区別）を assert するため、モック拡張は原則不要。定性的な「洞察の質」は人間評価の対象であり、モックでは代用しない。

## 5. 未到達領域の優先順位

三要素分析（ADR-0067）の観点で、**データ設計の境界検証**が最も未成熟（read-only・階層・parentIslandId・RoundSnapshot の往復保持が E2E 未固定）。優先順位は以下とする。

1. **C群（ロール境界）**: fail-closed の固定が安全不変条件（ADR-0067・SafeMode・管理面分離）に直結し、最も価値が高い。
2. **D群（洞察の質・コラボレーション性・可読性）**: 本質的価値（生成AI単独より質の高い洞察）を直接検証する。決定性の担保できる部分（proposal-only・接地・reviewState明示）を E2E で固定し、定性的な質評価は人間評価と併用。
3. **A群（階層・大量カード）**: 実物大のKJ実践（階層化・A型図解）がプロダクト価値（価値実現）の中心。
4. **B群（W型6ラウンド）**: 高度KJ法の差別化機能であり、`w_type_iterative_inquiry_requirements.md` の要件充足をE2Eで裏付ける。
