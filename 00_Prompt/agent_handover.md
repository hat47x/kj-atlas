# agent_handover — AIエージェント開発引き継ぎガイド

本ドキュメントは、kj-atlas の開発を **AIエージェント中心で継続可能にするための共通運用ガイド** です。

- 入口: `AGENTS.md`
- 行動規範・概念制約: `system_prompt.md` / `domain.md`
- 本書: 実行順序、DoD、検証、停止・復旧

---

## 1. 目的と完了定義

### 1.1 目的

- 仕様逸脱を抑制しつつ、継続実装・継続検証・継続文書更新を可能にする
- SafeMode 既定ON・漏えい防止（share/export）を維持する
- 中断しても再開しやすい運用を共有する

### 1.2 完了定義（DoD）

次を満たした時点で、引き継ぎ運用は成立しているとみなす。

1. Read Order が共有されている
2. タスク開始時に Scope / Acceptance / Checks を先に固定している
3. 変更順序（00〜02整合 → 03実装 → 04文書同期）を守っている
4. SafeMode・漏えい防止違反をレビューまたはCIで差し戻せる
5. 停止基準・復旧手順・エスカレーション条件が明文化されている
6. 完了判定を、実行コマンドと差分の事実で説明できる

---

## 2. 1タスクの標準フロー

### 2.1 固定順序

1. Scope を決める（Docs / Frontend / Backend / Schema）
2. Acceptance を決める（3〜7項目）
3. Validation plan を決める（tests / lint / docs-check / diff確認）
4. 実装する（上位層整合を確認してから）
5. 検証する
6. 文書を同期する
7. Acceptance を照合して完了判定する

### 2.2 開始テンプレート

```md
## Task Brief
- Scope:
- Non-Goals:
- Acceptance Criteria:
  - [ ] ...
  - [ ] ...
- Validation Plan:
  - [ ] tests/lint
  - [ ] docs sync
  - [ ] safeMode impact
- Stop Conditions:
  - [ ] 上位文書との矛盾
  - [ ] 安全境界への抵触
  - [ ] 必須検証の再現不可
```

### 2.3 Acceptance の最低基準

- 仕様根拠（00〜02）を参照している
- 差分が最小・可逆である
- SafeMode既定ONと漏えい防止を破らない
- 参照導線の更新漏れがない
- 完了判定に使うコマンドまたは確認方法が明示されている

---

## 3. 検証原則

- 完了宣言は **検証結果の事実** を前提とする
- docs-only でも、少なくとも差分確認と必要な docs-check を行う
- 記録として最低限残すのは、**実行コマンド / 成否 / 未実施理由 / 変更ファイル一覧**

検証失敗時は、闇雲に試行せず、原因を切り分けて最小修正で再試行する。上位文書との矛盾が残る場合は、実装継続ではなく停止・論点化へ切り替える。

---

## 4. 継続進行

反復サイクルは次で固定する。

**Plan → Execute → Verify → Record → Continue**

- Plan: 受入条件と停止条件を先に出す
- Execute: 単一スコープで変更する
- Verify: 自動チェック + 目視を行う
- Record: 変更点 / 未対応点 / 理由 / 次の1手を残す
- Continue: 未達条件があれば次タスク化する

中断復帰時に最低限残す情報:

1. 未完了の受入条件
2. 現在のブロッカー
3. 次の1手（再開コマンド / 編集対象）
4. 未反映の文書同期箇所

優先順位は、**Security / SafeMode → 上位層整合 → 回帰防止 → 開発速度** の順とする。

## 5. リリース前チェック

### 必須

- [ ] 変更は宣言スコープ内
- [ ] 上位文書（00〜02）と矛盾なし
- [ ] SafeMode既定ON・漏えい防止を維持
- [ ] 対象範囲の検証を実施
- [ ] `AGENTS.md` / 関連文書 / 対象文書の導線を整合
- [ ] 完了根拠を再現可能なコマンドまたは差分で説明できる

### 条件付き

- [ ] Schema変更: import/export/validation/tests を追随
- [ ] UI視覚変更: スクリーンショットを取得
- [ ] LLM経路変更: 外部サービスとの共有設定・監査項目を確認
- [ ] 人間判断待ち論点: 未確定在庫と承認キューを更新

---

## 6. 停止・復旧・エスカレーション

### 停止基準

- 上位層（00〜02）との矛盾
- SafeMode / 漏えい防止への抵触
- 受入条件に対する重大未達
- 不可逆変更が必要だが承認がない
- 完了根拠を事実ベースで示せない

### 復旧手順

1. 差分をスコープ単位で切り戻す
2. 仕様根拠を再確認する
3. 受入条件と検証方法を再定義する
4. 最小修正で再開する

### 人手エスカレーション条件

- 仕様変更そのものが必要
- 価値判断を伴うトレードオフ
- セキュリティ影響の確信が持てない
- 2案以上に圧縮しても、どれを採るかが上位文書から決まらない

## 7. ツール固有追補

本書は共通運用を定義する。ツール固有の手順は追補として分離する。

- Codex固有: 実行環境制約、利用ツール、PR作成手順
- GSD固有: milestone / phase / verify の運用補助
- MCP / Browser固有: UI確認、スクリーンショット、補助検証
